## SoT に無いプラットフォーム側の成果物は SoT ベースの一括操作が黙って破壊する
2026-07-28、note の送客リンク是正で `note-update-body`（Ctrl+A→Delete→paste の全文置換）を建設部門196本へ流し、**本文内の PDF 添付カードを179本ぶん消した**。添付は note のプラットフォーム機能で `article.md` に一行も現れないため paste では戻らない。売上ログ142件中74件が建設部門＝購入者が既に払った対価が届かなくなった。**是正作業そのものが商品を壊した**。同日、別経路の同型（公開したが添付し忘れ）で¥1,980商品が「末尾に添付」と書きながら添付ゼロで売られていたことも判明。
- **Why:** SoT（リポジトリ）を真実源と設計すると「ライブにしか存在しない状態」が思考から抜ける。一括操作は SoT を正として上書きするので、ライブ固有の成果物は差分としてすら現れず破壊が無音になる。スクリプトに `--images-only`（添付を触らない逃げ道）が既にあった＝既知の破壊だったのに既定で止まらなかったのが決定的。
- **How to apply:**
  - ライブへ一括書き込みする前に「SoT に無いがライブにある物」（添付ファイル・予約設定・プラットフォーム側メタ）を数える。0でなければ破壊するのか保全するのかを明示的に決める。
  - 危険な既定を「逃げ道つき」で放置しない。回避オプションが必要になった時点で既定を逆にすべき（既定で中断し、破壊は明示フラグ `--allow-*` のみ）。
  - 各工程の出口で落とす（横断ゲート1本だと気づくのが遅い）: ①公開して添付忘れ→publish が exit 9、②添付したつもり→attach が live 実測、③全文置換→update が事前中断、④累積ドリフト→横断ゲート。
  - done-log を `.tmp` に置かない（git 管理外＝原因究明時に消えている）。`.claude/state/` の追跡下へ。
  - API フィールドを意味の推測で使わない: note の `remained_file_num` は添付数ではなく、14ファイル添付済みが `0` を返す。著者ログインで `a[href*="api/v2/attachments/download"]` を数える実測で確定。
  - CI で見えないものを CI に載せない: 有料エリアの添付カードは未ログイン HTML に出ない＝Actions からは原理的に不可視。ソース層=CI／ライブ層=ローカルと分ける（[[feedback_gate_zero_coverage_false_pass]]）。

## 外向きの一括操作は案の前に「やらないと何が壊れるか」を実測する（2026-09-24）
本数・間隔・順番の案を出す前に、やらない場合に何が壊れるかを実測し「必須」と「任意」を分けて出す。
- **Why:** PR #598（note 原稿675本のリンク張り替え）の後、`check-note-republish` の「要再公開674本」をそのまま受け、674本の全文置換を段階的に流す案を出した。実際は旧 `/docs/` は本番で301転送されUTMも残るため必須は404を直した1本（配合計算-実戦演習）だけで、ユーザーに「なぜ必要？」と聞かれて初めて絞った。さらに「転送1回分だけ」と説明したが #598 の PR 本文には「Google が旧 URL を正規に選ぶ（重複18件）」という SEO 理由があり読み落としていた。データで確かめると17件のうち7件は note から張られていないのに同じ状態で、note の寄与は未検証（DN-0298 で追跡）。逆方向の誤りも: 「必須は1本」と絞った根拠が #598 の差分だけで、同じ drift に 9/23 18:47 の表示崩れ修正（太字が `**` のまま出る149か所・重複画像）が混ざっていたのを見落とし、DN-0297 で drift を分類して初めて要再公開128本の大半が live で実際に崩れていると分かった（公開 API で `**` を確認）。全文置換は有料境界・画像・PDF を壊しうるので不要な分まで流すのは害。
- **How to apply:** surfacer の件数（drift・要対応N件）をそのまま作業量にせず、放置したとき読者・計測・SEO のどれが実際に壊れるかを実物（curl で 301 と UTM・ライブの 404 等）で確かめる。起点の PR/カードの「なぜ」を読み、主張された効果はデータで裏取り（取れなければ「未検証」）。drift の中身は1つの PR の差分で代表させず、記録時の版と現原稿を実際に比べて変更の種類ごとに数える（`check-note-republish` の 301 等価判定・`note-republish-plan` の分類）。案は「必須（壊れているもの）」と「任意（等価・将来のため）」に分け、任意分は次の改稿時かデータで条件がそろったら実行を既定に。

## 販売実績のある有料記事は「下書きに戻す」不可（2026-06-20）
note は「下書きに戻す」を**有料記事／過去に販売実績がある記事／有料・定期購読マガジンに追加したことがある記事**に許可しない（編集 UI が「この記事は下書きに戻せません」でブロック・2026-06-20 BK-I で実機確認）。公開停止の唯一の手段は不可逆「削除」。
- 販売中有料記事の大改稿差し替えは、編集画面が paste 不可（全面差し替え不可）かつ旧版を綺麗に非公開化もできない二重制約のため、**新規 /new で公開→マガジン入替（新追加＋旧を追加済 toggle で off）→旧版は孤児化（マガジン外で放置）**が現実解。旧版の削除は不可逆＋販売履歴ゆえユーザー確認必須・原則は孤児化。マガジン購入者は新版（マガジン経由）でアクセス継続。手順は update-mode.md「対象の制約」＋ Phase U-B 手段3、handoff `docs/handoffs/2026-06-20-bki-i2-draft-staging.md`。
