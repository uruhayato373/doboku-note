同じ種類のものが**大量に溜まっている**のを見つけたら（重複 pack 993 個、未使用ファイル数百件、古いログ数万行、孤児画像の山）、その量を根拠に掃除を提案しない。**先に「なぜ増え続けているのか」を実体で確認し、生成元を止められるかを判断する。**

大量にある、という事実そのものが「今も作られ続けている」証拠であることが多い。溜まった沈殿物なら掃除で終わるが、継続生成なら掃除しても戻る。この 2 つは見た目の数字が同じなので、量だけでは区別できない。

**Why:** 2026-08-21、DN-0111 Phase 0 で pack 12.01GiB に対しユニーク 6.64GiB・pack エントリ 43 万 vs ユニーク 16 万 を測り、「重複だから repack で 5GiB 回収できる」とユーザーへ提案して承認を得た。結果は (1) `git repack -a -d` が到達可能 commit を 21 個落とし（origin から復旧・[[partial-clone-repack-hazard]]）、(2) その後 git の auto-gc が同じ重複を作り直して 13GiB へ戻った。**993 個という数を見た時点で「何が作っているのか」を問うべきだった。** 問わなかったので、リスクだけ払って成果ゼロになった。CLAUDE.md §8 の「データは『何が』は示すが『なぜ』は示さない。原因は実体で確認する」の、そのままの違反。

**How to apply:**
- 掃除・削除・最適化を提案する前に、**生成元を名指しできるか**を自問する。名指しできないなら「未確認」と書き、提案しない。
- 不可逆・回復困難な操作の承認を求めるときは、リスクだけでなく **「実行後に何をどう検証して成功と判定するか」** を承認前に書く。書けないなら、まだ提案の段階に達していない。
- 外部ドキュメント（man page・公式仕様）の記述を検証の代わりにしない。挙動は手元で確かめる（[[no-overstate-external-specs]] / [[verify-your-excuses]]）。
- 過去に同じ問題をどう解いたかを先に見る。2026-07 は repack ではなく clone 作り直しで解決していた（[[disk-cleanup-textbook-r2-2026-07]]）。採らなかった手段には理由があることが多い。
