**「異常0件」と「検査0件」は出力が同じ緑になり、後者は事故を隠す。** 2026-07-28 に **5 つのスクリプトが同時にこの状態**だった。検査ゲートだけでなく**実行系スクリプト**も同じ形で壊れる。

| スクリプト | 故障 |
|---|---|
| `check-note-structure` | Node `fetch` がプロキシで全滅 → `FETCH_ERR` が `sev:'INFO'` 固定で `critGate` に入らず、`--ci` 無しでは `process.exit()` すら呼ばれない（675/675 失敗でも緑） |
| `check-note-site-utm` | `join()` が返す `\` 区切りを `/\/article\.md$/` で判定 → **Windows の全量実行が常に0件**（`--staged` は git の `/` 出力なので動き、発覚が遅れた） |
| `check-note-republish` / `audit-note-cards` | `name === 'article.md'` 固定で型別 `article-*.md` を走査せず、建設部門の大半が対象外 |
| `check-note-live-headings` | 全件取得失敗でも `bad.length` だけで判定し「✓ 不整合なし」 |
| **`note-sync-tags`（実行系）** | live タグ取得が fetch で全滅 → 全件 `[skip] API 取得失敗` → **「追加すべきタグなし（全て in-sync）」と表示して exit 0**＝同期したつもりで1件も同期していない |

その陰で **有料記事2本が無料プレビュー0字**（購入前に何も読めない）、**送客リンク64件がライブでリンク切れ**、**note ライブのハッシュタグが675本中250本で90未満**（0タグ19本）のまま公開されていた。いずれも「緑だから問題なし」と読める状態が続いていた。

**Why:** ゲートは「異常を検出する」ことは設計するが「自分が機能しているか」は自己申告しない。走査ロジックや取得経路が壊れると、対象0件のまま最も安全に見える出力（緑）を返す。

## 裏返し: 「取得できない」を FAIL と呼ぶと、偽の不足と phantom タスクが生まれる（2026-07-30）

同じ根から**逆向き**の事故が出た。未ログインの note public API はメンバーシップ限定記事に `body='' / hashtag_notes=[] / price=0` を返す（`status` は `published`）。これを素朴に読むと「タグ0」「画像欠落 live=0/sot=2」に見えるが、**著者ログインで実測すると タグ99/98/98・画像2/2 で充足していた**。実害2件:

- `note-sync-tags` が3記事を `[6] FAIL: ライブ件数が増えていない（0→0）` と報告 → 実際は保存成功。この偽 FAIL から「試し読みサブフローでタグ入力が破棄される（2026-07-23 実測）」という誤った結論と allowlist 登録が生まれ、1年近く残りかけた
- 「note ライブ本文の画像欠落3件を修復」という backlog タスク → 実体は充足済みの **phantom タスク**

判別は `scripts/lib/note-live-check.mjs` の `isUnmeasurable()`。該当記事は UNMEASURABLE として**分母から外して別枠表示**する（充足にも不足にも混ぜない）。

**もう一つ**: 事前に作った固定リストの完走を「全量完了」と呼ばない。07-30 のタグ反映は 668件リストを完走したが、リストに無い4本が49〜54タグで残っていた。露出したのは `--list` 無しの全量ゲートだけ。**完了判定は必ず全量ゲートで行う。**

## 3 つめの形: 「構造的に必ず赤いゲート」も同じ害（2026-07-30）

`weekly-review-guard` が 2 週連続 failure。ログは「先週分の review が存在しません → クラウドルーティンの発火状態を確認」。**これを見て「ルーティン停止」と結論したが誤りだった。** 週次レビューには保持方針（最新週だけ残す）があり、W31 を作るコミットが W30 を削除する。guard は「先週分のファイルが今あるか」だけを見ていたため、**サイクルが正常に回っていても翌週分が作られた瞬間に必ず赤くなる**構造だった。実際 W31 は月曜朝に生成済みだった。

害が 2 つ: (1) 常に赤いゲートは読み飛ばされ、本当の欠落を隠す。(2) guard のメッセージが「ルーティンを再作成せよ」と誘導しており、従えば **重複生成事故を再演**する＝偽赤が誤った是正行動を促していた。

**さらに自分の修正でも踏んだ**: 判定を git 履歴（`git log --diff-filter=A`）に変えたら `fetch-depth: 0` が必要になり、65,000 ファイルのリポジトリで checkout が job の 5 分 timeout を超えて **cancelled**。緑にも赤にもならず検査不成立。→ 履歴不要な「現存する最新週が先週以降か」に作り替えた（保持方針下でも最新週は必ず 1 つ残る）。

**How to apply:**
- **同じ赤が 2 回続いたら、まずゲート自身の欠陥を疑う**。外部原因（ルーティン停止・API 障害）と断定する前に、ゲートの判定条件が運用（保持方針・ローテーション・意図的削除）と衝突していないか確認する。
- **「今の状態」で判定するゲートは、成果物が意図的に消される運用と衝突しないか確認する**。消える運用なら「生成された事実」または「最新世代の新しさ」で判定する。
- **ゲートの修正指示に破壊的アクションを書かない**。「再作成せよ」ではなく「まず切り分けよ（誰が生成しているか → list-first → 不在を確認できないなら作らない）」。
- **判定の精度を上げるために CI を重くしない**。監視の checkout/取得コストが job timeout を超えると cancelled になり、緑にも赤にもならない＝何も検査していない。軽い不変条件で同じことが言えないか先に考える。
- `RemoteTrigger list` は cursor を渡しても同じページを返し**全件列挙できない**（2026-07-30 実測）＝不在を証明できないので routine を create しない（CLAUDE.md §8 list-first）。

## 4 つめの形: エージェント自身の手打ち確認でも同じ誤読をする（2026-08-27）

スクリプトに課してきた規律を、**自分の確認作業には当てていなかった**。同一セッションで 2 回踏んだ。

| 叩いたもの | 返り | 誤読 | 実際 |
|---|---|---|---|
| `gh release list \| grep asset-inbox` | 空 | 「release が消えた＝取込成功」と報告 | release は残存・workflow は failure |
| `curl --noproxy '*' https://doboku-note.pages.dev` | `HTTP 000` / `<main` 0 | 「デプロイ失敗・SSR 破壊」と報告しかけた | 200 で正常。`--noproxy` で自分がプロキシを外していた |

R2 でも同型。`rclone lsd obsidian-r2:` の空を「bundle が無い」と読みかけたが、**対照実験**（中身があると分かっている
公開バケットを同じ remote で引く）でも空 → その remote から見えていないだけと判明（endpoint が別アカウント）。

対策として判定をコードへ落とした: `npm run check-production-ssr`（exit 0=正常 / 1=壊れている / **2=検査不成立**）。
deploy skill Step 7.5 はこれを呼ぶだけにし、手打ち curl を禁じた。

**How to apply（自分の確認作業）:**
- 外部コマンドの**空応答は「無い」の証拠にならない**。`grep -c` で件数を出し、0 件なら**対照実験**（存在が分かっている
  ものを同じ経路で引く）を 1 本挟んでから結論する。
- 会社 PC で外部 URL に `--noproxy` を付けない（プロキシを自分で外す＝必ず 000）。localhost だけは逆に必要。
- 接続不能は合格でも不合格でもない**第三の状態**。「デプロイの成否」を報告せず、まず自分の経路を疑う。

## 5 つめの形: 「1回だけ見て断定する」＝待ち不足の偽陰性（2026-09-07）

同じセッションで 3 か所が同型だった。いずれも**否定側（不足・未ログイン）を 1 回の観測で確定**していた。

| 場所 | 単発判定 | 出た嘘 |
|---|---|---|
| `check-note-attachments --live` | goto → 2.5s → scroll → 1.5s → 1回数える。`live < want` をそのまま確定 | 添付があるのに `live=0`＝「購入者が受け取れない」と報告（2日で2件） |
| 同スクリプトの account gate | `assertAccountGate(attempts:1, intervalMs:1500)` | 実際は authenticated なのに **20 分の走査を開始 3 秒で ABORT** |
| `auth:status` | goto → `waitForTimeout(1500)` → 1回分類 | note が `--all` では `unknown`・`--service` では `authenticated`（実測: marker は **4 回目＝約6秒**で出る） |

**Why:** 肯定（充足・authenticated）は 1 回見えれば真だが、**否定は「まだ描画されていない」と区別できない**。
1 回の観測で否定を確定すると、偽陰性が「本物の欠落」として台帳・スナップショット・レポートに残る。

**How to apply:**
- **決着済みの分類は即返し、未決着のときだけ待ち直す**。全件を遅くする必要はない＝コストは否定側にだけ払う
  （`check-note-attachments` は「不足と出た記事だけ」を単独条件で再実測して確定。575本で暫定不足1→再実測で解消1・確定不足0）。
- **出力に「暫定 / 解消 / 確定」を必ず出す**。偽陰性率が毎回見えないと、直ったかどうかも言えない。
- **待ちの既定値を下げる特別扱いをしない**。ライブラリ既定（10回×2秒）より短い値を書くなら理由を残す。
  20 分のジョブを 1.5 秒の判定で落とすのは割に合わない。
- **否定の証拠は肯定の証拠の後ろで見る**。ログアウト検出にパスワード欄を使うのは正しいが、
  account marker 確認より**前**に置くと、認証済みの設定画面（note `/settings/account`＝パスワード変更欄がある）を
  `expired` と誤判定する。同型の順序ミスを踏みかけて回帰（`coconala` が authenticated のまま）で気づいた。
- ログアウト判定を **URL の redirect だけ**に頼らない。実測では
  google=`/search-console/about` へ退避、x=`x.com/` でパスワード欄で、どちらも redirect パターンに当たらず
  `unknown` に埋もれていた（実体はログアウト）。

**How to apply（緑/赤の共通）:**
- **赤を見たとき**: 「そもそも計測できていたか」を確認する。値が 0 なら「無い」か「読めない」かを別経路（著者ログイン等）で1件実測してから作業を起こす。0 を根拠に作業リストを作らない。
- **書くとき**: 検査対象数と実検査数を必ず出力する（「実検査 N本（対象M・取得失敗K）」）／取得失敗が支配的（>20%）なら exit 1＝「検査不成立」／ファイル判定は**パス全体でなくファイル名**で行う（`join()` は Windows で `\`）／note 記事の走査は `/^article(-[^/\\]+)?\.md$/`（型別を落とさない）／外部取得は `fetch` でなく `curl --ssl-no-revoke`（[[feedback_metrics_cicd_supplied]]）。
- **実行系（書き込みスクリプト）にも同じ規律を当てる**: 「対象0件だったので何もしなかった」と「全部失敗したので何もできなかった」を区別して出力する。`skip` を無言で積み上げて最後に「全て in-sync」と言わない。`note-sync-tags` はこれで1件も同期せず緑を返していた。
- **読むとき**: 緑を見たら「何件検査したか」を確認する。0 件や対象数より極端に少ない緑は**故障の可能性が高い**。
- **メタゲート**: `npm run check-gate-coverage` がソース走査型ゲートの検査件数を監視し、急減で落とす（r2-audit.yml 週次）。故障注入で捕捉を実測済み。
- 真実源: `.claude/knowledge/reference/note-api-verification.md`「メタゲート」節、CLAUDE.md §9。
