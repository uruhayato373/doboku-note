# コンテンツ原則

doboku-note のすべてのコンテンツ作成・校正時に従うべき原則。各スキル（keyword-page、review-mobile 等）から参照される。

## ペルソナ

| 項目 | 内容 |
|---|---|
| **属性** | 実務経験10年以上の土木系技術者。一般部門（建設等）は合格済み |
| **知識レベル** | 5つの管理の概念は業務で触れているが、体系的に整理できていない。キーワード集の用語を網羅的には把握していない |
| **学習環境** | 通勤中にスマホで読むことが多い。まとまった勉強時間は週末のみ |
| **ゴール** | 総監部門の合格。「ここだけ読めば試験範囲をカバーできる」サイトを求めている |
| **不安** | 一般部門とは勉強法が違うことは知っているが、何をどう整理すればよいかわからない |
| **行動パターン** | キーワード集の用語を1つずつ確認しながら読む。過去問を解いて不明点をキーワードページで調べる |

## 文体ルール

コンテンツの役割に応じて「である調」と「ですます調」を使い分ける。同一ページ内での混在は禁止。

| 文体 | 対象コンテンツ | 理由 |
|---|---|---|
| **である調** | キーワードページ、教科書、択一式過去問の解説 | 概念の定義・分類・比較を簡潔に伝える技術文書。1文が短くなりモバイルで読みやすい |
| **ですます調** | ガイド記事、受験戦略、2次試験対策、論文添削例 | 読者に語りかけ学習の道筋を示すコーチング的な文書。「〜してください」「〜しましょう」が自然に使える |

迷ったときの判断基準: 「概念を説明する」→ である調、「読者に行動を促す」→ ですます調。

## コンテンツ原則

### 1. 冒頭では概念の本質を簡潔に示す

「〜とは」セクションでは、この概念が**何を扱い、どういう場面で使われるか**を簡潔に説明する。試験での重要性や他の管理分野との関連は「総合技術監理における位置づけ」セクションに集約する。

- 冒頭で書くべきこと: 概念の定義、対象範囲、基本的な仕組み
- 冒頭で書かないこと: 「試験で頻出」「総監技術者として重要」などの試験文脈

### 2. 表・箇条書きの前に文脈を与える

表やリストの直前に、その情報が**何を意味するか**を示す導入文を必ず置く。見出しの直後にいきなり表や箇条書きが来ると、読者は「何のための情報か」を把握できない。

- 悪い例: `### 7大ロス` → （即座に表）
- 良い例: `### 7大ロスとOEEの関係` → 「OEEの3要素はそれぞれ異なるロスの影響を受ける。どのロスがどの要素に影響するかを整理すると、改善すべきポイントが明確になる。」→ （表）

### 3. 1文1段落でモバイル可読性を確保

空行で段落を分け、スマホでの視認性を優先する。連続4行以上の段落は分割する。Markdownの単純な改行は無視されるため、段落を分けるには必ず空行を入れる。

### 4. 表は2軸比較にのみ使う

表は「行と列の両方向に読んで比較する」データにのみ使用する。各行が独立した説明なら箇条書きを使う。

**表が適切な場面**:
- 2軸以上の比較（例: BCP vs 防災計画、MAC vs DAC vs RBAC）
- 短いセルの分類一覧（各セル15文字以内、3列以内）
- マトリクス（SWOT等の2×2グリッド）

**表を使わない場面**:
- キーバリュー表（正式名称・目的・所管等） → 冒頭の散文に統合
- 用語+説明（効果/内容、留意点/内容） → `- **用語**: 説明` の箇条書き
- 計算手順 → 番号付きリスト（1行1ステップ）。KaTeX数式を表セル内に入れない
- 時系列・プロセス → `<Timeline>` コンポーネント
- 4列以上 → 原則禁止。比較として不可欠な場合のみ、各セル15文字以内

**iOSアプリ展開を見据えた判断基準**: 「この情報をSwiftUIのListで表現できるか？」と考える。Listで自然に表示できるなら、表ではなく箇条書きやコンポーネントを使うべき。

### 5. ExamPointは文脈の後に配置

概念の説明が終わった後に配置する。定義セクション（〜とは）の直後に置かない。読者がまだ概念を理解していない段階で試験ポイントを示しても効果がない。

**個数の上限**:
- **原則1個**: 「総合技術監理における位置づけ」セクション末尾の総括ExamPoint 1個が基本パターン
- **最大2個まで**: H3サブセクションが複数あり、各サブテーマごとに独立した試験ポイントがある場合のみ2個まで許容
- **3個以上は禁止**: 内容を統合できないか必ず検討する

**配置の鉄則**:
- 「総合技術監理における位置づけ」セクション末尾に総括ExamPointを必ず1個置く
- フラットなH2のみ構造（H3サブセクションがない構造）では H2 末尾に追加配置しない（ExamPointが本文中に散らばる原因になる）
- 異なるセクションの内容を1つのExamPointに混ぜない

**禁止パターン**（過去問の解説に属する内容をキーワードページに書かない）:
- 「誤り選択肢パターン」「代表的な誤り」「頻出の誤り」など、過去問の選択肢判定に属する内容を ExamPoint の `summary` や `items` に書かない
- これらは過去問MDX（`r*-primary/article.mdx` 等）の `<details>` 解説ブロック内に書く
- キーワードページは概念解説に専念する
- 本文中に「❌」「✅」「正答：N」など過去問の判定記号を書かない（過去問MDXのみ許可）

**ベンチマーク**: BCP（事業継続計画）ページは ExamPoint 2個（H3末尾＋総括）の構成。これを上限の参考とする。

### 6. 試験での位置づけを明示

「総合技術監理における位置づけ」セクションで、この概念がキーワード集のどの章・節にあるかを示す。複数セクションに関わる場合はその横断性を説明する。

- 例: 「BCPは経済性管理（2.1 事業企画）と安全管理（5.5 危機管理）の両方に位置づけられる。試験では両方の文脈から出題される可能性がある。」

### 7. 過剰装飾を避ける

- 絵文字（❌✅💡🔑📌⚠️等）を使わない
- Calloutは1記事に3個以内。警告・注意点がある場合のみ使用する
- 太字は1段落に1〜2箇所。すべてを太字にすると何も目立たない
- **太字スコープは 30 字以下に絞る** ── 特に「○○とは…である」概念定義文では、長文全体ではなく **核心キーワードのみを太字にする**

#### 太字スコープの正例・反例

**反例（NG）**:

> インフラ老朽化対策とは、**高度経済成長期に集中整備された社会インフラが一斉に更新時期を迎える問題に対し、計画的な維持管理・更新で機能と安全を確保する取組** である。

59 字の長大な太字。読者の視線がどこに向かうべきかわからず、強調が機能しない。

**正例（OK）**:

> インフラ老朽化対策とは、高度経済成長期に集中整備された社会インフラが一斉に更新時期を迎える問題に対し、**計画的な維持管理・更新** で機能と安全を確保する取組である。

12 字の核心キーワードに絞った太字。方法論の中核（事後保全との対比軸）が即座に伝わる。

**正例（2文分割パターン）**:

> 4E対策とは、労働災害の防止対策を **4 つの観点（4E）** から体系的に実施する考え方である。4E は Education（教育）・Engineering（技術）・Enforcement（徹底）・Example（模範）の 4 要素を指す。

定義文と要素列挙を 2 文に分け、太字を「4 つの観点（4E）」だけに絞る。

#### 執筆時の自己チェック

「○○とは…である」を書き終えたら、**太字部分の文字数を即座に数える**。30 字を超えていたら必ず縮める。`/review-mobile` スキルが機械的にも検出する（カテゴリ 7-1）。

太字に絞る対象の優先順:

1. **方法論的中核**（例: 「**計画的な維持管理・更新**」「**4 つの観点（4E）**」）
2. **唯一識別する固有名詞**（その概念を他から区別する用語）
3. **キー数値・略語**（例: 「**RTO**」「**95% 以上**」）

これらに該当しない長い説明部分は太字にしない。

### 8. リンクの使い分け

文中で関連キーワードに言及する場合と、セクション末尾で一覧表示する場合で、リンク方法を使い分ける。

- **文中のインラインリンク** → Markdownリンク `[キーワード名](/docs/pe-comprehensive-management-{slug})`
- **セクション末尾の関連キーワード一覧** → `<RelatedKeywords>` コンポーネント（ブロック配置）

`<RelatedKeywords>` はブロックレベルUI（ボーダー付きdiv）であり、文中にインラインで使うと視覚的に不自然になる。また、MDXプリプロセッサとの相性問題でコンパイルエラーが発生する場合がある。

### 9. 参考資料の構成

`## 参考資料` セクションは公的資料と民間解説記事の両方を含めること。公的資料は正確性、民間記事はわかりやすさの観点で相互補完となる。

**最低構成**:
- **公的資料 最低1件**: 官公庁（go.jp）・公的機関（or.jp）・大学（ac.jp）の解説ページ
- **民間解説記事 最低1件**: Wikipedia、技術ブログ、note記事、弁護士事務所等の解説、業界団体の啓発ページなど

**記載ルール**:
- 形式: `- [資料タイトル](URL)（出典元）`
- URL は **WebSearch で候補発見 → WebFetch で実在確認 → 記載** の順序で必ず検証する。推測や記憶からの URL 記載は禁止
- 試験の公式ページ（キーワード集ダウンロードページ等）は学習リソースではないため不適切
- 組織のトップページではなく、当該キーワードを直接解説しているコンテンツへのリンクを優先する
- 同一組織の異なるURLでも内容が同じなら1件に絞る（重複排除）
- 存在確認できなかったURL・内容がキーワードと無関係なURLは記載しない（出典名だけテキストで残すのも不可）
- **書籍（著者名＋書名＋出版社）は記載しない** — 参考資料は読者がワンクリックでアクセスできる Web リソースに限定する。書籍の内容が重要な場合は、同等の内容を扱う公的ページまたは民間解説記事を探して記載する

**法令条文へのリンク**:
- 本文中で法律の条文に言及する場合、e-Gov法令検索の該当条文へのアンカーリンクを付与する
- URL形式: `https://laws.e-gov.go.jp/law/{法令番号}#Mp-At_{条番号}`
- MDX では `**[text](url)**` が正しくパースされないため、太字はリンクテキストの内側に置く: `[**法律名第◯条**](url)`

## コンテンツ品質レベル（L1 / L2 / L3）

コンテンツの品質を3層に分け、対象ごとに到達すべきレベルを明確にする。すべてのコンテンツにL3を求めない。

### L1: 構造品質（全コンテンツで必須）

原文に忠実な情報が、正しいフォーマットで格納されていること。

- frontmatter（title, seoTitle, description, category, tags, published）が正確
- 文字化け（U+FFFD）がない
- MDX構文エラーがない
- 設問番号・選択肢が原文に忠実
- コンポーネント（Callout, ExamPoint等）が正しく使われている

**L1を満たさないコンテンツはpublished: falseにする。**

### L2: 学習品質（主要コンテンツで実現）

読者が「読んで理解し、試験対策に使える」状態。

- 正答・解説が付いている（過去問）
- ExamPointで試験頻出ポイントが明示されている
- RelatedKeywordsで関連ページへの双方向リンクがある
- モバイルでの視認性が確保されている（表の適切性、段落分割）
- 本ファイルのコンテンツ原則1〜8に準拠している

### L3: 体験品質（特定コンテンツに集中）

「ここだけで合格できる」と感じさせる体験。

- 図版・数式が原文と同等に再現されている
- 分野横断の出題傾向分析がある
- 学習の導線が設計されている（次に読むべきページが明確）
- ベンチマークページ（BCP）と同等以上の品質

### 現在の配分方針

| コンテンツ | 到達目標 |
|---|---|
| 過去問（最新5年: R03〜R07） | L2 |
| 過去問（H21〜R02） | L1 → 順次L2へ |
| キーワードページ（頻出） | L2 |
| キーワードページ（その他） | L1 |
| ガイド記事 | L3 |

### Wave方式

コンテンツは1記事ずつ完璧に仕上げるのではなく、全体を波のようになぞる。

1. **第一波（L1）**: 全記事の構造を作る。問題文のみ、キーワードは定義のみ
2. **第二波（L2）**: 主要記事に解説・リンク・ExamPointを追加
3. **第三波（L3）**: ガイド記事・最重要キーワードに体験品質を入れる
