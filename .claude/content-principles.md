# コンテンツ原則

doboku-note のすべてのコンテンツ作成・校正時に従うべき原則。各スキル（keyword-page、review-mobile 等）から参照される。

## ペルソナ

| 項目 | 内容 |
|---|---|
| **属性** | 実務経験10年以上の土木系技術者。一般部門（建設等）は合格済み |
| **知識レベル** | 5つの管理の概念は業務で触れているが、体系的に整理できていない。キーワード集の用語を網羅的には把握していない |
| **学習環境** | 通勤中にスマホで読むことが多い。まとまった勉強時間は週末のみ |
| **ゴール** | 総監部門の合格。「ここだけ読めば試験範囲をカバーできる」サイトを求めている |
| **不安** | 一般部門とは勉強法が違うことは知っているが、何をどう整理すればよいかわからない |
| **行動パターン** | キーワード集の用語を1つずつ確認しながら読む。過去問を解いて不明点をキーワードページで調べる |

## コンテンツ原則

### 1. 冒頭では概念の本質を簡潔に示す

「〜とは」セクションでは、この概念が**何を扱い、どういう場面で使われるか**を簡潔に説明する。試験での重要性や他の管理分野との関連は「総合技術監理における位置づけ」セクションに集約する。

- 冒頭で書くべきこと: 概念の定義、対象範囲、基本的な仕組み
- 冒頭で書かないこと: 「試験で頻出」「総監技術者として重要」などの試験文脈

### 2. 表・箇条書きの前に文脈を与える

表やリストの直前に、その情報が**何を意味するか**を示す導入文を必ず置く。見出しの直後にいきなり表や箇条書きが来ると、読者は「何のための情報か」を把握できない。

- 悪い例: `### 7大ロス` → （即座に表）
- 良い例: `### 7大ロスとOEEの関係` → 「OEEの3要素はそれぞれ異なるロスの影響を受ける。どのロスがどの要素に影響するかを整理すると、改善すべきポイントが明確になる。」→ （表）

### 3. 1文1段落でモバイル可読性を確保

空行で段落を分け、スマホでの視認性を優先する。連続4行以上の段落は分割する。Markdownの単純な改行は無視されるため、段落を分けるには必ず空行を入れる。

### 4. 表は2軸比較にのみ使う

表は「行と列の両方向に読んで比較する」データにのみ使用する。各行が独立した説明なら箇条書きを使う。

**表が適切な場面**:
- 2軸以上の比較（例: BCP vs 防災計画、MAC vs DAC vs RBAC）
- 短いセルの分類一覧（各セル15文字以内、3列以内）
- マトリクス（SWOT等の2×2グリッド）

**表を使わない場面**:
- キーバリュー表（正式名称・目的・所管等） → 冒頭の散文に統合
- 用語+説明（効果/内容、留意点/内容） → `- **用語**: 説明` の箇条書き
- 計算手順 → 番号付きリスト（1行1ステップ）。KaTeX数式を表セル内に入れない
- 時系列・プロセス → `<Timeline>` コンポーネント
- 4列以上 → 原則禁止。比較として不可欠な場合のみ、各セル15文字以内

**iOSアプリ展開を見据えた判断基準**: 「この情報をSwiftUIのListで表現できるか？」と考える。Listで自然に表示できるなら、表ではなく箇条書きやコンポーネントを使うべき。

### 5. ExamPointは文脈の後に配置

概念の説明が終わった後に配置する。定義セクション（〜とは）の直後に置かない。読者がまだ概念を理解していない段階で試験ポイントを示しても効果がない。

- 1記事に1〜3個
- 異なるセクションの内容を1つのExamPointに混ぜない
- 記事全体の総括として「総合技術監理における位置づけ」セクションの末尾に置くのが最も自然

### 6. 試験での位置づけを明示

「総合技術監理における位置づけ」セクションで、この概念がキーワード集のどの章・節にあるかを示す。複数セクションに関わる場合はその横断性を説明する。

- 例: 「BCPは経済性管理（2.1 事業企画）と安全管理（5.5 危機管理）の両方に位置づけられる。試験では両方の文脈から出題される可能性がある。」

### 7. 過剰装飾を避ける

- 絵文字（❌✅💡🔑📌⚠️等）を使わない
- Calloutは1記事に3個以内。警告・注意点がある場合のみ使用する
- 太字は1段落に1〜2箇所。すべてを太字にすると何も目立たない

### 8. リンクの使い分け

文中で関連キーワードに言及する場合と、セクション末尾で一覧表示する場合で、リンク方法を使い分ける。

- **文中のインラインリンク** → Markdownリンク `[キーワード名](/docs/pe-comprehensive-management-{slug})`
- **セクション末尾の関連キーワード一覧** → `<RelatedKeywords>` コンポーネント（ブロック配置）

`<RelatedKeywords>` はブロックレベルUI（ボーダー付きdiv）であり、文中にインラインで使うと視覚的に不自然になる。また、MDXプリプロセッサとの相性問題でコンパイルエラーが発生する場合がある。

## コンテンツ品質レベル（L1 / L2 / L3）

コンテンツの品質を3層に分け、対象ごとに到達すべきレベルを明確にする。すべてのコンテンツにL3を求めない。

### L1: 構造品質（全コンテンツで必須）

原文に忠実な情報が、正しいフォーマットで格納されていること。

- frontmatter（title, description, category, tags, published）が正確
- 文字化け（U+FFFD）がない
- MDX構文エラーがない
- 設問番号・選択肢が原文に忠実
- コンポーネント（Callout, ExamPoint等）が正しく使われている

**L1を満たさないコンテンツはpublished: falseにする。**

### L2: 学習品質（主要コンテンツで実現）

読者が「読んで理解し、試験対策に使える」状態。

- 正答・解説が付いている（過去問）
- ExamPointで試験頻出ポイントが明示されている
- RelatedKeywordsで関連ページへの双方向リンクがある
- モバイルでの視認性が確保されている（表の適切性、段落分割）
- 本ファイルのコンテンツ原則1〜8に準拠している

### L3: 体験品質（特定コンテンツに集中）

「ここだけで合格できる」と感じさせる体験。

- 図版・数式が原文と同等に再現されている
- 分野横断の出題傾向分析がある
- 学習の導線が設計されている（次に読むべきページが明確）
- ベンチマークページ（BCP）と同等以上の品質

### 現在の配分方針

| コンテンツ | 到達目標 |
|---|---|
| 過去問（最新5年: R03〜R07） | L2 |
| 過去問（H21〜R02） | L1 → 順次L2へ |
| キーワードページ（頻出） | L2 |
| キーワードページ（その他） | L1 |
| ガイド記事 | L3 |

### Wave方式

コンテンツは1記事ずつ完璧に仕上げるのではなく、全体を波のようになぞる。

1. **第一波（L1）**: 全記事の構造を作る。問題文のみ、キーワードは定義のみ
2. **第二波（L2）**: 主要記事に解説・リンク・ExamPointを追加
3. **第三波（L3）**: ガイド記事・最重要キーワードに体験品質を入れる
