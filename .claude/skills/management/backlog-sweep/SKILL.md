backlog の「実行」と「削除」を回す。タスクの選定は**スクリプトが決める**（CLAUDE.md §5・モデルに委ねない）。

## 使い方

```
/backlog-sweep              # 1サイクル（実行候補2件 + 分類2件）
/backlog-sweep --limit 1    # 1件だけ
/loop /backlog-sweep        # 自走
/backlog-sweep --audit      # 台帳の棚卸し（月初 or 機械しきい値超過時）
```

## --audit モード（台帳の棚卸し）

通常サイクルが**カード 1〜2 枚**を出口まで運ぶのに対し、`--audit` は**台帳コーパス全体**を見る。sweep が選定できるのは `sweep`/`機械` のカードだけで、実測では **98 枚中 49 枚が選定対象外**＝`/loop` を何周しても一度も実査されない。そこを埋めるのがこのモード。

**`/loop` はこのモードを選ばない**（月次の監査を毎周回すため）。

### 起動条件

**判定は機械が持つ**（散文のままでは誰も判定せず、人が覚えている間しか回らない）。
`scripts/check-backlog-health.mjs` の `DUE_RULES` が唯一の実装で、SessionStart フックが
`--due` で毎セッション評価し、**踏んだときだけ**セッション開幕に 1 ブロック出す。

```bash
npm run check-backlog-due   # 期限なら理由を表示・でなければ無音（常に exit 0）
```

条件（`DUE_RULES` と同じ・変えるときは両方同時に直す）:

- 🟢🟣 に沈んだ不具合 ≥ 1（S2）／`種類:定期` ≥ 1（S4＝置き場違い）
- `[起票:]` 90 日超 ≥ 15（S5）／語彙外カテゴリ ≥ 10（S6）
- 重複候補ペア ≥ 3（S8）／`.claude/todo` の 4 層以外が増えた（S9）
- **ID の再利用 ≥ 1（S10）** — 完了カードは削除するので `DN-####` は歯抜けになる。そこへ
  新しいカードが空き番を拾うと、**過去のコミットメッセージ・plan・レビューが指す ID が別物**に
  なる（2026-08-20 に DN-0096 / DN-0097 で実発生・同日 2 件）。1 件でも起きたら監査対象
- 月初（7 日まで）で、その月にまだ棚卸しを記録していない

> [!note] S5 は現状ほぼ機能しない（2026-08-18）
> `[起票:]` を持つカードが 98 枚中 24 枚しかなく、**残り 74 枚は古さを測れない**。
> 鮮度による陳腐化検出を効かせるには起票日の backfill（git log の初出コミット日から導出）が要る。

### 手順

1. `node scripts/check-backlog-health.mjs --json` で候補シグナルを取る
2. **親が実体を検証する**: 対象カードの `[検証:cmd]` を実走し、`git log --oneline -30` と関連 SSOT の現物値を集める（エージェントには推測でコマンドを叩かせない）
3. tier セクションをシャードにして `backlog-curator` を**同時 3 体まで**起動（🔴 / 🟡 / 🟢+🟣）。1 体あたり 25〜35 枚
4. 返ってきた verdict（KEEP / RETAG / TRIM / MERGE / DELETE）を**親が裁定して適用**する。エージェントは backlog.md を編集しない
5. 適用後に `check-backlog-schema` と `check-backlog-health` を回して S2/S3/S4/S6/S9 が 0 に戻ったか確認
6. **実施を記録する**: `node scripts/check-backlog-health.mjs --record-audit`
   （`.claude/state/backlog/audit-log.json`。月初条件はこの記録を見るので、書かないと翌セッションから催促が続く。**回していないのに記録しない**）

### 退役条件

3 回連続の監査で、機械シグナルを除いた**純粋な意味判断が 10 件未満**だったら `backlog-curator` を退役させ、親のインライン判定に戻す（読み手のいない仕組みを残さない）。

## 1サイクルの手順

### 1. 選定

```bash
node scripts/backlog-sweep-pick.mjs --json
```

`run[]`（実行候補）と `classify[]`（token が欠けている＝分類待ち）が返る。**`run` が空でも `unclassifiedTotal > 0` なら「タスクが無い」ではなく「分類していないから選べない」**。その場合は手順5の分類だけ行う。

**`run[]` の順序は「`[種類:不具合]` が第1キー・tier が第2キー」**（2026-08-18〜）。tier がもはや不具合の緊急度を表しておらず、不具合が 🟢（時期未定）に沈んでいたため、壊れているものを先に出す。`sunkDefects[]` に 🟢/🟣 の不具合が入るので、選定時に目に入る。

`kind` は `run[]`/`classify[]` の各要素に入る。**手順2の実査は種類で内容が変わる**（不具合は再現確認、制作は不要）。

### 2. 実査ファースト（最重要）

**実行に入る前に、そのタスクがまだ生きているかを現物で確かめる**。backlog の記述は陳腐化する（2026-08-17 の実測で1日に6件が「実査したら既に完了」だった）。

- 記述が指すファイル・設定・公開状態を Read / curl / スクリプトで確認する
- **既に達成されていたら、実行せずセクションを削除して commit**（`outcome: swept`）。これも成果として数える
- 記述と実態が食い違うが未完なら、記述を実態に合わせてから実行する

CLAUDE.md §8「提案・推奨の前に現物を確認する（憶測で gap を断定しない）」がここに効く。

#### バルク編集の前に 3 件サンプル確認（2026-08-18 新設）

**「N 件に X を追加/修正せよ」型のカードは、着手前に対象から 3 件を選んで一次資料で主張を確認する。**
カードの記述でも検査の出力でもなく、**現物**（記事本文・設定ファイル・ライブの状態）を見る。
矛盾したら実行せず、カードを是正して終わる（`outcome: swept`）。

同日にこれで 2 件止まった。どちらも指示どおり実装していれば**状況を悪化させていた**:

- **総監模範論文 77 本に「印刷用PDF」節を追加** — 3 本開いたら全部に既に案内があった。
  `check-note-attachments` の正規表現が「印刷用 PDF」（半角スペース入り＝日本語と欧文の間を空ける
  組版慣習）を拾えていないだけの偽陽性。実行していれば**案内が重複した記事を 77 本**作っていた
- **内部メモ除去を IG パックへ横展開** — IG の SoT を開いたら JSON で、HTML コメントの慣習が
  存在しなかった（0 件）。監査が X から一般化した誤り。真の穴は X ツールチェーン内の別の場所にあった

> [!important] `[検証:cmd]` はこの確認の代わりにならない
> カードが持つ検証コマンドは**誤りの発生源と同じ検査を指すことがある**。総監のカードは
> `[検証:check-note-attachments]` を持っていたが、それを流しても偽陽性が追認されるだけだった。
> **カードと検証が同じ誤りを指すと自己整合する**ので、一次資料に当たる以外に検出手段がない。

確認した 3 件は「何をどう見たか」を実行報告に書く（後から再現できる形で）。

### 3. 実行

タスク記載の手順に従う。**sweep は新しい権限を持たない** — 外向き操作（note 公開・ライブ反映・ココナラ出品・X 予約）は既存スキル/スクリプトの `dry-run → 検証 → --commit` ゲートをそのまま使い、通れば完了まで進めてよい（2026-08-17 ユーザー確定）。

例外: X の予約投入は `x-post-policy.md` §11.6（1週間分ずつ・一括禁止）が上位。凍結の兆候が1度でも出たら即停止。

### 4. 検証

`タグ:` に `[検証:cmd]` があればそれを実行。無ければタスク本文の完了条件を決定的ゲートとして通す（`curl` で `<main`、`npm run check-*`、テスト等）。**汎用の「ダブルチェック」は足さない**（§9）。

### 5. 分類（`classify[]` の消化）

`classify[]` の `missing` が欠けている token を示す（`実行` / `種類`）。実査ベースで付ける。**推測で付けない** — 判断できなければ飛ばす。

**`[種類:X]`** — 上から順に、最初に当たったものを採る（真実源は backlog.md の凡例）:

| token | 意味 |
|---|---|
| `[種類:定期]` | 期日で反復発火する。**これが付いたら backlog に置くべきでない合図**（monthly/weekly か `check-*-due` へ移す） |
| `[種類:意思決定]` | 成果物が「決めたこと」そのもの。決まるまで着手できない。**このとき tier は 🟣** |
| `[種類:不具合]` | 約束・仕様に対して現状が壊れている／欠けている |
| `[種類:制作]` | 新しい成果物（記事・図・書籍・投稿・商品）が増える |
| `[種類:改善]` | 上のどれでもない（動いているものをより良くする） |

**新規カードを起票するとき**は見出しを `### [DN-####] タイトル` にする（ID は必須・欠番は再利用しない）。
`[種類:]` `[実行:]` `[起票:]` も同時に付ける（`check-backlog-schema --staged` が欠落を止める）。

**`[実行:X]`**:

| token | 意味 |
|---|---|
| `[実行:sweep]` | AI が単独で完了まで持っていける |
| `[実行:機械]` | スクリプト実行だけで終わる |
| `[実行:対話]` | ユーザーと詰める判断が要る |
| `[実行:ユーザー]` | ユーザーの手作業（パスワード・KDP・実測など） |
| `[実行:windows]` / `[実行:別環境]` | この Mac では実行できない |

余力があれば `[検証:cmd]`・`[起票:YYYY-MM-DD]` も併せて付ける。

### 6. 記録

- 完了/掃除したタスクは**セクションごと削除**して即 commit（backlog.md:5 の規約）
- `.claude/state/dispatch/dispatch-log.json` の `entries` へ1行追記（スキーマは同ファイルの `_schema`）。`outcome` は `done` / `swept` / `blocked` / `fail`

### 7. 出口ゲート（再発防止の3問）

完了したタスクごとに答える。答えが「いいえ」なら**その場で直すか、検出器タスクを backlog へ起票する**。

1. 同種の欠陥を機械で検出できるか
2. その検出器は**誰がいつ読むか**（読み手がいないなら `ci:true` にするか、作らない）
3. 台帳・SSOT の更新は同一 commit に入っているか

### 8. 報告

```
消化 N / 掃除 M / 分類 K / スキップ L（理由）/ 選定可能残り R
```

**「消化 0」と「選べるタスクが 0」を必ず区別して書く**（§9）。

## 注意

- 🟣 判断待ちは自動選定しない。ユーザーの意思決定が要るため
- 1サイクルは小さく保つ。長引くなら分割して次サイクルへ回す（中断安全性がループの前提）
- `[Codex候補]` は「バルク向き」の印であって自動ディスパッチ配線ではない
