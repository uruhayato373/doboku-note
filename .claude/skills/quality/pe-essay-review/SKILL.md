# /pe-essay-review — 総監記述式 模範論文レビュー

総監記述式の **模範論文ページ**（`pattern-essay-*` ハブまたは `r0X-essay-*` 各年度ページ）を、3 つの専門家ペルソナで評価する Evaluator スキル。Generator（私自身が前回作成した模範論文）と Evaluator を分離する CLAUDE.md ハーネス原則に従う。

## 引数

```
/pe-essay-review {target} [--mode shallow|deep]
```

| 引数 | 説明 |
|---|---|
| `{target}` | 対象ファイルの slug（例: `r05-essay-general-contractor`）または属性（例: `general-contractor` で全年度） |
| `--mode shallow` | 視点ごとに概観評価のみ（高速） |
| `--mode deep` | 視点ごとに具体的な引用と改善案を出す（低速・詳細） |

デフォルトは `--mode deep`。

## 3 つのレビュー視点

### 視点 1: 採点者（A評価合格者）

**ペルソナ**: 技術士総合技術監理部門に合格し、複数年度の答案添削経験がある合格者。試験委員会が公表する評価項目（**視点の広さ・記述の明確さ・論理的なつながり・論文全体のまとまり**）を採点軸として用いる。

**プロンプト**:
> あなたは技術士総合技術監理部門の合格者で、後輩の論文添削を多数経験している。以下の模範論文を試験委員会の評価項目で 1〜10 点評価し、A 評価（60% 以上）を取れる答案として通用するか判断せよ。
>
> 評価項目:
> - 視点の広さ（5管理を俯瞰し、トレードオフを意識して論じているか）
> - 記述の明確さ（用語定義・問題文との対応が明示されているか）
> - 論理的なつながり（三層構造の各段階が前段の伏線を回収しているか）
> - 論文全体のまとまり（属性・規模・前提条件が一貫しているか）
>
> 各項目を 1〜10 点 + 理由 + 「実際の試験で減点される表現」の指摘 + 改善提案を出せ。

### 視点 2: 現役総監技術士 OB（業界実務者）

**ペルソナ**: 当該属性（道路発注者・ゼネコン・コンサル河川など）で 20 年以上の実務経験がある現役の技術士総合技術監理部門。事実誤認・固有用語の正確性・規模感・組織体制のリアルさを判断する。

**プロンプト**:
> あなたは「{属性}」業界で 20 年以上の実務経験を持つ現役技術士総合技術監理部門。後輩から論文添削を頼まれた立場で、以下を 1〜10 点評価せよ。
>
> 評価項目:
> - ペルソナの妥当性（事業名・規模・組織体制・予算規模・主要顧客の設定が業界実態と整合）
> - 固有用語の正確性（i-Construction 2.0・CCUS・ConCAS・流域治水交付金・ブルーカーボン等の制度・規格・数値が事実か）
> - 業務プロセスのリアルさ（受注 → 設計 → 施工 → 引渡の流れが現実的か）
> - 数値の妥当性（投資額・人員数・売上規模・ROI 期間が実態と整合）
>
> 各項目を 1〜10 点 + 理由 + **「業界の人が読んで違和感を覚える具体箇所」を引用付きで指摘** + 修正案を出せ。

### 視点 3: 受験予備校講師（試験戦略）

**ペルソナ**: 総監記述式対策の予備校講師または対策本著者。多数の受験者の答案を採点した経験から、A 評価筋に乗る論文の戦略パターンを熟知している。

**プロンプト**:
> あなたは総監記述式対策の予備校講師。多数の答案を採点した経験から、A 評価筋に乗る戦略パターンを熟知している。以下の模範論文を 1〜10 点評価せよ。
>
> 評価項目:
> - 三層構造の組み立て（現在 → 5 年以内 → 我が国施策、または現在 → 近未来 → 5〜10 年後の流れが綺麗か）
> - トレードオフの選び方（A 評価筋の組み合わせか、無難すぎないか、深さは十分か）
> - 設問読解の精度（Phase 1 で抽出した設問チェックリストを根拠に、①必須記述項目の取りこぼし ②枚数・構成の指示違反 ③設問固有制約の無視 を原文引用付きで指摘する。推測禁止・設問原文が根拠）
> - 「テンプレ丸暗記」と判定される表面的要素の有無（具体性に欠ける汎用語、似た言い回しの繰り返し、トレードオフフレームの使い回し）
>
> 各項目を 1〜10 点 + 理由 + **「試験本番で減点される試験戦略上の問題」を具体的に指摘** + 修正案を出せ。

## 実行フロー

```
/pe-essay-review {target}
  │
  ├─ Phase 1: ファイル特定と読み込み
  │   ├ slug 解決: r05-essay-general-contractor → .local/r2/posts/.../article.mdx
  │   ├ 模範論文ファイル read（最大 1000 行）
  │   ├ inline チェック（U+FFFD 文字化け、frontmatter 必須項目）
  │   └ 【設問突合】年度を slug から抽出（r05 → r05-secondary）し
  │       .local/r2/posts/pe-comprehensive-management/r0X-secondary/article.mdx を read。
  │       設問構造（問い(1)〜(3) の枚数指定・要求項目・5管理明記要否）を抽出し
  │       "設問チェックリスト" として保持する。
  │       pattern-essay-* ハブの場合は設問突合をスキップ。
  │
  ├─ Phase 2: 3 視点で順次評価
  │   ├ 視点 1（採点者）: 4 項目を 1〜10 点評価 + 引用付き指摘 + 改善案
  │   ├ 視点 2（OB）: 4 項目を 1〜10 点評価 + 引用付き指摘 + 修正案
  │   └ 視点 3（講師）: 4 項目を 1〜10 点評価 + 具体指摘 + 修正案
  │       ※「設問読解の精度」は Phase 1 で保持した設問チェックリストと
  │         模範論文を突合して採点する（推測禁止・設問原文を根拠に引用）
  │
  └─ Phase 3: 集約・致命的問題のフラグ・優先度付き提案
      ├ 平均スコア（視点 × 項目）
      ├ 設問取りこぼし一覧（設問チェックリストの未対応項目）
      ├ 致命的問題（事実誤認・採点筋外し・テンプレ判定・設問無視）
      ├ 修正優先度: High（採点に直接影響）/ Med（事実精度）/ Low（表現改善）
      └ レポート保存: .claude/state/pe-essay-review/{slug}-{timestamp}.md
```

## 設問チェックリストの作り方（Phase 1 詳細）

`r0X-secondary/article.mdx` から以下を抽出して箇条書きにまとめる:

- 各問い（(1)(2)(3)）の **枚数制限**（例: 答案用紙2枚以内）
- 各問いで **必須の記述項目**（例: ①〜④ の箇条書き、5管理2つ以上明記）
- **設問固有の制約**（例: 「データ利用可能性に関するリスクは対象外」「DX と デジタル技術の利用を区別せよ」）
- **評価基準**（前文で明示されているもの: 視点の広さ・記述の明確さ・論理的なつながり・まとまり）

この設問チェックリストを視点 3（講師）の「設問読解の精度」評価に直接使用する。

## 合格基準（参考）

- **総合 8.0+**: 公開水準（実際の試験で A 評価筋）
- **総合 6.5〜8.0**: 改善余地あり（修正で公開水準に届く）
- **総合 6.5 未満**: 大規模修正が必要

## 制約

- 1 回の実行で 1 ファイル評価が原則（複数指定時は逐次実行）
- スキル単体で完結（エージェント呼び出しなし、シンプル設計）
- 出力は `.claude/state/pe-essay-review/` に保存（CLAUDE.md「機械可読データ」の Tier 3 ではなく Markdown レポート）

## 関連スキル

- `pe-essay-cycle`: 総監記述式の統括オーケストレーター（本スキルを `--mode review` で呼ぶ）
- `pe-essay-draft`: 対になる Generator スキル（本スキルの添削レポートを `--mode revise` で反映する）
- `note-prepublish-review`: note 公開前レビュー（多軸統合）
- `cem-qa`（エージェント）: キーワードページの 5 軸ルーブリック評価
