# Phase 2：原稿制作とQA

## 1. 制作単位

1商品を最小完結単位にする。`dossier確定 → 原稿生成 → 機械検査 → semantic QA → 修正 → 再QA → 公開準備`を終えてから次の商品へ進む。複数商品の初稿生成は可能だが、QA未完了の山を作らない。

原稿の年度構成と記事本数は、実装時点の既存14商品と現行試験年度を棚卸しして固定する。終了済みのR8予想を新規36商品へそのまま複製しない。

## 2. 制作バッチ

売上は存在判定ではなく公開順に使う。市場母数、既存販売との近さ、技術的検証のしやすさで4段階にする。

### Batch A：最大需要・既存商品に近い8件

- コンサル：鋼構造及びコンクリート、土質及び基礎、地質、トンネル
- 施工会社：道路・舗装、橋梁・鋼構造・コンクリート、トンネル・地下、維持修繕・更新

### Batch B：主要インフラ11件

- コンサル：港湾及び空港、鉄道、上水道及び工業用水道、下水道、建設環境
- 施工会社：河川・砂防・ダム、港湾・海洋、鉄道、上下水道、基礎・地盤改良、都市開発・造成

### Batch C：長尾・地域インフラ13件

- コンサル：農業土木、森林土木、水産土木、廃棄物、造園、施工計画・施工設備・積算
- 施工会社：環境・廃棄物施設、本社施工計画・積算・DX、農業土木、森林土木・斜面、水産土木・漁港、造園・公園、電力・エネルギー土木

### Batch D：専門QA負荷が高い4件

- コンサル：電力土木、機械、電気電子
- 施工会社：機械・電気設備と土木の統括

Batch Dは対象分野の一次資料と専門レビュー観点が不足する場合、公開せずdraftで止める。ロスターからは削除しない。

## 3. 生成契約

既存の`cem-essay-writer`を使用し、各記事へdossierを明示的に渡す。生成時の共通条件:

- 当該ペルソナの権限内で意思決定する。
- A/Bの2業務類型を年度ごとに使い分け、全年度を同じ事例で押し切らない。
- 5管理の正式名を使い、主軸以外の管理も必要に応じて統合する。
- 施策ごとの字数上限、散文性、設問3の国家スケール等は現行の総監論文ルールに従う。
- 「私はこの会社で経験した」等の架空の経歴を付けない。
- 一次資料で確認できない数値・制度・基準名を発明しない。
- 既存14商品、同batchの兄弟商品、同年度の記事を素材として逐語転用しない。

## 4. QA契約

生成者とは別の`cem-essay-qa`で全記事を評価する。既存の必須ゲートに次を追加する。

### 機械ゲート

- 文字数・見出し構造・note lint。
- frontmatter、価格直書き、リンク、画像、PDF配布物の構造。
- productId、ペルソナID、年度、記事数のレジストリ整合。
- 兄弟商品とのn-gram／類似度サーフェス。閾値超過は自動不合格ではなくsemantic QAへ渡す。

### semanticゲート

- 権限逸脱がない。
- 2つの業務類型が当該分野に固有である。
- 主要ステークホルダーと5管理の対立が、最近傍ペルソナと区別できる。
- 名詞置換ではなく、問題認識・選択肢・トレードオフ・残余リスクが変わっている。
- 専門技術、制度、法令、数値が一次資料と一致する。
- 著者の真正経験と想定ペルソナの境界が読者に誤認されない。

平均点だけで重大違反を薄めない。越権、捏造、一次資料不一致、逐語重複は1件でも公開ブロックとする。

## 5. 商品ごとの完了証拠

各商品に次を残す。

```text
persona id / productId
dossier path
article paths and count
mechanical gate result
semantic QA result
fact-check sources
sibling-difference summary
ready / blocked
```

実行ログの恒久保存先はDN-0093で確定する共通ライフサイクルを使う。確定前は本計画へ長いログを追記せず、作業セッションのGit差分とQA生成物を証拠にする。
