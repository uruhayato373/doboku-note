# コンテンツ原則

doboku-note のすべてのコンテンツ作成・校正時に従うべき原則。各スキル（keyword-page、review-mobile 等）から参照される。

## ペルソナ

| 項目 | 内容 |
|---|---|
| **属性** | 実務経験10年以上の土木系技術者。一般部門（建設等）は合格済み |
| **知識レベル** | 5つの管理の概念は業務で触れているが、体系的に整理できていない。キーワード集の用語を網羅的には把握していない |
| **学習環境** | 通勤中にスマホで読むことが多い。まとまった勉強時間は週末のみ |
| **ゴール** | 総監部門の合格。「ここだけ読めば試験範囲をカバーできる」サイトを求めている |
| **不安** | 一般部門とは勉強法が違うことは知っているが、何をどう整理すればよいかわからない |
| **行動パターン** | キーワード集の用語を1つずつ確認しながら読む。過去問を解いて不明点をキーワードページで調べる |

## 文体ルール

コンテンツの役割に応じて「である調」と「ですます調」を使い分ける。同一ページ内での混在は禁止。

| 文体 | 対象コンテンツ | 理由 |
|---|---|---|
| **である調** | キーワードページ、教科書、択一式過去問の解説 | 概念の定義・分類・比較を簡潔に伝える技術文書。1文が短くなりモバイルで読みやすい |
| **ですます調** | **すべてのガイド**（受験戦略系・技術リファレンス系を問わず。合格戦略、学習計画、受験申込手順、試験インデックス、キーポイント集、トレードオフ整理、出題傾向分析、管理体系まとめ）、記述式・2次試験の解答戦略、論文添削例 | 読者に語りかけ学習の道筋を示すコーチング的な文書。ガイドは入口コンテンツであり、文体を統一して語りかける一貫した読書体験を提供する |

**ガイドは内容を問わず ですます調に統一する**: `tags: guide`（およびタイトル末尾が「戦略」「計画」「手順」「ガイド」「インデックス」「キーポイント」「整理」「分析」「体系」「トレードオフ」）のページはすべて ですます調。技術リファレンス系（キーポイント集・管理体系まとめ等）も、概念説明の地の文は「〜です」「〜します」で統一する。

**である調を残すのはガイド以外**: キーワードページ・教科書・択一式過去問の解説は従来どおり である調。

なお、文体統一の対象は**地の文（散文）**のみ。次の要素は元の簡潔表記（体言止め・常体）を維持する: 見出し、表のセル、`<SpecSheetList>` 項目、`<ExamPoint>`（体言止めが規約）、図キャプションの短句、KaTeX 数式、コード。

## コンテンツ原則

### 1. 冒頭では概念の本質を簡潔に示す

「〜とは」セクションでは、この概念が**何を扱い、どういう場面で使われるか**を簡潔に説明する。試験での重要性や他の管理分野との関連は「総合技術監理における位置づけ」セクションに集約する。

- 冒頭で書くべきこと: 概念の定義、対象範囲、基本的な仕組み
- 冒頭で書かないこと: 「試験で頻出」「総監技術者として重要」などの試験文脈

### 2. 表・箇条書きの前に文脈を与える

表やリストの直前に、その情報が**何を意味するか**を示す導入文を必ず置く。見出しの直後にいきなり表や箇条書きが来ると、読者は「何のための情報か」を把握できない。

- 悪い例: `### 7大ロス` → （即座に表）
- 良い例: `### 7大ロスとOEEの関係` → 「OEEの3要素はそれぞれ異なるロスの影響を受ける。どのロスがどの要素に影響するかを整理すると、改善すべきポイントが明確になる。」→ （表）

**機械検知**: 表は `lint-mdx-mobile.mjs` **6-1（MEDIUM）**。箇条書き・図・`<SpecSheetList>` が見出し直下に来るケースは **6-2 / 6-3 / 6-4（MEDIUM、group: guide 限定）**。キーワードページ（である調・簡潔技術文）は許容度が異なり全件強制するとノイズになるため、ガイド以外はエージェントの目視判断（`§17-2`）に委ねる。

### 3. 1文1段落でモバイル可読性を確保

空行で段落を分け、スマホでの視認性を優先する。連続4行以上の段落は分割する。Markdownの単純な改行は無視されるため、段落を分けるには必ず空行を入れる。

### 3.5. 見出し（H2/H3）の括弧書き

見出しの括弧書きは **TOC ナビゲーションの識別子として機能するか** で取捨を判断する。識別子になっていない補助情報を機械的に並べると、TOC が縦長化してモバイルでの一覧性が低下する。

**避けるべき括弧書き**:

- 単純な所管組織名・部署名（例: `### 経済財政白書（内閣府）` の `（内閣府）`）— 本文 1 段落目で説明すれば十分。受験者は白書名で覚えるため識別子にならない
- 同一カテゴリ内の繰り返しメタデータ（例: 「白書マップ」内で各エントリに省庁名を毎回付ける）

**残してよい括弧書き**:

- **略称・通称**（例: `### 製造物責任法（PL 法）逐条解説`、`### 労働経済の分析（労働経済白書）`）— 通称で検索する読者の到達性を確保
- **旧名称・別表記**（例: `### DX 動向 2025（IPA、旧 DX 白書）`）— 検索ヒット性に直結
- **年代・期間**（例: `### 定着期（令和 3 〜令和 7 年度）`）— 学習計画上の識別子
- **分類フラグ**（例: `### A. 気候変動適応 × グリーンインフラ（重点度: 高、主役）`）— 重要度の即時判別
- **本文の構造補足**（例: `## 国土交通白書R7 5管理マッピング（主要数字）`）— セクション内容の即時把握
- **合冊・併記の構造情報**（例: `### 環境白書・循環型社会白書・生物多様性白書（3 白書合冊）`）— ナビゲーションに必要

**判定の自己チェック**: 「この括弧書きを削除したら、読者が TOC を見て迷うか？」を自問する。迷わないなら削除する。

**校正観点**: ガイド記事の H3 が 10 件以上ある記事で、過半数の H3 が同種の括弧書きパターン（特に組織名・部署名）を含む場合は本ルール違反の可能性が高い。`grep "^### .*（" {article}.mdx` で機械的に検出できる。

#### 見出しの番号記号（①②③④⑤・1.・(1) など）

見出し冒頭の番号記号は **原典準拠（過去問の設問番号等）以外では使わない**。番号は §2「絵文字禁止」「過剰装飾を避ける」の精神に反し、本質情報（見出し本文）を視覚的に圧迫する。

**使ってよい番号記号**:

- 過去問・公式試験原典の設問番号復元（例: `### ①利活用するデータと方法` — R03 記述式の設問構造をそのまま転載）
- 手順書の番号付きステップ（例: `### ステップ 1: 環境構築`）— 順序が学習価値そのもの

**使ってはいけない番号記号**:

- 並列セクションの装飾的な番号付け（例: `## ① 経済性管理に対応する白書` — 5 管理名で識別可能、番号は装飾）
- 5 管理・3 軸など固定構造の枚数強調（番号がなくても構造は読者に既知）

**判定の自己チェック**: 「番号を削除して並びだけにしたら、見出しの意味が壊れるか？」を自問する。壊れないなら削除する（過去問設問など順序自体が情報の場合のみ維持）。

**校正観点**: `grep -E "^##+ *[①-⑳1-9]" {article}.mdx` で機械検出。装飾用途と原典準拠を区別して対応する。

### 4. 表は2軸比較にのみ使う

表は「行と列の両方向に読んで比較する」データにのみ使用する。各行が独立した説明なら箇条書きを使う。

**表が適切な場面**:
- 2軸以上の比較（例: BCP vs 防災計画、MAC vs DAC vs RBAC）
- 短いセルの分類一覧（各セル15文字以内、3列以内）
- マトリクス（SWOT等の2×2グリッド）

**表を使わない場面**:
- キーバリュー表（正式名称・目的・所管等） → 冒頭の散文に統合
- 用語+説明（効果/内容、留意点/内容） → `- **用語**: 説明` の箇条書き
- 計算手順 → 番号付きリスト（1行1ステップ）。KaTeX数式を表セル内に入れない
- 時系列・プロセス → `<Timeline>` コンポーネント
- 4列以上 → 原則禁止。比較として不可欠な場合のみ、各セル15文字以内

**4列が許容される典型パターン**:
- **3 者以上の比較**: 観点列 + 3 つの対象列（例: グレーインフラ / グリーンインフラ / ハイブリッド、CSR / CSV / SDGs）
- **マトリクス**: SWOT（2×2）等、構造的に 4 セル以上が必要な場合

いずれも各セル 15 字以内を厳守。超える場合は箇条書きに分解する。

**iOSアプリ展開を見据えた判断基準**: 「この情報をSwiftUIのListで表現できるか？」と考える。Listで自然に表示できるなら、表ではなく箇条書きやコンポーネントを使うべき。

#### 機械ゲート（表・入れ子リスト・段落長のモバイル可読性）

表・リスト・段落のモバイル可読性は `lint-mdx-mobile.mjs` が機械検知する。ルールの重大度・資格×種別の有効/無効の SSOT は **`.claude/config/content-rules.json`**（policy .md ↔ config .json ↔ guard script パターン）。主なルール:

- **1-3 / 1-4 / 1-5 / 1-7**: 4列以上の表・3列以上のセル15字超・キーバリュー表・壊れた表 → 表を避け、下記の変換パターンへ
- **3-1**: 入れ子リスト（2階層以上）→ 太字リード＋フラット1階層 or `<SpecSheetList>`
- **15-3**: 1段落300字超 → 2〜3文・目安200字で改段（§24。note は〜120字で別系統）

**具体的な変換パターンカタログ**は [content-authoring.md](content-authoring.md) の「モバイル視認性」節を参照（現状の表 → 変換先の早見表）。

全量ラチェット `npm run check-content-quality`（週次 CI `r2-audit.yml`）が既存違反を baseline で grandfather しつつ、**新規違反（baseline 超過）を赤落ち**させる。既存違反はリライトで漸減させる（優先度は `.claude/state/quality/latest-report.md` の GA4 人気度順）。なお pre-commit フックが実行するのは `pre-commit-mdx.mjs`（MDX コンパイル・frontmatter・壊れ表・SVG 等）であり、`lint-mdx-mobile.mjs` 自体の実行点は品質サイクル（`/quality-cycle`・`bulk-score`・`/check-mdx`）・手動・週次 CI ラチェットの3系統。

#### 「用語+定義+例」型 shallow table の散文化（2026-05-27 追加）

2-3 行の table で各行が `**用語**（bold）| 定義 | 例` の構造になっている場合、原則として **散文段落** に展開する。箇条書きではなく散文段落が educational 価値が最も高い（背景・例外・関連を補足できる）。優先順位は **散文 > 箇条書き > 表** で、表は最後の手段。

**散文化対象の判定**:
- 行数が 2-3 行
- 第 1 列が `**...**` の用語名
- 第 2-3 列のテキストが各 50 字以内かつ数値・年代・条文番号を含まない
- セクションの主題が「概念定義」（比較・分類ではない）

**散文化の書き方**:
- 各概念を独立した段落で書く（1 概念 1 段落）
- 用語は `**用語名**` で散文中に bold inline
- 定義 → 具体例 → 背景・補足 の順で 2-4 文に展開
- 表セルに収まらなかった「経緯・例外・関連」を補足できるのが prose の強み

**表を維持してよい場面**:
- 4 行以上の indicator data（数値・年代付き）— 例: 法令対象事業者一覧、白書統計の年次比較
- 異なる属性（観点）を 2 つ以上比較する 3+ 列 — 例: 3 者比較（グレー/グリーン/ハイブリッド）
- reference 用途（scan して引きたい）— 例: ISO 規格番号一覧

**過去事例**: 2026-05-27 の decoupling 記事リファクタ（commit de0aba766）で「2類型」「資源/影響」「日本状況」の 3 表を散文化 → モバイル可読性向上 + 背景説明追加で学習価値拡大。

#### 壊れた表（ヘッダー＋セパレータのみ）を残さない

`| 項目 | 内容 |` ＋ `|---|---|` の **2 行だけで本文行（`| ... |`）が 1 行も無い**表は、GFM で空テーブルとして崩れて描画される。PDF→MDX 変換や「キーバリュー表の散文化」の途中で、表本体だけ箇条書き・段落に置換され、ヘッダー行と区切り行が残骸として取り残されたときに生じる（2026-06-16、9 ファイル 32 箇所を検出・是正）。

- **キーバリュー残骸**（`| 項目 | 内容 |` の直後が箇条書き）: 残骸の 2 行を削除し、箇条書きを本体として残す
- **キャプション table**（`| 表 3.1 ... |` ＋ `|:--|` の単一セル、直後に実データ表）: キャプションは `**表 3.1 ...**` の太字テキスト行にして、実データ表の上に置く
- **空フォーム**（多列ヘッダーのみの帳票・様式の再現）: 空のまま残さず、記載項目を箇条書き化するか、原典に値があれば本文行を補う

**機械検知**: `lint-mdx-mobile.mjs` カテゴリ **1-7（HIGH）**（review-mobile / bulk-score で surface）に加え、**`scripts/pre-commit-mdx.mjs` の `checkBrokenTables` が pre-commit でコミットをブロックする**（HIGH）。本文行ゼロの表を検出する。

### 5. 試験ポイントの担当分離（図版 vs コンポーネント vs IG）

試験頻出ポイント・引っかけ論点の情報は、以下の**3層に分離**して管理する（混在禁止）。

| 担当 | 場所 | 役割 |
|---|---|---|
| `<ExamPoint>` / `<Callout>` | MDX 本文 | ページ読了後の整理・ナビゲーション |
| IG テキストスライド（`0N-text.svg`） | `docs/sns/instagram/.../keyword-packs/` | SNS フォロワー向けの要点配信 |
| **figure-*.svg** | `.local/r2/posts/**/img/` | **含めない（禁止）** |

**figure-*.svg に「試験ポイント」「引っかけ」バー・注記ボックスを入れてはならない。** 概念・構造・比較の可視化に専念させる。詳細は `figure-canvas-policy.md §2.5`。

### 6. ExamPointは文脈の後に配置

概念の説明が終わった後に配置する。定義セクション（〜とは）の直後に置かない。読者がまだ概念を理解していない段階で試験ポイントを示しても効果がない。

**個数の上限**:
- **原則1個**: 「総合技術監理における位置づけ」セクション末尾の総括ExamPoint 1個が基本パターン
- **最大2個まで**: H3サブセクションが複数あり、各サブテーマごとに独立した試験ポイントがある場合のみ2個まで許容
- **3個以上は禁止**: 内容を統合できないか必ず検討する

**配置の鉄則**:
- 「総合技術監理における位置づけ」セクション末尾に総括ExamPointを必ず1個置く
- フラットなH2のみ構造（H3サブセクションがない構造）では H2 末尾に追加配置しない（ExamPointが本文中に散らばる原因になる）
- 異なるセクションの内容を1つのExamPointに混ぜない

**禁止パターン**（過去問の解説に属する内容をキーワードページに書かない）:
- 「誤り選択肢パターン」「代表的な誤り」「頻出の誤り」など、過去問の選択肢判定に属する内容を ExamPoint の `summary` や `items` に書かない
- これらは過去問MDX（`r*-primary/article.mdx` 等）の `<details>` 解説ブロック内に書く
- キーワードページは概念解説に専念する
- 本文中に「❌」「✅」「正答：N」など過去問の判定記号を書かない（過去問MDXのみ許可）

**ベンチマーク**: BCP（事業継続計画）ページは ExamPoint 2個（H3末尾＋総括）の構成。これを上限の参考とする。

**適用範囲と例外**（2026-05-17 追記、1級土木 guide ピラー型の運用整合）:

本 §5 の ExamPoint 規定は **CEM（総監）キーワードページ・1級土木 secondary（二次過去問）** を主対象とする。**1級土木 textbook/guide ピラー型ページ**では、以下の理由から `<Callout type="note" title="試験のポイント">` を ExamPoint の代替パターンとして許容する:

- **配置位置の役割差**: ExamPoint は「ページ末尾の総括」（読了後の振り返り）、guide ピラーの試験のポイント Callout は「各 H2 セクション直前の頻出論点予告」（読了前のナビゲーション）。pedagogical 役割が異なる
- **個数の構造的非互換**: guide ピラーは H2 が 5-8 個並ぶ重量ページが多く、各セクション冒頭に予告マーカーを置く運用が定着。ExamPoint「1-2 個」上限と相反する
- **書式の自由度**: Callout は散文＋太字で予告フレーズを書ける（「○○の長所と短所が頻出」等）。ExamPoint の体言止め強制では予告として機能しない

guide ピラー型ページでの推奨運用:

- `<Callout type="note" title="試験のポイント">` を **1 セクション 1 個まで**（合計 5-8 個が標準）
- **見出し（H2/H3）と Callout を直結しない**: 見出しの直後に地の文なしで Callout を置くと、H2→枠の段差が連続してリズムが単調になり、Callout の注意喚起機能も薄れる。見出しと Callout の間に、そのセクションが扱う範囲を示す **1〜2 文のリード**を必ず挟む（「H2 → リード → Callout → 本文」）。機械検出は lint `6-5`（見出し直下・guide 限定）＋`6-6`（記事冒頭の構造物直始まり・guide/secondary/textbook）＋`9-14`（Callout 連続）＋`9-15`（例題・計算例の Callout 化）＋`9-16`（密度超過 guide/pillar>12・他>3）。2026-07-15 の全数調査（1,069 本）に基づき一括設計・fullScan 登録済み
- **例題・計算例は Callout に入れない**: 例題は注意喚起でなく本文コンテンツ（§7.1-1 の「Callout が本文を担う」に該当）。`#### 例題1：…` の見出し＋地の文で書く（解答リスト・KaTeX は維持）。同種 Callout の連続（§7.1-5）も回避できる
- 末尾に総括 ExamPoint を置く必要はない（重複になる）
- ベンチマーク: `guide-last-minute-2026` / `guide-four-management` / `guide-law-key-points`（Callout 7-12 個で構造的に成立）

textbook（個別概念ページ）では原則 ExamPoint を 1 個末尾配置すべきだが、画像・表が中心で本文が薄いページではCallout で代替してもよい。

**items の禁止パターン**（機械分割バグの再発防止 — 2026-05-16 追記、AdSense 再申請対応）:

`<ExamPoint items={[...]}>` 配列内の各文字列は **体言止め or 完結した独立文** で書く。**句読点（、。，．）で割られた途中切れの断片を items に詰めない**。lint カテゴリ 9-11 で機械検出される。

- ❌ 反例（機械分割バグの典型）:
  ```mdx
  <ExamPoint
    summary="ブロック積擁壁工は，原則として胴込めコンクリートを設けない空積ではなく，胴込めコンクリートを設ける練積みが原則である。..."
    items={[
      "ブロック積擁壁工は",
      "原則として胴込めコンクリートを設けない空積ではなく",
      "**胴込めコンクリートを設ける練積み**が原則である",
      "水平方向の目地が直線とならない谷積で積み上げるという点は正しいが",
      "空積が原則というのは誤りである",
    ]}
  />
  ```
- ✅ 正例（体言止め独立ポイント、items は 1〜3 個）:
  ```mdx
  <ExamPoint
    summary="ブロック積擁壁工は原則として練積で施工する"
    items={[
      "胴込めコンクリートを充填する練積が原則（空積は例外）",
      "水平目地が直線にならない谷積で積み上げる",
      "石材・ブロックの背面に栗石または割石を擁壁高さに応じて配置",
    ]}
  />
  ```

ルール:
- `summary` = 核心 30〜50 字（試験で問われた本質を 1 文で）
- `items` = 体言止めの独立ポイント **1〜3 個**（最大 3 個、原則 2 個）
- 各 item は ≤60 字、**内部に句読点を含めない**（末尾の句点は許容しない）
- 「正答：」「❌」「✅」「適当でないものは N」を items に含めない

機械分割の元凶: `.claude/scripts/migrate-civil-answer-style.mjs` の `generateExamPoint()` で約 1,440 個の壊れた ExamPoint が生成された（DEPRECATED 済み）。修復は `civil-exampoint-restorer` Generator サブエージェントを使う。

### 7. 過剰装飾を避ける

- 絵文字（❌✅💡🔑📌⚠️等）を使わない
- **Callout はメリハリをつけるために使う**（1 記事に 3 個以内）
  - **使いどころ**: 原則の例外・頻出引っかけ肢・誤解されやすい定義など、**受験者が平文で読み飛ばすと失点する論点**
  - **使わない**: 単なる補足、本文で十分伝わる一般的な説明、装飾目的
  - **2026-04-22 Claude Design ハンドオフで全面リデザイン**: 旧 9 種（info/warning/error/success/note/tip/question/caution/danger）を廃止し **12 種に再編**。デザインは **左アクセントバー + 円形アイコン + 任意タイトル** のミニマル構成（zip 原設計に厳密準拠）。ラベルテキスト（"NOTE"・"ポイント" 等）は**描画せず**、型の識別はアイコン + 色で行う（スクリーンリーダー向けには `aria-label` で補完）
  - **汎用種別（5 種）**:
    - `type="note"`（メモ / 青系 / Info） — 事実の強調・補足情報。旧 `info` の移行先
    - `type="tip"`（ポイント / 緑系 / Lightbulb） — 学習コツ・覚え方のヒント
    - `type="warn"`（注意 / 橙系 / AlertTriangle） — 行動への警告・頻出引っかけ。旧 `warning` / `caution` の統合先
    - `type="danger"`（重大リスク / 赤系 / Ban） — 致命的な誤解・重大な誤答
    - `type="success"`（合格ライン / 緑系 / CheckCircle） — 到達水準・達成条件の明示
  - **ドメイン特化種別（7 種）**:
    - `type="exam"`（出題頻度 / 桃系 / Flag） — 本文中の出題頻度アクセント（「ここは出題頻度高」等の単発注意）
    - `type="formula"`（公式 / 藍系 / Sigma） — 公式・計算原理の枠（例: V = F/C、指数平滑法の逆算式）
    - `type="standard"`（基準・規格 / 紫系 / BookOpen） — JIS / ISO / 法令条文の引用枠
    - `type="example"`（実例 / 青緑系 / Beaker） — 具体的な計算例・事例・ケーススタディ
    - `type="reference"`（参考文献 / 灰系 / Link2） — 書籍・論文・外部 URL への誘導枠
    - `type="faq"`（よくある質問 / 黄系 / MessageSquare） — 受験者が繰り返し聞きがちな Q&A 形式
    - `type="quote"`（引用 / 中立灰 / Quote） — 原典文献の直接引用枠
  - **旧 type は削除済み**（既存 MDX は自動移行）: `info` / `warning` / `caution` / `error` / `question` は廃止。使用するとランタイムで `note` にフォールバックする
  - **`<Callout type="exam">` と `<ExamPoint>` の使い分け**:
    - `<ExamPoint summary items>` — 記事**末尾の構造化総括**（要点＋箇条書き、記事全体を締める）
    - `<Callout type="exam" title>` — **本文中の単発アクセント**（特定論点に出題頻度アクセントを付けたい場合）
    - 役割が異なるため両者は共存する
  - **過小も品質問題**: 長文キーワード（H3 が 4 つ以上）で Callout がゼロの場合、引っかけ論点を視覚分離できていない可能性がある。cem-qa で surface する
  - **docs/ 配下 .md ドキュメントの Obsidian callout（`> [!note]` 等）は別物**: 公開記事 MDX 用の `<Callout>` コンポーネントとは記法・種類・実装が独立。社内ドキュメント執筆時は [docs-markdown-style.md](./docs-markdown-style.md) を参照（推奨 4 タイプ限定）
- 太字は1段落に1〜2箇所。すべてを太字にすると何も目立たない
- **太字スコープは 30 字以下に絞る** ── 特に「○○とは…である」概念定義文では、長文全体ではなく **核心キーワードのみを太字にする**

#### 太字スコープの正例・反例

**反例（NG）**:

> インフラ老朽化対策とは、**高度経済成長期に集中整備された社会インフラが一斉に更新時期を迎える問題に対し、計画的な維持管理・更新で機能と安全を確保する取組** である。

59 字の長大な太字。読者の視線がどこに向かうべきかわからず、強調が機能しない。

**正例（OK）**:

> インフラ老朽化対策とは、高度経済成長期に集中整備された社会インフラが一斉に更新時期を迎える問題に対し、**計画的な維持管理・更新** で機能と安全を確保する取組である。

12 字の核心キーワードに絞った太字。方法論の中核（事後保全との対比軸）が即座に伝わる。

**正例（2文分割パターン）**:

> 4E対策とは、労働災害の防止対策を **4 つの観点（4E）** から体系的に実施する考え方である。4E は Education（教育）・Engineering（技術）・Enforcement（徹底）・Example（模範）の 4 要素を指す。

定義文と要素列挙を 2 文に分け、太字を「4 つの観点（4E）」だけに絞る。

#### 執筆時の自己チェック

「○○とは…である」を書き終えたら、**太字部分の文字数を即座に数える**。30 字を超えていたら必ず縮める。`/review-mobile` スキルが機械的にも検出する（カテゴリ 7-1）。

太字に絞る対象の優先順:

1. **方法論的中核**（例: 「**計画的な維持管理・更新**」「**4 つの観点（4E）**」）
2. **唯一識別する固有名詞**（その概念を他から区別する用語）
3. **キー数値・略語**（例: 「**RTO**」「**95% 以上**」）

これらに該当しない長い説明部分は太字にしない。

### 7.1 Callout 使用観点（5 判定基準）

`§7` の「1 記事 3 個以内」「単なる補足には使わない」を実装段階で判断するための 5 ステップ判定フロー（2026-05-17 策定、`mlit-whitepaper-2025` の Callout 10→2 整理の知見を恒久化）。執筆・校正時に Callout を残すか散文化するか迷ったら順に当てはめる。

1. **本文を担っているか？** — Callout 内に「その節の主要コンテンツ」が詰め込まれていて、外の本文がほぼ空、なら NG。処置: 散文化（地の文に戻す）または `<SpecSheetList>` / 表に変換
2. **本文と二重に書いていないか？** — Callout と隣接コンポーネント・本文が同内容を別表現で繰り返しているなら NG。処置: §17（散文中心）に従い Callout を削る
3. **「答案にそのまま転写したい／後で見返したい」強い利用シーンがあるか？** — YES なら視覚カード化の利便性が明確で、Callout を残す正当理由
4. **本文と別レイヤーの誘導か？** — 商業 CTA（note magazine 等）・致命的失敗の警告（type="danger"）・本文フローを意図的に中断する重要なお知らせなら Callout が正当。単なる「関連記事一覧」「記事の使い方」程度は冒頭リード文の散文に溶かす方が自然
5. **同種 Callout が並列していないか？** — 同 type・同用途の Callout が 3 個以上連続するなら、個別ハイライトではなく「箇条書きの代替」。`<SpecSheetList>` に統合する

#### type と用途の対応表（本記事スコープ）

| type | 使う場面 | 使わない場面 |
|---|---|---|
| `tip` | 商業 CTA、note magazine 誘導、本文外への送客 | 一般的な助言・記事の使い方紹介 |
| `note` | 事実の強調（短く）、補助情報 | 主要数字・要点の集約（→ `<SpecSheetList>`） |
| `example` | 「そのまま転写可」な答案テンプレ、コピペシーン明確 | 散文中で十分伝わる例示 |
| `warn` / `danger` | 致命的な誤解を防ぐ警告、引っかけ論点 | 単なる注意 |
| `exam` | 単発の出題頻度アクセント | 早見表の代替（→ `<SpecSheetList>`） |
| `formula` / `standard` / `reference` / `faq` / `quote` | 各 type 定義通りの専用枠 | 装飾目的の汎用化 |

#### 適用範囲と例外

- **キーワードページ・PE guide（試験概要系）** — 本 §7.1 を厳守、Callout 3 個以内
- **1 級土木 guide ピラー型** — §5 の例外規定（`<Callout type="note" title="試験のポイント">` を 1 セクション 1 個まで＝合計 5-8 個）が優先
- **過去問ページ（primary / secondary）** — 各問の正答・解説・引っかけ論点マーカーが構造的に多用されるため、本 §7.1 の個数上限の対象外（type 妥当性のみチェック）

### 8. 図表は説明の流れの中に配置する

図表・グラフは独立した「図解」セクションにまとめず、**それを説明する本文の直後に配置する**。読者が概念を読み、図で確認し、次の説明に進む流れを作る。

- 悪い例: 計算式のセクション → 関連指標のセクション → 「## 図解」でグラフとデータ表をまとめて掲載
- 良い例: 計算式のセクション内にグラフを配置 → データ表を「計算例」として計算過程とセットで掲載

**図の前には必ず 1 文の導入文を置く**。「何を示す図か・なぜこの位置にあるか」を本文で誘導してから図を出す。図だけを見て概要が伝わる必要はなく、本文の一部として機能させる。

- 悪い例: `## 手続きの流れ` → 直下に `<ArticleImage>`（いきなり図、文脈なし）
- 良い例: `## 手続きの流れ` → 6 ステップの番号付きリスト → 「各フェーズで誰がどう関与するかを示す」1 文 → `<ArticleImage>`

`{/* quiz-figures:start */}` / `{/* quiz-figures:end */}` マーカーは図の出典管理用であり、見出しの要否とは無関係。マーカーは残しつつ、図を本文中の適切な位置に配置する。

**`<ArticleImage>` の caption は「図の説明」には使わない。** 図の内容は本文で説明する（caption に書くと本文と重複して冗長になる）。

ただし、**出典・著作権帰属・機種名などの短い帰属情報は caption に書いてよい**（目安 60 字以内）。CC 写真の出典表示やメーカー機種名は、本文に織り込むと文章が不自然になるため、caption の方が自然な置き場所となる。読者にも「誰の撮影か」「どの機種か」が伝わる。

- 悪い例（説明型 caption）: `<ArticleImage caption="図: 実行可能領域（青）と等利益線（赤の破線）。等利益線を z 増加方向へ平行移動し…" />`
- 良い例（説明は本文、帰属は caption）: `<ArticleImage alt="線形計画法の図解法" caption="Wikimedia Commons, CC BY-SA 4.0" />` + 本文で図の読み方を説明
- 良い例（機種名のみ）: `<ArticleImage alt="トータルステーション" caption="Leica TC305（Public Domain）" />`

### 9. 試験に直結しない情報は省く

「歴史・背景」「理論的根拠」セクションは、その内容が**試験で問われる場合のみ**記載する。制定年・制定経緯が出題される法律（例: 災害対策基本法と伊勢湾台風）は記載すべきだが、学説の発展史や業界統計のトリビアは省く。

判断基準: 「この情報がないと過去問を解けないか？」— No なら不要。

### 10. 数式の表記

数式は以下の優先順で表記方法を選ぶ。

1. **SVG（推奨）**: フォントサイズが統一され、モバイルでも崩れない。分数を含む場合は `÷` 表記にして1行で書く
2. **KaTeX**: SVG化が過剰な場合（インラインの短い数式など）。ただし `\frac{}{}` は分子・分母のフォントが縮小されてモバイルで読みにくいため、可能な限り `÷` 表記に書き換える
3. **プレーンテキスト**: `MTBF = 総稼働時間 / 故障回数` のように記号だけで伝わる場合

### 11. リンクの使い分け

文中で関連キーワードに言及する場合と、セクション末尾で一覧表示する場合、別ページに論点を集約している場合でリンク方法を使い分ける。

- **文中のインラインリンク** → Markdownリンク `[キーワード名](/docs/pe-comprehensive-management-{slug})`
- **本文中で別ページへ強く誘導したい時** → `<SeeAlso href="..." title="..." reason="..." />`（「あわせて読みたい」カード、1 記事 5 個以内）
- **セクション末尾の関連キーワード一覧** → `<RelatedKeywords>` コンポーネント（ブロック配置）

`<RelatedKeywords>` はブロックレベルUI（ボーダー付きdiv）であり、文中にインラインで使うと視覚的に不自然になる。また、MDXプリプロセッサとの相性問題でコンパイルエラーが発生する場合がある。

`<SeeAlso>` は「ここで深掘りせず別記事に集約している論点」を本文中で目立たせる用途。`reason` には「なぜそのページを併読すべきか」を 1〜2 行で書く。Callout の 1 記事 3 個ルールから独立しているが、過剰使用を避けるため 1 記事 5 個以内に抑える。詳細は [`src/components/ui/SeeAlso/README.md`](../../../src/components/ui/SeeAlso/README.md)。

### 12. 参考資料の構成

`## 参考資料` セクションは公的資料と民間解説記事の両方を含めること。公的資料は正確性、民間記事はわかりやすさの観点で相互補完となる。

**最低構成**:
- **公的資料 最低1件**: 官公庁（go.jp）・公的機関（or.jp）・大学（ac.jp）の解説ページ
- **民間解説記事 最低1件**: Wikipedia、技術ブログ、note記事、弁護士事務所等の解説、業界団体の啓発ページなど

**記載ルール**:
- 形式: `- [資料タイトル](URL)（出典元）`
- **説明文（` — 解説`）は書かない**。出典自体が権威性のシグナルとして機能するため冗長。タイトルが組織名のみ等で内容が分からない場合は、説明文で補うのではなく **タイトル自体を記述的にする**（例: 「中央労働災害防止協会」→「中央労働災害防止協会のパトロール手法解説」）
- URL は **WebSearch で候補発見 → WebFetch で実在確認 → 記載** の3ステップを必ず踏む。推測や記憶からの URL 記載は禁止。WebFetch で 404 やリダイレクトが返った場合は記載しない
- **校正依頼を受けたページは必ず参考資料 URL を全件 WebFetch で確認する**。新規作成か既存編集かを問わず、また参考資料セクション自体を編集したかどうかに関わらず毎回実施する。「元々あった URL だから信頼できる」という前提は禁止。官公庁サイトはページ移転・PDF 削除が頻繁に起きる
- **Wikipedia の項目名は特に注意**: 中黒（・）の有無、漢字/カタカナの表記ゆれで別ページになる（例: 「デザインイン」は存在しないが「デザイン・イン」は存在する）。必ず WebSearch で正確な項目名を確認してから URL を組み立てる
- **連番 URL の捏造リスク（2026-05-27 追加）**: 民間 解説サイトの記事 ID は推測してはならない。特に危険なパターン:
  - `emira-t.jp/pedia/{数字}/` — pedia 系の番号は飛び番が多く、近似番号でも別記事 or 404
  - `{site}/article/{連番}/` `{site}/column/{slug}/` 等の連番・slug URL
  - 失敗事例: 2026-05-27 のエネルギー分割作業（commit c7f5aa167）で EMIRA `pedia/26789/` `pedia/19895/` `pedia/24613/` を 3 件パターン補完で記載 → 全て 404、cem-qa 並列評価で発見 → 修正 commit 646d2461f
  - 鉄則: 候補 URL は必ず **書く前に WebFetch で実在確認**。「いつもこの形式だから」「他の番号で存在するから」は無効
- 試験の公式ページ（キーワード集ダウンロードページ等）は学習リソースではないため不適切
- 組織のトップページではなく、当該キーワードを直接解説しているコンテンツへのリンクを優先する
- 同一組織の異なるURLでも内容が同じなら1件に絞る（重複排除）
- 存在確認できなかったURL・内容がキーワードと無関係なURLは記載しない（出典名だけテキストで残すのも不可）
- **書籍（著者名＋書名＋出版社）は記載しない** — 参考資料は読者がワンクリックでアクセスできる Web リソースに限定する。書籍の内容が重要な場合は、同等の内容を扱う公的ページまたは民間解説記事を探して記載する

**法令条文へのリンク**:
- 本文中で法律の条文に言及する場合、e-Gov法令検索の該当条文へのアンカーリンクを付与する
- URL形式: `https://laws.e-gov.go.jp/law/{法令番号}#Mp-At_{条番号}`
- MDX では `**[text](url)**` が正しくパースされないため、太字はリンクテキストの内側に置く: `[**法律名第◯条**](url)`

### 13. 計算例・具体例で概念を補強する（条件付き）

概念の理解を深めるために計算例・適用例を記載するかどうかは、キーワードごとに判断する。**以下の 3 条件を全て満たすキーワードにのみ記載** し、満たさないキーワードには書かない（冗長・論点拡散の原因となる）。

**適用条件**（全て満たす必要あり）:

- **条件 A**: 過去問で具体的な数値問題・計算問題として出題される
- **条件 B**: 条件・順序・配分等で結果が変わり、直感と一致しない側面を持つ
- **条件 C**: 式または数値表で「なぜそうなるか」の根拠を示せる

**書き方**:

- 数式は原則 10 に従い KaTeX（`$$...$$` または `$...$`）または SVG を使う。**コードブロック（\`\`\`）は使わない**
- 計算例は 1 つに絞る（複数並べると冗長）
- 出題源の過去問へインラインリンクを張り、計算例の出所を明示する
- 変数を使う場合は必ず定義を添える（例: 「ここで $C_i$ は $i$ 番目に処理した作業の完了時刻」）
- 計算過程は番号付きリストまたは箇条書きで示す（表セル内に KaTeX は入れない）

**該当する例**（計算例を記載すべきキーワード）:

- [リードタイム](/docs/pe-comprehensive-management-lead-time) — SPT ルールと平均フロータイム計算
- [工程能力指数](/docs/pe-comprehensive-management-process-capability-index) — Cp/Cpk の数値例
- [損益分岐点](/docs/pe-comprehensive-management-break-even-point) — 売上高・費用の数値例
- [正味現在価値](/docs/pe-comprehensive-management-npv-net-present-value) — 割引率と NPV 計算
- [線形計画法](/docs/pe-comprehensive-management-linear-programming) — 実行可能領域と目的関数
- [PERT/CPM](/docs/pe-comprehensive-management-pert-cpm) — クリティカルパスの計算

**該当しない例**（計算例を記載すべきでないキーワード）:

- [フォロワーシップ](/docs/pe-comprehensive-management-followership) — 定性概念
- [組織コミットメント](/docs/pe-comprehensive-management-organizational-commitment) — 定性概念
- [サーバントリーダーシップ](/docs/pe-comprehensive-management-servant-leadership) — 定性概念

**判断に迷ったときの自己チェック**: 「この概念を過去問で問われたとき、計算なしで正解が導けるか？」── Yes なら記載不要、No なら条件 A/B/C を改めて検証する。

### 14. 半角数字と日本語の間にスペースを入れる

半角数字と隣接する日本語文字の間には **半角スペース**を 1 つ入れる。可読性が向上し、CJK と ASCII の視覚境界が明確になる。

- 良い例: 「2015 年の計画」「100ha 以上」「タイプI → II → III の順」「第 4 次社会資本整備重点計画」
- 悪い例: 「2015年の計画」「100ha以上」「タイプI→II→IIIの順」

**例外**:
- 規格名・型番・ID 内部の数字（`ISO 14020`, `COP10`, `RTO`）は単体のトークンとして扱うためスペース不要
- 半角数字同士（`2015-2026`）は当然スペース不要

### 14-b. bold の内側に全角括弧を含めない

`**text）**` や `**XX（YY）として勤務後に退職**` のように bold スパン `**…**` の **内側に全角括弧 `（）「」『』【】`** を含めると、レンダリングが崩れる。原則は **括弧は必ず bold の外側に出す**。

**2 つの異なる原因が同時に存在する**:

1. **末尾の約物** — `**…）**` のように bold 閉じタグ `**` の直前が約物で、かつ**直後が文字・数字**のとき、CommonMark 仕様の「right-flanking delimiter run」判定に失敗し bold が無音でレンダリングされない（サイト側 MDX で発生）。約物は全角閉じ括弧 `）」』】` に限らず `。，％℃` 等でも起きる一方、直後が空白・行末・記号なら閉じ括弧でも崩れない。「末尾が全角閉じ括弧なら必ず崩れる」は近似であって真ではないので、判定は下記の実パースに委ねる
2. **note 独自パーサの中間全角括弧** — `**…（…）…**` のように bold 内部のどこかに全角括弧を含む（特に長い span・複数括弧・リンク混在）と、note.com のレンダラが bold スパンを正しく解釈しない（note 側で発生）

**サイト側（MDX）で起きる例（原因 1）**:
- NG: `**道路橋（約 37%）**であり`
- OK: `**道路橋**（約 37%）であり`

**note 側で起きる例（原因 2）**:
- NG: `**地方自治体の土木職（発注者）として勤務後に退職**`
- OK: `地方自治体の**土木職**（発注者）として勤務した後に退職`
- NG: `**1 級土木施工管理技士・…・技術士（建設部門）・技術士（総合技術監理部門）**`（複数全角括弧を含む長い太字）
- OK: 箇条書きに展開し、項目自体に太字を付けない
- NG: `**¥2,480（6 本セット、単品比 17%OFF）**`
- OK: `**¥2,480** （6 本セット、単品比 17%OFF）`

**機械検知**:
- サイト側 MDX: `scripts/check-bold-rendering.mjs`（`npm run check-bold-rendering`）が原因 1 を検知。規則を再実装せず **remark で実パース**し、`text` ノードに `**` が残る＝描画されていない、で判定する（ground truth）。pre-commit（`--staged`）と `quality:audit --ci` の両経路に結線済み。機械的に安全な形の一括修正は `npm run fix-bold-rendering`（dry-run 既定・`--commit` で適用）
  - 旧 `pre-commit-mdx.mjs` の `checkBoldEndingParen` は 2026-08-04 に削除。`）」』】）` の 5 文字だけを見る近似ルールで、`。，％℃` や壊れたリンクを取りこぼす一方、実際には描画される形を誤検知していた
- note 側ドラフト: `/note-prepublish-review` Phase 1 § 4b の **Pattern A**（`**…（…）…**` 任意位置・リンク有無不問）が原因 1・2 の両方を検出して BLOCK
- 補助: 同 Phase の **Pattern B'**（`)**（` 境界）はリンク URL 直後の全角括弧連続パターンを検出

**判断基準**: 太字を付けたい部分から全角括弧を取り除けない場合は、**太字を諦めるか、太字範囲を括弧の外側で区切る**。「資格列挙のような長文を 1 つの太字で囲む」スタイルは、note では特に **箇条書きに展開**するか **太字を付けない**選択を優先する。

### 14-c. note 有料マガジン導線 CTA は「リンクカード＋価格なし」で書く

note 記事本文（`docs/note/**/article.md`）から有料マガジンへ誘導する CTA は、次の 2 つを必ず守る。

1. **マガジンURL は bare URL を単独行に置く（リンクカード化）**。`[テキスト](https://note.com/dobokunote/m/ID)` の markdown リンク形式は note でカード化されず、視覚的に弱くなる（CTR 低下）。適切な導入文のあとに **空行＋URL 単独行＋空行**で配置する。
2. **CTA 本文に価格（¥）を書かない**。マガジンは価格改訂があり、本文直書きの価格は陳腐化して **誤記** になる（2026-06-12、建設部門入口記事 16 本が旧 ¥1,980 のまま放置され、実価格 ¥2,480 と乖離していた事例）。価格は note 販売ページに委譲する。価格・noteUrl の SoT は `src/lib/note-magazines.ts`。

**NG → OK の例**:

- NG: `[必須科目I 模範解答集（R03〜R07）](https://note.com/dobokunote/m/m0f3bc3933454)（¥1,980）では…`
- OK:

  ```
  令和3〜7年度と令和8年度予想を収録した模範解答集です。

  https://note.com/dobokunote/m/m0f3bc3933454

  本記事の論点が、実際の答案でどう展開されるかを確認できます。
  ```

**機械検知**: `.claude/scripts/check-note-magazine-cta.mjs`（① markdown リンク形式のマガジンURL ② マガジンURL同一行の ¥ を検出）。`scripts/note-lint.mjs`（pre-commit ゲート）と `/note-prepublish-review` Phase 1 の両方から呼ばれ、コミット時に自動 BLOCK する。価格が CTA から離れた別段落にある旧来パターン（既存マガジン記事）は対象外（誤検知回避のため近接のみ）。

**もくじ index の例外**: frontmatter `noteSeries: 総合案内`（L1 総合案内・各資格 L2 もくじ）は多数マガジンを一覧する index ページのため、① markdown リンクのコンパクト列挙を許容する（note カードは bare URL でしか生成できず、12 本超を全部カード化すると index が冗長になる）。ただし ② 価格（¥）は index でも禁止（陳腐化する・note カードが実価格を表示する）。in-article CTA は「読者を 1〜2 件へ誘導」＝カード必須、index は「全件の一覧」＝リンク許容、と使い分ける。関連: §14-b（太字内全角括弧）。

**冒頭パック CTA の例外**: `<!-- cta:pack-top -->`／`cta:pack-top-light` マーカー直後のブロック（次の空行まで）は、[note-funnel-architecture.md](note-funnel-architecture.md) 原則2「冒頭はパックへ**インラインで軽く**（カード連打で読み物の信頼を損ねない）」に従い、① markdown リンクを意図的に用いるため対象外とする（末尾 `cta:{exam}-mokuji` はカード＝bare URL のまま）。ただし ② 価格（¥）は冒頭 CTA でも禁止で、価格は note 販売ページ（`src/lib/note-magazines.ts` が SoT）に委譲する。機械可読 CTA 文面の SoT は `.claude/config/note-funnel.json` の `exams.{key}.topCta.text`（価格を含めない）。

### 14-d. note 記事の「3点セット」は公開状態で機械強制する

note 記事1本の完成条件は **3点セット**: `article.md` + `img/cover.png`（アイキャッチ）+ `hashtags.txt`（タグ）。cover.png と hashtags.txt は本文執筆と別工程（`scripts/generate-note-covers.mjs` で frontmatter `cover:` ブロックを PNG 化／`/note-hashtags` でタグ生成）で後から作るため、**公開時に生成漏れが起きやすい**（2026-06-12、公開済 194 本中 2 本が `hashtags.txt` 欠落のまま公開されていた）。

**ルール**: 記事が**公開状態**（frontmatter `noteUrl` 非空 OR `noteStatus` が `publish` を含む）になったら、`img/cover.png` と `hashtags.txt` は必須。**下書き（draft）は欠落して正常**（公開直前に仕上げる工程のため）。

> [!warning] タグは「ソース」と「ライブ」の2トラック（2026-07-28 追記）
> 本節のゲートが見ているのは**ソースの `hashtags.txt`** だけ。note ライブに実際に何個入っているかは別問題で、**独立して壊れる**。2026-07-28 の実測では、ソースは 748 件すべて 90+ で完備なのに **ライブは 675 本中 250 本（37%）が 90 未満**（0タグ19本）だった。ソースだけ見ていると永遠に緑になる。
> ライブ側は `npm run check-note-live-tags`（curl 経路・週次 CI）が見る。不足は `note-sync-tags --list <対象> --commit` で差分追加（本文・有料境界は非破壊）。詳細 → [note-api-verification.md](note-api-verification.md)「タグはソースとライブの2トラック」。

**hashtags.txt は「存在」だけでなく「タグ数」も検査する**（下限 `MIN_TAGS`＝既定 40・`NOTE_MIN_HASHTAGS` で調整可）。ハッシュタグは note 検索流入の主要導線で標準は**上限 99 近くの ~90 個**（`/note-hashtags`）。だが「存在だけ」を見ていた旧ゲートを、`/note-hashtags` を実行せず**手書き最小（10 個）や templ 軽量**の `hashtags.txt` が素通りしていた（2026-07-05、civil 二次学科ライン13本が10個・まるごとLP がライブ3個で発覚。バルク公開時に per-article の `/note-hashtags` を省いたのが原因）。下限未満は 3 点セット未完として BLOCK する。バルク記事を作るワークフローは**公開前に必ず `/note-hashtags` を各記事へ回す**（~90 個生成）。

**機械検知**: `.claude/scripts/check-note-3set.mjs`。2 モードで運用する。

- `scripts/note-lint.mjs`（pre-commit）: 既定モード＝**公開状態の記事のみ** BLOCK（下書き commit は止めない）。公開状態にしたのにアセットが無いコミットを自動で止める。
- `/note-prepublish-review` Phase 1（4e）: `--require` モード＝公開意図なので**無条件必須**（公開直前は `noteUrl` 未設定のことが多く state を見ない）。

cover.png はマガジン記事の共用図 `../img/cover.png` も探索する。生成: `node scripts/generate-note-covers.mjs <slug>`（カバー）/ `/note-hashtags <slug>`（タグ）。関連: §14-c（マガジン CTA）。

### 14-e. note 記事の段落は短く（1〜2 文・~120 字以下）

note はモバイル閲覧が主体で、**1 段落が長いと読まれない**。本文の段落は **1〜2 文・~120 字以下**を目安にし、論点の切れ目で改行（空行）を入れて余白をつくる。1 段落 150〜300 字の塊は避ける（2026-06-12、建設部門入口 16 本で 402 段落中 185 段落が 120 字超だった）。

**自動化（語句を変えず改行だけ足す）**: `node scripts/reflow-note-paragraphs.mjs [--target N] <file|dir>`（`npm run note-reflow`）。長い段落を**文（。）境界**で再パッキングする決定論ツールで、語句・文意は一切変えない（空白除去後の本文一致で検証可能）。見出し・箇条書き・URL 単独行・太字見出しは対象外。`--dry` で点検のみ。**essay マガジン記事の答案本文（`## 試験問題` 以降）は自動保護**して触らない（模範答案は連続散文のため）。導入部に特化した essay 専用ツールは `scripts/split-essay-intro-paragraphs.mjs`（note-essay-review-checklist Step 3c）。

**残る長文**: `。` を含まない**単文で 120 字超**は機械分割できない（割ると語句改変になる）。これは `--dry`/公開前レビューが WARN で surface するので、**手動で 2 文に分ける**か、許容するか人が判断する。

**機械検知**: `/note-prepublish-review` Phase 1（4f）が `reflow --dry` を呼び、>120 字の段落数を **WARN**（情報提供のみ・GO 判定に影響しない）で報告する。BLOCK にしないのは、段落の切り方が編集判断（読み味）であり一律強制に馴染まないため。関連: §14-c（CTA）/ §14-d（3 点セット）。

### 15. 総監ページに教材外の実務応用セクションを追加しない

総合技術監理（pe-comprehensive-management）キーワードページには、教材『情報管理』『安全管理』『社会環境管理』『経済性管理』『人的資源管理』等の標準テキストに **書かれていない実務応用セクション**（建設現場での活用 / 業務での適用例 / 実務応用 / 現場での活用 / 建設実務での活用 / 業務での留意点 など）を独自に追加しない。

**理由**:
- 総監は 5 つの管理を **横断的・抽象的に統合する** ことが本質。建設実務の具体例を入れると **一般部門（建設）との区別が崩れる**
- 教材原典に無い内容は **過去問との整合性を欠き**、誤った知識を植え付けるリスクがある
- LLM の執筆バイアス（「抽象概念を具体例で補強する」）と doboku-note のサイト性格（土木・建設系試験対策）が誤って結合し、生成的に追加されやすい既知パターン

**例外**:
- 教材本文の事例（例: BCP の建設業の事例）が直接書かれている場合は、教材内容として記載してよい
- `civil-construction-1`（1 級土木施工管理技士）等、建設実務系資格のページでは正当な内容なのでこのルールは適用しない

**機械検知**: `lint-mdx-mobile.mjs` のルール 9-7（MEDIUM）で、`pe-comprehensive-management/` 配下の H2 タイトルに以下のパターンが含まれる場合に検知する。

```
^##\s*(建設現場|業務|実務|現場).*?(での)?(活用|適用|応用|留意点|事例)\s*$
```

**校正時の対応**: 9-7 違反を検知したら、原則として該当 H2 セクションを **削除** する。教材本文に該当事例がある場合のみ、教材どおりの内容に書き換えて維持する。

### 16. 校正時の標準チェック項目（過去問核心 Callout の有無）

「校正して」と依頼された場合、以下を **標準ルーチン** として毎回確認する。過去問逆引きカード（PastExamBacklinks）は build-time に自動注入されるが、**過去問の引っかけ論点を視覚分離する Callout は手動追加が必要** で、この差を埋める。

**手順**:

1. **過去問逆参照の有無**: `src/config/past-exam-backlinks.json` で対象キーワードを lookup
2. **過去問あり**: 該当する過去問 MDX（例: `r04-primary/article.mdx`）を読み、`<details>` 内の解説から誤答パターン・引っかけ論点を把握
3. **既存 Callout のカバレッジ確認**: 引っかけ論点が既存の `<Callout type="warn">` で警告されているか
4. **未カバー論点があれば提案**:
   - 受験者が読み飛ばすと失点する論点が未カバーなら Callout 追加候補を提案
   - **§7 準拠**: 「単なる補足」「本文で十分伝わる一般説明」レベルは追加しない、1 記事 3 個ルールを超えない
   - 過去問が無いキーワード or 引っかけ要素がない場合は「追加なし」と明示する

**コスト**: 1 ページあたり JSON lookup + 過去問 1〜2 件読み = 30〜60 秒。校正の標準フローに組み込む。

**対象**: PE keyword ページ（過去問データが揃っている）。civil-construction-1 等は構造が異なれば別途判断。

**半自動化（2026-05-11 起動）**: `/audit-exam-mapping` Skill + `exam-keyword-mapping-auditor` エージェントが、過去問 1 問の現紐づけ slug 群を semantic に評価し、追加/削除候補を confidence 付きで surface する。校正時の「過去問逆参照の lookup → 引っかけ論点把握 → Callout 追加判断」のうち、**前半 2 ステップを agent に肩代わりさせる**ことで、人間は Callout 追加判断と確認に集中できる。サンプリング監査は NotebookLM で実施（詳細は `.claude/skills/quality/audit-exam-mapping/SKILL.md`）。

### 17. 散文中心・表と図は補足

キーワードページは **散文（地の文）で概念を説明する** ことを基本とし、表・箇条書き・コンポーネントは散文の補足として後置する。教材『総監標準テキスト』（`docs/textbook/技術士（総監）/テキスト/総監標準テキスト/`）が散文 60〜65%／表・箇条書き 30〜35% のバランスで構成されており、この比率を doboku-note のキーワードページでも目標とする。

**理由**:
- 概念の理解は文脈の中で起こる。表だけを読んでも「なぜそうなるか」「どう使われるか」がわからず、試験本番の応用問題に対応できない
- LLM 生成物は「表で要約しがち」というバイアスを持つ。明示しないと散文薄＋表依存に偏る
- 散文薄ページは末尾の `<ExamPoint>` `<RelatedKeywords>` だけが目立ち、本文との重みバランスが崩れる（§18 と相互依存）

**ルール**:

1. **「○○とは」セクション**: 散文 2〜3 段落（目安 200 字以上）で概念定義・対象範囲・基本仕組みを説明する。1 段落で済ませない
2. **各 H2 セクション**: 最低 1 段落の散文導入を必須とする（§2「表の前に文脈」の発展）。H2 直下に表・箇条書き・コンポーネントから始めない。**1 セクションの散文量は 200〜400 字（理想 250〜350 字）を目安**とし、これを大きく下回るセクションは概念説明が薄い兆候（§24 の文長ルールと併用して読みやすさを担保する）
3. **散文比率**: 1 記事全体で散文行 60% 以上を目安。散文行とは「通常の Markdown 段落で、表行・箇条書き行・コードブロック・JSX タグ単独行以外」を指す
4. **表・箇条書き・図は補足**: 散文で概念を説明したあと、構造化された情報（比較・分類・段階）を整理するために用いる
5. **コンポーネント（ExamPoint・SeeAlso 等）は本文の補強**: 散文を置き換える存在ではない。本文が薄いままコンポーネントだけで補おうとしない

**ベンチマーク**:
- 教材原典: `docs/textbook/技術士（総監）/テキスト/総監標準テキスト/安全管理.md`（各概念に 2〜4 段落の散文）
- タイプ B 模範: `.local/r2/posts/pe-comprehensive-management/business-continuity-plan/article.mdx`、`cash-flow-statement/article.mdx`、`alps-treated-water/article.mdx`
- タイプ A 反例（散文薄＋表依存）: `pdca-cycle/article.mdx`（58 行）、`four-m-of-production/article.mdx`（53 行）

**機械検知（カテゴリ 12、警告レベル）**:
- 12-1 LOW: 全体散文密度 < 0.5
- 12-2 LOW: H2 セクション内に散文 0 行（表・箇条書きのみで構成）
- 12-3 MEDIUM: コンポーネント末尾塊化（§18 と連動）

**校正時の対応**: 12-1/12-2 違反を検知したら、教材スタイルに沿って散文を厚くする。§15 教材外実務応用 H2 を新設してはならない（散文は既存セクション内で増やす）。

### 18. 末尾コンポーネント塊化の禁止

`<SeeAlso>` `<ExamPoint>` `<RelatedKeywords>` などのコンポーネントを記事末尾にまとめて並べない。**末尾の標準パターンは `<ExamPoint>` + `<RelatedKeywords>` の 2 点のみ**で、それ以外は本文中の適切な位置に配置する。

**理由**:
- 末尾に 3 件以上のコンポーネントが連続すると本文との重みバランスが崩れ、読了時に「結局この記事は何を言いたかったのか」がぼやける
- 末尾肥大化は **本文の散文不足のサイン**（§17 と相互依存）。コンポーネントを末尾に並べたくなったら、まず散文を厚くするか、コンポーネントを本文中に分散できないか検討する

**ルール**:

1. **`<SeeAlso>` は本文中（言及した直後）に配置**（§11「本文中で別ページへ強く誘導したい時」の徹底）。末尾配置は反パターン
2. **`<ExamPoint>` は「総合技術監理における位置づけ」セクション末尾に 1 個**（§5）
3. **`<RelatedKeywords>` は最後のコンテンツセクション末尾、`## 参考資料` の前**（§11）
4. **`<Callout>` は引っかけ論点に紐づく場所**（§7）

**反パターン例**（避けるべき末尾構造）:

```
本文 H2 セクション群（薄い）

## 総合技術監理における位置づけ
[2-3 段落]

<SeeAlso ... />        ← 本文中ではなく末尾に置いている
<ExamPoint ... />
<RelatedKeywords ... />

## 参考資料
```

**正パターン例**:

```
本文 H2 セクション群（散文中心、§17 準拠）

## 総合技術監理における位置づけ
[段落 1]

[段落 2 ＝ 関連トピックに言及]

<SeeAlso ... />        ← 関連トピックの直後

[段落 3 ＝ 5 管理視点]

<ExamPoint ... />
<RelatedKeywords ... />

## 参考資料
```

**機械検知**: `lint-mdx-mobile.mjs` カテゴリ 12-3（MEDIUM、警告レベル）で、コンポーネント 3 件以上の連続を検知する。

**校正時の対応**: 12-3 違反を検知したら、SeeAlso を本文中の関連トピック直後に移動する。それで解消しなければ本文の散文を厚くして、コンポーネントが「総括」として機能する位置関係を作る。

### 19. 5管理トレードオフ段落は機械的に追加しない

「総合技術監理における位置づけ」セクション内に **5管理トレードオフ**（経済性／人的資源／情報／安全／社会環境の各観点で当該キーワードの限界・矛盾を整理する段落）を入れるかは、キーワードごとに判断する。**以下の 3 条件を全て満たすキーワードにのみ記載** し、満たさないキーワードには書かない（形骸化・段落水増しの原因となる）。

**適用条件**（全て満たす必要あり）:

- **条件 A**: 過去問が複数の管理軸にまたがる論点でそのキーワードを問うている、または受験参考書がトレードオフ視点で言及している
- **条件 B**: 4-5 軸のうち少なくとも 2 軸で**具体的・固有なトレードオフ**が書ける（「短期業績偏重で長期投資が削られる」のように、そのキーワードでなければ成立しない論点）
- **条件 C**: キーワード自体が 5 管理のいずれか 1 つに完全に属するわけではない（横断的な手法・概念）

**書き方**:

- 4-5 軸全てを並列で書かない。**最も尖った 1-2 軸を散文で深掘り**する
- 「○○管理との関係では…」を 5 個並べる「定型ヘッダー羅列」は禁止（段落水増し）
- トレードオフは「○○を導入すると××が起きる」と因果で記述する。抽象論（「バランスが重要」「総合的に判断」）にしない
- 過去問・実務事例で実証されないトレードオフは書かない

**該当しない例**（5管理段落を書かないキーワード）:

- 5 管理のいずれかに完全に属する: [安全管理](/docs/pe-comprehensive-management-safety-control)、[経済性管理](/docs/pe-comprehensive-management-economy-control) 等（自己言及で循環する）
- 特定領域に閉じた専門用語: 個別の安全基準名、特定指標の計算式、法令の細目条文
- 横断性が乏しい技術的概念: 暗号方式、特定アルゴリズム、規格番号

**該当する例**（5管理段落を書くキーワード）:

- 人事評価制度全般（[目標管理制度（MBO）](/docs/pe-comprehensive-management-mbo)、[能力考課](/docs/pe-comprehensive-management-competency-evaluation)）— 短期業績 vs 長期投資、SMART と数値化困難業務など具体的トレードオフが書ける
- プロジェクトマネジメント手法（[アジャイル](/docs/pe-comprehensive-management-agile)・[ウォーターフォール](/docs/pe-comprehensive-management-waterfall) など）— スピード vs 品質保証、ドキュメント vs 適応性
- 横断的な経営概念（[PDCA サイクル](/docs/pe-comprehensive-management-pdca-cycle)、[SDGs](/docs/pe-comprehensive-management-sdgs) など）— 部分最適 vs 全体最適、短期 KPI vs 長期持続可能性

**判定の自己チェック**: 5管理段落を書こうとしたとき、「○○管理：[抽象論]」しか思い浮かばない軸は省く。残った 1-2 軸を散文で 200-400 字に深掘りする方が、4-5 軸並列の 1,000 字より学習価値が高い。

### 20. ガイド記事の末尾構成（group: guide 専用）

**スコープ宣言**: §5 / §6 / §12 / §17 末尾標準パターン / §18 / §19 は **キーワードページ（`group: keyword` または group 未設定）の構造ルール** である。`group: guide` のガイド記事には適用しない。ガイド記事は受験戦略・学習計画・俯瞰ハブを担う **コンバージョン地点** であり、外部離脱（公的資料リンク）を意図的に最小化する。

**ガイド記事で使ってはいけないセクション**:

- `## 総合技術監理における位置づけ` — キーワードページ専用。試験文脈はガイド本文の散文に統合する
- `## 参考資料` / `## 参考文献` — キーワードページ専用。外部離脱を生むため末尾に置かない。本文展開で公式リソースを引用する場合はインラインリンクで言及する

**ガイド末尾の標準パターン**（記事性質で 2 型を使い分け）:

**Type-1「○○の選択肢」型**（戦略・実務手順系）— note 強誘導:

- 該当例: `essay-exam-strategy`（記述式対策の選択肢）、`exam-application-guide`（業務経歴票添削の選択肢）、`exam-passing-strategy`
- 末尾セクション名: `## ○○の選択肢`
- 構成: 散文 1〜2 段落で「読者の次の意思決定」を提示 → サイト内 1〜2 件 + note 有料コンテンツリンクカード（URL 単独行、`feedback_note_link_card` 準拠）
- 目的: 学習プランをサイト無料 + note 有料の組み合わせで完成させる導線

**Type-2「次のステップ」または「関連リソース」型**（俯瞰・分析系）— サイト内回遊 + note 補足:

- 該当例: `r8-essay-keyword-forecast`（候補テーマ俯瞰）、`whitepaper-study-map`（白書マップ）、`management-tradeoffs`（5 管理間トレードオフ思考フレーム）
- 末尾セクション名: `## 次のステップ` または `## 関連リソース`（既存表記に合わせる）
- 構成: **散文 1 段落で「読者の状況別にどう選ぶか」の判断軸を明示** → **`<SeeAlso>` 1〜2 件のみ**（主推奨 + 副推奨の二段構え、各カードの `reason` で「なぜそのページを次に読むべきか」を 1〜2 行で説明）
- 該当する場合は note リンクカード（URL 単独行）を追加
- **`<RelatedKeywords>` は末尾に置かない**（次のステップと完全重複しやすく、選択肢過多で決定疲れを生む — 2026-05-18 改訂）
- 目的: サイト内回遊率を上げつつ、note 有料コンテンツへの補足導線を持つ。**読者が「次の 1 つの行動」を即決できる構造**を最優先

**なぜ `<SeeAlso>` 1〜2 件か**:

- ガイド記事の役割は「読者の選択肢を減らす」こと。末尾で選択肢を増やすのはハブ機能と矛盾
- 箇条書き 3〜5 件 + `<RelatedKeywords>` 5 件 = 実質 8〜10 個の選択肢になり、決定疲れで読者がどこにも進まなくなる（Iyengar & Lepper のジャム研究）
- 同じ slug が箇条書きと `<RelatedKeywords>` で重複表示されると認知負荷が増える純粋な冗長
- `<SeeAlso>` は `reason` フィールドで「なぜ次に読むべきか」を明示できるため、読者の意思決定を能動的に支援する

**ハブ記事の例外パターン**:

- 該当例: ハブ機能そのものが記事の主要価値である場合（例: 多数の関連記事への分野別ナビゲーションが本質）
- 「テーマ別深掘り」「分野別深掘り」など **ハブ機能そのものが記事の主要価値** である場合は、ハブセクション（例: `## テーマ別深掘り`）を別途設け、3〜7 件の箇条書きナビゲーションを維持してよい
- ただし「次のステップ」セクションとは **明確に分離**する（ハブナビゲーション ≠ 学習導線推奨）
- 「次のステップ」自体は依然として `<SeeAlso>` 1〜2 件に絞る

**模範論文記事の例外パターン**:

- 該当例: `pattern-essay-*`（3 ペルソナ別ハブ）、`r0X-essay-*`（年度 × ペルソナ別）、`essay-pattern-cross-year-application`（1 パターン × 複数年度流用）
- これらは「ペルソナ → 同一年度別ペルソナ → 公式過去問」の三段ナビゲーション機能が記事の主要価値であり、`<SeeAlso>` 3〜5 件を許容
- セクション名は `## 関連リソース` でよい（学習導線が「次の 1 つ」ではなく「複数の比較対象」として構造化されているため）
- ただし内容は依然として「機能ごとに 1 件の SeeAlso」を保ち、同一機能の SeeAlso 重複は避ける

**俯瞰・分析系ガイドとの区別**:

- 俯瞰・分析系ガイド（`r8-essay-keyword-forecast` / `whitepaper-study-map` / `management-tradeoffs` 等）は「次の 1 つの行動」を読者に決めさせる → `<SeeAlso>` 1〜2 件 + 「次のステップ」セクション名
- 模範論文記事（上記）は「複数の比較対象」を提示するハブ機能 → `<SeeAlso>` 3〜5 件 + 「関連リソース」セクション名

校正観点として「**列挙の意図**」を自問する。読者に「次の 1 つを選んで進んで」と促すなら 1〜2 件、「複数を比較して自分に合うものを選んで」と促すなら 3〜5 件。前者で 3 件以上になっていたら過剰選択肢の可能性が高い。

**機械検知**: `lint-mdx-mobile.mjs` カテゴリ 12 で検出する。

- **12-1 MEDIUM**: `group: guide` で `## 総合技術監理における位置づけ` を検出
- **12-2 MEDIUM**: `group: guide` で `## 参考資料` または `## 参考文献` を検出
- **12-3 LOW**: `group: guide` で末尾 H2 が `関連リソース` / `次のステップ` / `〇〇の選択肢` 以外（推奨パターン外）

**校正時の対応**: 12-1 / 12-2 違反を検知したら本セクションの該当する Type を選んで末尾を再構成する。Type 判定で迷ったら記事タイトル末尾で判断する（「戦略」「計画」「手順」「ガイド」→ Type-1、「予測」「分析」「俯瞰」「マップ」「トレードオフ」→ Type-2）。

**過剰選択肢の自己チェック**（Type-2 改訂後の校正観点）: 末尾の `## 次のステップ` 配下に箇条書き 3 件以上 + `<RelatedKeywords>` 5 件の旧パターン構成を見つけたら、`<SeeAlso>` 1〜2 件 + `<RelatedKeywords>` 削除の新パターンに修正する。両方を残さない（重複と決定疲れの原因）。ハブ機能を持つ記事は「ハブセクション + 次のステップ」の二段構成に分離する。

### 22. インライン出典（factual table・段落直下に出典リンク）

数値・年度・固有名詞・法令条文番号・指定数・罰則金額等の **verifiable claim** を含む table または段落の直下に、`<Callout type="reference" title="出典">` 形式で出典リンクを配置する。

**適用範囲（2026-06-21 確定）**: キーワードページ・過去問・textbook が対象。**`group: guide` のガイド記事は対象外＝出典不要**。ガイドは受験戦略・俯瞰ハブを担うコンバージョン地点で、外部離脱を意図的に最小化する方針（§20）のため、factual table に出典 Callout を付けない。機械検知 `lint-mdx-mobile.mjs` 14-1 も group: guide を除外する。

```mdx
| 指標 | 値 | 評価 |
|---|---|---|
| ... | ... | ... |

<Callout type="reference" title="出典">
[タイトル（機関）](URL) / [タイトル2（機関）](URL)
</Callout>
```

**書式の変更履歴**: 2026-04-25 公式化時点では blockquote 形式 `> 出典: ...` を採用していたが、視覚的な弱さ（generic quote と区別がつかない）から 2026-05-27 に `<Callout type="reference">` へ統一。Link2 アイコン + slate トーンで「参考文献誘導」の意味論と一致させた。既存 17 ページは migration script で一括変換済み。

**§12（footer §9 参考資料）との役割分担**:
- 本節（§22）: ピンポイント検証用、特定の数値・年代がどの一次ソース由来かを明示
- §12（footer）: ページ全体の主要参考資料、公的＋民間 各 1 件以上を最低構成として満たす
- **footer と URL が完全一致するインライン出典は置かない（2026-06-08 改訂）**。footer 参考資料は記事末に `<ExternalReferences>` カードとして抽出表示されるため、同一 URL を本文中にも出すと視覚的に二重表示になり冗長。インライン出典が価値を持つのは、その URL が footer の概要リンクより **粒度が細かい一次ソース**（特定の白書ページ・条文ページ・統計表 URL 等）で、かつ footer に載っていないときに限る。footer に載せるべき主要ソースと同じ URL を引きたい場合は、インライン出典を足さず footer 側に集約する

**適用対象**:
- 数値・年度を含む factual table（人口・排出量・指定数・参加国数等）
- 法令条文番号・罰則金額を含む段落
- 国際合意の採択年・発効年・批准国数を含む散文段落
- 統計データを引用した比較表

**適用しない**:
- 概念定義のみの表（メリット・デメリット等の評価表）
- ExamPoint items（短いので本文/footer に集約）
- 散文中の一般的記述（数値・年代を含まないもの）

**禁止事項**:
- 教科書（総監標準テキスト等）を出典として書かない（§12 書籍禁止と整合、Pattern H と同じ規律）
- 出典 URL は WebFetch で実在確認してから記載（dead link 防止）
- インライン出典を増やすために本文記述を細切れに装飾しない（散文中心 §17 の精神を維持）

**lint（cem-qa による自動検知）**:
- カテゴリ 14（インライン出典）: verifiable claim を含む table・段落の直下に、**footer 参考資料に載っていない固有の一次ソース URL** があるのに `<Callout type="reference" title="出典">` で示していない場合のみ MEDIUM 違反。footer と同一 URL しか引けない claim は指摘対象外（インライン出典は不要）
- カテゴリ 14R（重複インライン出典・2026-06-08 追加）: インライン出典の URL が全て footer 参考資料に含まれる場合、冗長として MEDIUM 違反（削除を提案）
- lint 9-x（強制降格）対象外、関連付け軸または参考資料軸の判定材料として使用

### 23. 管理間トレードオフ記述の構造ルール（横断ガイド記事専用、2026-05-28 追加）

横断ガイド記事（`management-tradeoffs` 等）の `### {管理A}×{管理B}` H3 内で 5 管理間トレードオフを記述するときの構造ルール。**個別キーワードページの 5 管理段落は §19 で別途規定**、本 §23 は横断ガイド記事のトレードオフ章を対象とする。

#### 23.1 管理間トレードオフ ≠ 解決策の選択肢

管理間トレードオフとは **2 つの管理それぞれの「核となる目標」が同じ局面で対称的に衝突する** 構造を指す。解決手段の二極化（「事後保全 vs 予防保全」など）は **トレードオフを解決する一つの分岐** であり、トレードオフそのものではない。

**正例**:

> 経済性管理は「コスト・工期・原価の最適化」、安全管理は「人命・健康・第三者影響の回避」を核とし、両者は同じ局面で頻繁に衝突する。安全水準を上げれば対策費・維持管理費が増えて経済性が悪化し、コストを抑えれば事故・健康被害リスクが上昇するという対称的ジレンマである。

**反例**（解決策の二極化をトレードオフと書く）:

> 事後保全に偏れば突発的な重大事故が起き、一律予防保全に踏み込めば予算枠が破綻する、という対称的ジレンマである。

反例は「事後保全 vs 一律予防保全」という **解決手段の選択肢の対立** を書いており、経済性管理と安全管理の **核と核の対称関係を直接記述していない**。受験生がこのまま論文化すると、「経済性 vs 安全」を論じているはずが「保全方式の選択」の議論に滑ってしまう。

#### 23.2 5 管理の核（対立構造化の参照軸）

| 管理 | 核となる目標 |
|---|---|
| **経済性管理** | コスト・工期・原価・収益の最適化 |
| **人的資源管理** | 労働力の確保・育成、労働環境の改善、モラール |
| **情報管理** | 情報の機密性・完全性・可用性（CIA）、業務効率化 |
| **安全管理** | 人命・健康・第三者影響の回避、労働安全 |
| **社会環境管理** | 環境保全・景観・地域合意・社会受容性 |

H3 散文の冒頭で「{管理A} は…、{管理B} は…を核とし、両者は…で衝突する」と **核同士の対称関係を 1 文で宣言** することを推奨する。

#### 23.3 構造（4 ブロック）

各 H3 内は次の順序で構成する：

1. **対立構造化** — 散文 1 段落（核同士の対称関係＋具体場面の枚挙、過去問接続）
2. **具体的なトレードオフ** — 散文 1 段落（何と何が両立しないか、評価軸は散文に内在化）
3. **解決策の組み合わせ** — 散文 1 段落で **複数の方向性**（標準形＋制約条件別の派生形 2-3 案）を並列提示
4. **SpecSheetList** — 解決フレームのメニュー（4〜6 個）、タイトル末尾に **「2〜3 個を組み合わせる」** と明示

評価軸の独立段落（「評価軸は X 対 Y の二軸で立てる」のような メタ解説）は **作らない**。評価軸の感覚は具体的トレードオフ段落の散文に内在化させる。受験生が答案でメタ解説を書く時間的余裕は少なく、構造としても重い。

#### 23.4 受験参考用途のスコープ

横断ガイド記事は **記述式答案の参考フレームを提供する** ことが目的。以下は意図的に **入れない**：

- **固有事業名**: 特定の国家施策名（i-Construction 2.0、CCUS、群マネ、PLATEAU、ウォーターPPP、流域治水プロジェクト2.0 等）
- **特定インシデント**: 八潮市陥没事故、成瀬ダム自動施工、豊田市衛星調査、福島県平田村「橋ログ」等
- **特定数値**: 「30% 縮減」「18.1 万人受入」「6 兆円」など年度・地域に紐づく具体数値
- **白書名の直接引用**: 「令和7年版国土交通白書によれば…」「特集『○○』では…」

**理由**:

- 受験生は答案で **自分の業務経験から具体例を出す** 立場にある。サイト側が特定事例を挙げると、受験生の事例選択肢を狭めてしまう
- 固有事業名・特定数値は **年度更新で陳腐化** する。総監フレームレベルの記述は数年単位で安定する
- 試験で問われるのは **思考の型（フレームの組み合わせ）** であり、特定事例の暗記ではない

**入れてよい**: 総監キーワード集の語彙レベル（ALARP、RBM、LCA、ミティゲーション階層、PoC、PI、合意形成、勤務間インターバル、CIA 三属性、PPP/PFI、VFM、人的資本投資 等）。これらは普遍的な総監フレームの名前であり、固有事例ではない。

#### 23.5 解決策は単独でなく組み合わせる

論文の骨格は単独フレームではなく **2-3 フレームの直列・並列** で組み立てる。SpecSheetList のタイトルに「2〜3 個を組み合わせる」と明示し、メニュー的に使う意図を伝える。代表的な組み合わせの例は散文中で示す（例: 「①リスクベース判断 → ②ALARP → ③残余リスク監視 の三層構造」「制約条件が技術職員不足なら 広域連携・PPP/PFI の方向、単年度予算枠が制約なら段階的実施・予算平準化の方向」）。

#### 23.6 残余リスク監視で締める

管理間トレードオフ章の末尾、または記事全体の末尾（既存の「論文締めの定型」セクション）で **残余リスクの監視体制** を明示する。完全な解消は不可能という総監的前提を提示し、KPI・閾値・フィードバック体制を 1〜2 文で記述する。

#### 23.7 機械検知（cem-qa による評価）

横断トレードオフ記事の各 `### {管理A}×{管理B}` H3 内で以下を検査する：

- **23-1 HIGH**: 散文に「{管理A} は…、{管理B} は…を核とし」の核同士の対称関係宣言がない（解決策の二極化のみで書かれている）
- **23-2 HIGH**: 固有事業名・特定インシデント・特定数値が散文に混入（§23.4 違反）
- **23-3 MEDIUM**: 解決フレームが SpecSheetList で 3 個未満（複数組合せの選択肢が薄い）
- **23-4 LOW**: SpecSheetList のタイトルに「組み合わせる」「メニュー」等の意図表現がない
- **23-5 MEDIUM**: 評価軸の独立段落（「評価軸は X 対 Y の二軸で立てる」型のメタ解説）が H3 内に存在する（§23.3 違反）

違反検知時は原則軸を 2 点以下に減点する。

#### 23.8 適用範囲

- **対象**: 横断ガイド記事の 5 管理間トレードオフ章（`management-tradeoffs` 等）
- **対象外**:
  - 個別キーワードページの「総合技術監理における位置づけ」内 5 管理段落 → **§19** を適用
  - 個別キーワードページ自体の構造 → §17-18 を適用
  - 模範論文（`docs/note/magazines/総監模範論文-*/`） → 「note 模範論文の品質原則」を適用

### 24. 文体: 1 文の長さと文末の単調回避（2026-06-16 追加）

モバイル可読性（§3）と読み味のための文体ルール。地の文（散文）にのみ適用し、見出し・表セル・箇条書き・`<ExamPoint>` 等のコンポーネント・コード・数式は対象外（§3 と同じ適用範囲）。

**① 1 文の長さは 60〜80 字を目安**にする（編集画面で 1 行半に収まる長さ）。ただし**ハードルールではない** — 法令・技術概念の定義文（例:「変形労働時間制度とは…週 40 時間を超えない範囲で…制度である」）は一文に要件を畳み込む必要があり、100 字前後まで許容する。句点で自然に切れる箇所があれば 2 文に割る。

- 機械検知: `lint-mdx-mobile.mjs` **15-2（LOW）**。句点区切りで **140 字超**の散文を「明らかな長文」として surface する（60〜80 字の目安より緩く取るのは、定義文の正当な長文を誤検知しないため）

**③ 同じ文末を 3 文以上連続させない**。「〜です。〜です。〜です。」のように丁寧体の語尾が単調に続くと、コーチング系の散文（ですます調のガイド）が稚拙・AI 的に読める。語尾に変化をつける（「〜です」「〜ます」「〜でしょう」「体言止め」等を混ぜる）。

- 機械検知: `lint-mdx-mobile.mjs` **15-1（MEDIUM）**。**丁寧体（です／ます／ました）が 3 文連続**したときのみ surface する
- **である調（常体）は対象外**: キーワードページ・教科書・択一解説の「〜である。〜する。〜た。」の連続は学術的な技術文として許容される。機械強制すると大量の誤検知になるため、である調の文末反復は編集者判断に委ねる（冒頭「文体ルール」の である調／ですます調 使い分けと整合）

**機械化しない関連ガイドライン（執筆・校正時の心得として保持）**:

- **② ひらがな・カタカナ・漢字・数字のバランス** — 良い心得だが機械判定に馴染まない。試験用語は漢字密度が高くて当然で、無理に薄めない
- **④ 見出し 2 に狙うキーワードを含める** — 本サイトの見出しは元来キーワードを含む（「変形労働時間制度とは」「変形労働時間制度の種類」）ため自然に充足。SEO 面は H1 自動生成＋`seoTitle` で別途処理。無理な詰め込みは §3.5（見出し＝TOC 識別子）と衝突するため避ける
- **⑤ 見出し内 200〜400 字** — §17 ルール 2 に統合済み
- **⑥ PREP 法（結論→理由→具体例→結論）** — §1「冒頭で本質を簡潔に」が結論ファーストを実装済み。「〜とは」が結論（P）に相当
- **⑦ 文字色装飾は 1 見出し 2 個まで／⑧ 装飾は中央・最下部／⑨ 装飾の種類を絞る** — 本サイトはインライン文字色を使わず、意味を持つ `<Callout>`（12 種）と太字で表現する。装飾の抑制は §7「過剰装飾を避ける」・§7.1（5 判定基準）、配置は §2/§8「装飾の直前に文脈（導入文）を置く」が、それぞれより教育的な形で実装済み
- **⑩ 画像 alt（代替テキスト）の設定** — §8 で `<ArticleImage>` の alt 運用として必須化済み（alt は説明、caption は出典のみ）

## コンテンツ品質レベル（L1 / L2 / L3）

コンテンツの品質を3層に分け、対象ごとに到達すべきレベルを明確にする。すべてのコンテンツにL3を求めない。

### L1: 構造品質（全コンテンツで必須）

原文に忠実な情報が、正しいフォーマットで格納されていること。

- frontmatter（title, seoTitle, description, category, tags, published）が正確
- 文字化け（U+FFFD）がない
- MDX構文エラーがない
- 設問番号・選択肢が原文に忠実
- コンポーネント（Callout, ExamPoint等）が正しく使われている

**L1を満たさないコンテンツはpublished: falseにする。**

### L2: 学習品質（主要コンテンツで実現）

読者が「読んで理解し、試験対策に使える」状態。

- 正答・解説が付いている（過去問）
- ExamPointで試験頻出ポイントが明示されている
- RelatedKeywordsで関連ページへの双方向リンクがある
- モバイルでの視認性が確保されている（表の適切性、段落分割）
- 本ファイルのコンテンツ原則1〜8に準拠している

### L3: 体験品質（特定コンテンツに集中）

「ここだけで合格できる」と感じさせる体験。

- 図版・数式が原文と同等に再現されている
- 分野横断の出題傾向分析がある
- 学習の導線が設計されている（次に読むべきページが明確）
- ベンチマークページ（BCP）と同等以上の品質

### 25. ガイド記事の本文ボリューム下限（group: guide 専用、2026-06-21 追加）

**ルール**: `group: guide` のガイド記事は **本文（frontmatter を除く、空白除去後）3,000 字以上** を必須下限とする。3,000 字に満たないガイド記事は「薄い記事（thin content）」とみなし、公開品質を満たさない。

**なぜ 3,000 字か**:

- ガイド記事は検索流入の入口かつ note 有料コンテンツへのコンバージョン地点（§20）であり、読者の意思決定を支えるには各 H2 セクションに §17（散文量 200〜400 字／セクション）を満たす実体が要る。H2 が 5〜8 個並ぶ標準的なガイドで各セクションが下限を満たせば、自然に 3,000 字を超える
- 3,000 字を下回るのは、概念説明が箇条書き・表・Callout に逃げて散文が痩せている兆候。§17-5「本文が薄いままコンポーネントだけで補おうとしない」の定量的な歯止め

**適用範囲**: `group: guide` のみ。**過去問（`group: primary` / `secondary`）・キーワードページ・textbook には適用しない**（§5 §188 の図表中心ページ例外を侵さない）。

**機械検知（ゲート）**: `node scripts/check-guide-length.mjs`（`npm run check-guide-length`）。published かつ `group: guide` の記事本文が 3,000 字未満なら **赤落ち（exit 1）**。pre-commit は staged のガイド MDX のみ、CI（`r2-audit.yml`）は全 published を検査する。**どちらも未公開（`published: false`）は対象外**——撤回済み記事の誤字修正まで commit が弾かれるのを避けるため（2026-08-04 に staged 側だけ published を見ておらず、unpublish 済み記事の太字修正がブロックされた）。

**加筆の方向性**: 字数合わせの水増しではなく、§17 に沿って各 H2 セクションの散文導入を 200〜400 字へ充実させ、読者の判断に効く具体（数値・体験・選択基準）を足す。加筆後は `guide-qa`（ガイド軸 5 軸）で再確認する。

> **重要（2026-06-21）**: この 3,000 字ゲートは「薄い記事」を粗く弾くフィルタにすぎず、**質を保証しない**。実際、ヘッジ語（「〜でしょう」等）の水増しで字数は容易に稼げる（A/B で Opus が密度を上げると逆に字数が減り下限を割った）。**質の本当の番人は字数でなく `guide-qa` の 5 軸**。さらに、加筆で足した試験統計・制度の事実は LLM（Opus 含む）が高頻度で誤るため、公開前に WebSearch で一次情報照合する（§ガイド記事の事実検証）。

### 26. ガイド記事の導入（リード文）の型（group: guide 専用、2026-06-21 追加）

**スコープ**: `group: guide` のガイド記事の **冒頭リード文**（最初の H2 より前の地の文）。§1「冒頭で概念の本質を簡潔に」は **キーワードページ（である調・概念定義ファースト）** の型であり、ガイド（ですます調・検索流入の入口・コンバージョン地点）には別の型を使う。

**ルール**: ガイド冒頭は **読者ベネフィット型リード**で始める。次の 3 要素を 2〜4 段落（各 1〜2 文）で順に置く:

1. **共感・問題提起**: 読者が抱える悩み・つまずきを 1 文で言い当てる（例:「施工管理はきついと聞くけれど、実際どうなのか不安ですよね」）
2. **この記事でわかること**: 記事を読むと何が解決するか・何が得られるかを示す（箇条書きにせず散文で。箇条書きにするなら導入文を 1 文置いてから）
3. **結論の方向性**: 記事全体の結論を一言先出しする（PREP の P＝結論ファースト。§24 ⑥と整合）

**禁止**:

- **冒頭をいきなり `<Callout>` で始めない**（§7.1 / L303）。「この記事の使い方」「関連記事一覧」程度の案内は Callout でなくリード文の散文に溶かす。Callout が正当なのは商業 CTA・致命的警告（type="danger"）など本文と別レイヤーの誘導のみ
- **リード文の直後にいきなり H2 → 箇条書き/表/図** を置かない（§2 / §17-2、機械検知 6-2/6-3/6-4）

**出典・背景**: ブログ記事構成の一般的なベストプラクティス（読者の悩み→ベネフィット提示→結論ファースト）。参考は `docs/todo/reference-sites.md`「たけの副業ロード」の記事構成テンプレ。本サイト既存の §1（結論ファースト）・§24 ⑥（PREP）・§7.1（装飾抑制）と矛盾しないガイド特化の入口型として追加。

## note 模範論文（総監記述式）の品質原則

`docs/note/magazines/総監模範論文-*/` および `docs/note/magazines/総監記述式-R8予想問題集/` 配下のフル模範論文を書く・校正するときに従う 5 原則。**最初に原則 0（字数制約）で評価し、字数を整えてから他の原則に進む**。R7 同ペルソナ模範論文と並列比較してから着手する。

### 0. 字数制約（最優先・厳守）

答案用紙は 24 字 × 25 行 = **600 字/枚**。設問ごとの枚数指定は**厳密な上限**で、許容範囲は存在しない。

| 設問 | 枚数 | 上限（厳守） | マージン考慮の目標値 |
|---|---|---|---|
| 設問(1) | 1 枚以内 | **600 字** | 585〜600 字 |
| 設問(2) | 各組合せ 1 枚以内 × 2 | **各施策 600 字 / 計 1,200 字** | 各施策 585〜600 字 |
| 設問(3) | 各組合せ 1 枚以内 × 2 | **各施策 600 字 / 計 1,200 字** | 各施策 585〜600 字 |
| **合計** |  | **3,000 字** | **2,925〜3,000 字** |

**R7 A案も 619 / 578 / 618 / 624 / 657 字と微〜やや超過しており、R7 を基準にすると 600 字超を許容してしまう**。R7 A案は超過例として参考にせず、新規執筆・既存校正は 600 字以内厳守で評価する。

**レビュー手順**：内容質の議論より先に **必ず字数を実測** し、600 字を超える施策があれば「まず圧縮、その後に内容質を議論」と順序を宣言する。字数評価を後回しにすると、内容質を上げた後に大幅圧縮が必要となり、書き直しが何度も発生する。

**字数計測スクリプト**:
```python
import re
def count_between(path, start, end):
    with open(path, encoding='utf-8') as f:
        text = f.read()
    s = text.find(start); e = text.find(end, s+1) if end else len(text)
    body = re.sub(r'[#*`\-|\[\]()>]+', '', text[s:e])
    return len(re.sub(r'\s+', '', body))
```

### 1. 設問(2) は散文化（箇条書き禁止）

「**内容**: ... **根拠**: ... **効果**: ...」のような bold ヘッダ＋箇条書きにしない。R7 同ペルソナ模範論文（`docs/note/magazines/総監模範論文-*/R07/article.md`）と同じ、流れる散文段落へ統合する。

- 良い例: 「内容として〜。〜することで〜（根拠）。効果として〜（経済性管理）、〜（情報管理）。」と 1 段落で書く
- 悪い例: `- **内容**: ...` `- **根拠**: ...` `- **効果**: ...` の箇条書き
- 「**障害と克服策（トレードオフ）**」も同様。「障害として〜（**A × B** のトレードオフ）。克服策として〜」と散文段落で書く

理由: 本番の答案用紙は手書きの散文で書くもの。模範論文を箇条書きで提示すると、読者が自分の答案構造を組み立てる際の参考にならない。

### 2. 設問(3) は一般技術者レベル

設問(3)（事業や組織の枠を超えた国レベル施策）は、一般技術者なら自分の言葉で書けるレベルに揃える。法制度設計・ICT サプライチェーン管理の専門用語は避ける。

- 避ける語彙: EU AI Act、第三者認証制度、AI-SBOM、ソフトウェア SBOM 国際標準、基盤モデル、リスクベース規制、サプライチェーンリスク評価、認証要件法制化
- 使う語彙: リスクに応じた規制、定期見直し条項、監督権限の集約、人材育成、社会受容性、代替チャネル、救済制度、透明化、研修体系
- 構成: 規制側施策 1 つ＋人材／社会受容性側施策 1 つで規制と社会の両輪を確保（R7 A案の「労働力確保＋社会保障改革」と同型）
- トレードオフ: 経 × 情・人 × 経・社 × 経 など、5 管理間の一般的な対立軸で立てる

理由: 設問(3) は受験者が業務経験を踏まえて書くもの。法学・ICT サプライチェーンの専門知識を前提にすると「自分には書けない論文」になる。

### 3. ペルソナの立場ラベルはシンプルに

立場ラベル（例: 道路維持課 課長補佐）はシンプルな肩書きに留める。「(情報化・DX 担当)」「(サイバーセキュリティ統括)」のような兼務付与は禁止。

- 越権施策の典型: 「ゼロトラスト移行」「庁内ネットワーク全面整備」「全庁 CIO 部局への提案」などを**自前実施**として書いてしまう
- 他部局所掌に踏み込む施策を書きたい場合: 「CIO 部局と連携して〜」「情報政策課と協議のうえ〜」と所掌調整の枠組みで書く（自前実施にしない）

理由: 立場を盛ると現実の組織で動けない施策が並び、採点者から「監理対象が曖昧」「役職と施策のスケールが合っていない」と判断される。

### 4. 白書根拠は章構成と原表現を WebSearch で確認

「令和7年版情報通信白書によれば〜」のように白書を出典として記述する前に、必ず WebSearch で白書の章構成と原表現を確認してから書く。

- 確認手順: 公式 HTML（総務省・文科省・NISC）の概要ページで章番号・章タイトル・本文の単語を確認
- NotebookLM 利用時: `notebooklm-research` で本文照合、認証期限切れなら `notebooklm login` をユーザーに依頼してから着手
- 確認できない単語は、より広い概念語に置き換える（例: 「ハルシネーション」→「偽・誤情報の流通」）
- 「予想問題本文」中の白書引用は出題者風の再構成が許されるが、「なぜR8でこのテーマが出題されると予想するか」の根拠説明は厳密に出典確認

理由: 「ハルシネーション・ランサムウェア・サプライチェーン攻撃・生成AI悪用」など耳慣れた用語を出典確認なしで白書由来として書くと事実誤認になる。
