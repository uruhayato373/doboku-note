# X(旧Twitter) 投稿ポリシー（多資格・エージェント分業）

X 投稿の真実源。文字数ルール・試験別テンプレ/タグ・投稿型・5 軸ルーブリック・偽成功検証を集約する。
IG の各 policy（`ig-carousel-policy.md` 等）とパラレルな位置づけで、Generator（`x-post-writer`）と
Evaluator（`x-post-qa`）が共通参照する。

> 設計原則: **資格別にエージェント/スキルを増やさない**。媒体（X）× 機能（Generator/Evaluator）で分業し、
> 試験（総監 / 1級土木 / 2級土木 …）は `exam` パラメータで横断する（IG と同じ思想）。

## 1. 戦略上の位置づけ

- X は**受験生コミュニティへの即効性チャネル**。フォロワー獲得の本質は**良質なリプライ運用**（戦略 v5 §7: 1 日 10 件、宣伝なしの補足・励まし）。
- 自動投稿よりも「**ネタの半自動生成（writer）＋手動の投稿・リプライ**」が現実的。`x-post-writer` は下書き（`tweets.md`）を量産し、投稿タイミングとリプライは人が担う。**この分業は凍結回避の観点でも要（自動化フットプリントの最小化 → §11）**。
- 真実源の戦略は `docs/project/03_SNS/01_SNS集客戦略.md` の X 節。

## 2. 文字数ルール（短文デフォルト＋長文 opt-in）

**既定は 280 weighted chars 以下の短文**。運用アカウントとプロフィール値の機械可読SSOTは **`.claude/config/x-account.json`**（現在 `@doboku373`、旧 @dobokunotecom は 2026-06-12 凍結）。Premium 加入時は技術上限が約 25,000 字まで拡張されるが、**タイムラインは長文でも「さらに表示」で折りたたまれ、リーチ・エンゲージメントは短文＋強いフックが有利**。よって **280 短文を全投稿のデフォルト**に保ち、長文は「詳しい解説／合格体験ストーリー／制度解説」に限って §2.1 の opt-in で使う。

> **旧記述の訂正（2026-07-02・X Premium 加入）**: 以前は「280 超は `publish-x` 予約時に X 側で reject される」としていたが、これは Premium 加入前の前提。**Premium では 280 超も投稿可能**（reject されない）。ただし上記リーチ理由から短文をデフォルトに保つ。長さは伸びの要因ではない——効くのはフックと文面のユニーク性（§11）。

| 要素 | 重み |
|---|---|
| 日本語・絵文字・全角記号 | 2 /字 |
| 英数字・半角記号・スペース・改行 | 1 /字 |
| URL（実長によらず） | 23 固定 |
| 上限（既定・短文） | 280 |
| 上限（`[longform]` 時） | 25,000（§2.1） |

→ 純日本語なら **本文 ≒ 117 字 + URL 1 本**が目安（短文デフォルト時）。

検証コマンド（`tweets.md` 変更後は commit 前に必須・違反で exit 1）:

```bash
node scripts/check-x-length.mjs                 # 全ドラフト（既定280・[longform]は25,000で判定）
node scripts/check-x-length.mjs --draft 040     # 単一
node scripts/check-x-length.mjs --over          # 違反のみ
```

> 既知の落とし穴: `check-x-length` は Windows で空振りした事例あり（[[measurement-incidents]] 系）。違反ゼロ表示を鵜呑みにせず、weighted 計算を目視確認する。

### 2.1 長文（longform）型の opt-in

短文が伸びにくい特定コンテンツ（詳しい解説・合格体験ストーリー・制度/法改正解説）に限り長文を使う。ハイブリッド運用＝**週次ドラフトの大半は短文、長文は少数を混ぜる**。

- **マーカー**: 長文にするツイートの `## Tweet NN:` 見出しに **`[longform]`** を付ける（例: `## Tweet 12: 解説・長文 [longform]（水 7/8 22:35）`）。`check-x-length` はこのマーカー付きツイートのみ上限を **25,000 weighted** に緩和し、無印は従来どおり 280 で判定する（weighted 判定なので実文字数 25,000 より保守的＝安全側）。
- **冒頭フック必須**: タイムラインは 1〜2 行で折りたたまれる。**最初の 1 文で結論／引き（フック）を出す**。折りたたみ前に興味を作れない長文は開かれない。
- **構成**: 結論→根拠→具体→CTA。段落を空行で区切り、箇条書きを活用（X 長文は改行が効く）。
- **凍結回避（§11）は長文でも同等に適用**。キーワード/ハッシュタグ詰め込み・同一 URL 反復・テンプレ反復は長文でも spam 判定対象。むしろ長文は詰め込みやすく危険。
- **URL**: 長文でも誘導 URL は原則 1 本（末尾 CTA）。
- **頻度**: 長文は毎日出さない。**週 1〜2 本まで**を目安（短文リーチの主軸を崩さない）。

### 5.1 切り口分割（angle-slice）型の作法

→ **真実源**: [`.claude/knowledge/reference/sns-repurpose-policy.md`](./sns-repurpose-policy.md)（X / IG / YT 全チャネル共通）

1 テーマを 6 切り口に刻み、単発投稿 ×6（1 日 1 本で約 1 週間分のネタ）として量産する。総監はキーワード 740+ ページと note 記事が厚く、最も効く。`angle=all` を指定すると6切り口すべてを生成する。`type` パラメータとは直交するため、`question` 型でも `keyword` 型でも任意の切り口で書ける。

| 切り口 | 役割 |
|---|---|
| 結論 | 主張を 1 文で言い切る（フック） |
| 理由 | なぜそう言えるか |
| 体験 | 合格者の視点・気づき |
| 反論 | よくある誤解への反証 |
| 数字 | 一次ソースの定量根拠 |
| ハウツー | 実践ステップ |

- **体験軸の鉄則**: 運営者は**総監合格者**（元・地方自治体土木職〔発注者〕の退職者、6 資格保有 → `src/config/author.ts`）。**合格者の権威で書いてよい**（「合格した／こう書いて受かった／発注者として実感した」等）。ただし**真実の範囲を超える固有値**（点数・順位・未確定の年度実績等）は捏造しない（→ 軸 2）。
- **数字軸**: 数値・固有名詞はネタ源から裏取りし捏造しない。
- **URL 方針**: 誘導 URL は **結論とハウツーの 2 本だけ**。他 4 本はリンクなし（in-feed リーチ・保存重視）。
- **ファイル構成**: 1 テーマ = 1 `tweets.md`。`## Tweet 01: 結論` …`## Tweet 06: ハウツー` の 6 セクション。
- 先行例: `051`〜`056`（総監 6 テーマ ×6 切り口 = 36 投稿）。

### 5.2.1 スレッド（2連投）の予約 — [thread] マーカー運用

**X ネイティブの予約はスレッド非対応**（2026-07-14 実機プローブで確定: composer に 2 本目
`tweetTextarea_1` を追加すると `scheduleOption` が `aria-disabled="true"` になり日時ダイアログも開かない。
「ネイティブはスレッドをまとめて予約できる」とした旧記述は誤りだったため訂正）。

実装（2026-07-14・ヘッド予約＋リプライランナー方式）:

- **書式**: `## Tweet NN: タイトル [thread]` ＋ 本文内を `--- リプライ ---` 行で区切る。1 部目＝ヘッド、2 部目以降＝リプライ。各部が独立ツイートとして 280 weighted 判定される（`check-x-length` が part 別に検査）。
- **即時投稿**（`--immediate`）: `publish-x` が composer で全部組んで一括投稿（完全対応）。
- **予約投稿**: `publish-x` は**ヘッドのみ**ネイティブ予約し、リプライ本文を `status.json` の `thread: { parts, replies_posted_at: null }` に記録する。予約時刻の経過後に **`node scripts/x-thread-replies.mjs --run`** を人間トリガーで実行 → ライブになったヘッドを自分のプロフィールから特定し、リプライをチェーンでぶら下げる（`--list` で pending 確認・`--dry-run` でヘッド特定まで）。リプライが数十分〜数時間遅れても自己リプライとして自然。
- cron 常駐はしない（自動化フットプリント最小化・§11.3）。予約スレッドがある週は、ヘッド配信後に 1 回 `--run` を叩く運用。

### 5.3 実績・社会的証明型の作法（売上スクショ）

- **購入者名は必ずマスク**。加工より DOM 置換（購入者名を「■■■」に置換してからスクショ）が確実（可逆リスクゼロ）。**外部公開前にユーザー目視承認を必須チェックポイントにする**。
- 数字軸の裏取り: 販売実績は `.claude/state/sales/sales-log.json` と突合してから書く（捏造・誇張の禁止・§9/軸2）。
- **合否保証・断定表現は禁止**（[[note-selling-structures]] の Red Line と同じ）。「買えば受かる」ではなく「不合格の再受験コスト（受験料＋1年）vs 教材コスト」の**機会費用の対比**で訴求する。
- 頻度は **週3本まで**（2026-07-14 ユーザー決定。当初案は週1本＝押し売り化懸念だったが、需要期の露出を優先して週3本に拡大）。緩和条件: ①3本は**各別角度**（機会費用/社会的証明/再受験をお金で買う 等）②**同一画像の3連投をしない**（少なくとも1本はテキストのみ＝メディア重複の spam footprint 回避）③near-dup ガード（Jaccard≥0.62 BLOCK）を全本通す。エンゲージ実測で押し売り兆候（伸び劣化）が出たら週1本に戻す。

## 6. URL / UTM

- 投稿内 URL は 1 本まで（23 weighted）。
- UTM 統一フォーマットは `docs/project/03_SNS/02_チャネル動線設計.md` §4 準拠（`utm_source=x` / `utm_medium=social`）。送客リンクへの付与は `node .claude/scripts/lib/utm-builder.mjs --url <URL> --channel x --format post --campaign <name>`（`utm-templates.json` 由来・冪等・既存 UTM は上書きしない）。
- リンクは短縮 URL を使い、weighted 23 固定の利点を活かす。
- **`/docs/{slug}` は本番フラット slug ＝「カテゴリ-ディレクトリ」を必ず使う**（最重要・404 防止）。ページの**ディレクトリ名だけ**で組むと 404 になる。
  - 誤: `/docs/primary-r03-kouki` → 正: `/docs/civil-construction-2-primary-r03-kouki`
  - 誤: `/docs/keyword-2026`（総監/土木で分岐）→ 正: `/docs/pe-comprehensive-management-keyword-2026` 等
  - slug の真実源は `src/config/doc-meta-index.json` の `docs` キー。執筆時はここに存在する slug かを必ず照合する。
- **検証の仕組み化（2026-06-08 新設）**: `node scripts/check-sns-urls.mjs` が `docs/sns/**` の `/docs/` リンクを doc-meta-index と突合し、本番に無い slug を検出する。pre-commit に `--staged` で組込済み（broken があるとコミット不可）。背景: 2026-06 に X 投稿 149 件のリンク切れ（560+ impressions ロス）が発生 → 接頭辞欠落が原因。

## 8. 5 軸ルーブリック（`x-post-qa` 採点）

各軸 0〜3 点、合格ライン平均 ≥ 2.0。

1. **文字数遵守**: 短文は 280 weighted 以下、`[longform]` は 25,000 以下（§2.1）。`check-x-length` で 0 違反。長文は「短文で足りない内容か・冒頭フックがあるか・週1〜2本の範囲か」も併せて確認。
2. **論点の的確さ**: 過去問型は正答全文ネタバレでなく論点提示。キーワード型は定義の核を外さない。誇張・捏造なし。
3. **タグ適切性**: 試験別ベースタグ準拠・1〜3 個・無関係タグなし。
4. **導線整合**: URL 1 本・UTM 正・サイト/note 誘導が自然。
5. **偽成功検証**: 投稿後に予約キューを**実体検証**（§9）。

> 加えて **§11（凍結回避）を重大減点ゲート**として適用する。near-duplicate なテンプレ文面の反復・同一 URL の多数貼り・毎回同一固定タグ → 軸2/軸4 を重大減点。スコア平均で薄まらないハードゲート扱い（X の spam/platform-manipulation 検知＝凍結リスクのため）。

## 11. 凍結回避（スパム・自動化検知ガードレール）

> **背景（2026-06-12 凍結事故）**: 運用 X アカウント（@dobokunotecom）が「platform manipulation and spam」（日本語通知では「**偽装行為**」と表示。同一カテゴリの訳ぶれ）で凍結された。異議申し立て（文面審査）は「当初の決定を撤回する正当な理由はない」として**却下**された（ただし解除の自助パスは別系統で残る → §11.3）。X はテンプレ重複文面・機械的な投稿パターン・短時間連投・同一リンク反復を spam / 自動化として検知する。本基盤は 1問1答パック・angle-slice・`publish-x`（Playwright 自動投稿）で**重複・自動化臭の高い投稿を量産しうる**ため、以下を全工程の制約とする。違反は「文字数 280 超」「リンク 404」と同格の**ブロッキング事項**。

### 11.1 文面のユニーク性（writer / qa）

- 同一ドラフト内・ドラフト跨ぎで **near-duplicate なテンプレ文面を量産しない**。「【過去問】◯◯／正答の論点は…／詳しくは {URL}」のような定型骨格をそのまま反復しない。
- 各ツイートで**フック（冒頭1文）・語順・締め（CTA）を変える**。最低でも冒頭1文と CTA 文言は使い回さない。
- **同一 URL を短期間に何本も貼らない**。1問1答・過去問連投では URL を一部のツイートだけに付け、残りはリンクなし（angle-slice の「結論・ハウツーのみ URL」と同じ発想・§5.1）。
- ハッシュタグの機械的固定（同テーマで毎回まったく同じ3個）も避け、論点タグを回す。

### 11.2 投稿頻度・間隔（publish-x / 人）

- **1 日の投稿は最大 3〜5 本目安**。新規・低フォロワー期はさらに絞る（2〜3 本）。**現行は 1 日 3 本**（2026-08-13 に S2 へ移行 → §11.6）。
- 一括予約で**毎日同時刻（08:00 固定等）に並べない**。時刻を日ごとにジッタ（±30〜90 分）させ人間的に分散する。
- まとめて何十本も予約キューに積まない。1 回の予約は数本に留め、キュー全体が**機械的な等間隔列に見えない**ようにする。
- **バースト連投（数分〜十数分間隔の連投）をしない**。最低 60〜90 分は空ける。

#### 11.2.1 時間帯スロット（1 日 3 本の配置）

1 日 3 本は **A（朝）/ B（昼）/ C（夜）を 1 本ずつ**に割り当てる。同一スロットに 2 本入れない。

| スロット | 帯 | 主に置く型 | 根拠 |
|---|---|---|---|
| **A 朝** | 07:10–08:40 | 共感フック・暗記・現場つぶやき | 自投稿実測で平均が最も高い（下表）。通勤前の受動閲覧に合う |
| **B 昼** | 12:10–12:55 | 過去問 1 問 1 答・要点圧縮・引っかけ | 最も弱い枠。**短時間で完結する型**を置き、重い導線は載せない |
| **C 夜** | 19:30–21:30 | 解説・導線（**販売系はここだけ**） | 中央値は朝と同等。腰を据えて読む枠なのでリンク先へ進みやすい |

- 各日 **時刻は分単位でジッタ**させる（帯の中で日ごとに動かす。同一 HH:MM の固定は §11.2 のとおり禁止）。
- 同一日の 2 本の間隔は **60 分以上**（`check-x-campaign-plan` v2 が機械で BLOCK）。
- **販売 funnel（note / coconala / brain）は 1 日 1 本まで、かつスロット C のみ**。朝昼を売り込みで潰さない。

> **実測（2026-08-13・`npm run x-own-metrics`・直近 100 投稿 / フォロワー 91）**
>
> | 区分 | 本数 | いいね中央値 | 平均 | 最大 |
> |---|---|---|---|---|
> | A 朝 | 36 | 1 | 3.03 | 57 |
> | C 夜 | 41 | 1 | 1.46 | 18 |
> | B 昼 | 22 | 0.5 | 1.00 | 6 |
>
> **平均だけで読まないこと**。リンクなし投稿は平均 7.31 だが**中央値 0**で、57 と 35 の 2 本が作った値だった（＝「リンクなしが 5 倍効く」は誤読）。安定して反応があるのは URL 付きの方（中央値 1）。
> 資格別の中央値は `civil-1` 3 / `civil-1-2` 2 / `civil-2` 2 / 総監 0 / **建設部門 0（7 本すべて 0）**。土木施工管理を中心に据える根拠。
> 取得できない指標（インプレッション・リプライ）があるため、**いいね 0 を「誰にも見られていない」とは読まない**。

### 11.3 自動化フットプリントの最小化

- §1 の原則どおり **自動投稿よりも writer による半自動生成＋人手の投稿/リプライ**を基本とする。`publish-x` はあくまで予約補助で、全量を機械投稿に寄せない。
- **自動フォロー / 自動いいね / 自動リプライ系は使わない**（X 規約の platform manipulation 直撃）。リプライ運用（§10）は人が手動で行う。
- 凍結・ロック時は SMS 認証など**正規手順で解除**し、回避目的の新規アカウント量産（ban evasion）はしない（通知にも「新規作成で回避を試みたら新アカウントも凍結」と明記）。
- **異議申し立て（文面審査）と解除手順は別系統**。異議が却下されても、通知末尾の「アカウントにログイン → 画面の手順を完了して違反を解決」（=ロック/機能制限状態の SMS・電話番号認証や captcha）で解除できる場合がある。却下＝終わり、ではない。
- **解除手順はメール/通知内リンクから辿らない**。凍結通知を装ったフィッシング（資格情報窃取）が常態。必ず自分で `x.com` または公式アプリを直接開いて画面手順を完了する（2026-06-12 受領通知に "witter" 等の崩れあり＝偽装通知の可能性も想定して扱う）。

### 11.4 qa の凍結リスク・ゲート

- `x-post-qa` は near-duplicate テンプレ／同一 URL 反復／機械的タグ固定を検出したら**重大減点**し、是正指示に「フック・CTA・語順の差し替え／URL を一部に限定／投稿の時間分散」を必ず含める（§8 重点チェック）。

### 11.5 予約前ゲート（再発防止・機械検査）

> **背景（2026-06-21）**: 凍結後に作った新アカウントで再開する際、(a) 古い予約が残ったまま同枠に再予約 → 同時刻二重投稿、(b) 旧アカ status.json の残骸を誤って publish → 凍結文面の再投稿、という二重事故を構造的に防ぐため**機械ゲート**を新設。`§11.1〜11.4` を人/エージェントの規律で守った上で、**予約実行の直前に必ず通す門番**として機能する。

**SSOT**: `docs/sns/x/{draft,published}/<NNN>-*/status.json` が「いつ・何を予約/投稿したか」の唯一の台帳。tweet ごとに `status`（`scheduled`/`posted`）・`scheduled_at`・`text` を持つ。予約・投稿の事実はここにしか書かない。

**門番**: `npm run x-schedule-guard`（[scripts/x-schedule-guard.mjs](../../../scripts/x-schedule-guard.mjs)）。全 status.json を読み、以下を判定して **BLOCK があれば exit 1**（文字数 280 超・リンク 404 と同格のブロッキング）。

| 検査 | 判定 | 対応する §11 / 事故 |
|---|---|---|
| 同時刻衝突（同一分に2件以上） | BLOCK | 二重投稿の直接原因 |
| near-duplicate 文面（正規化トライグラム Jaccard ≥ 0.62） | BLOCK | §11.1 テンプレ反復＝凍結カテゴリ「spam」本丸 |
| 1日上限超（既定3本、新規期は `--max-per-day 2`） | BLOCK | §11.2 |
| 時刻ジッタ不足（毎日同一 HH:MM 固定） | WARN | §11.2 |
| 同一 URL を3件以上の予約に貼付 | WARN | §11.1 |
| `--queue`: X 実キューに予約予定の本文が既存 | BLOCK | (a) 古い予約残存の実体検出 |

- **予約フロー**: `x-post-writer`（生成）→ `x-post-qa`（§11 ゲート採点）→ status.json に `scheduled_at` 記入 → **`npm run x-schedule-guard --queue` で緑**→ `publish-x` 実行 → `npm run x-sync-status`（偽成功の実査・§9＋下記 queued 昇格）。緑でない限り予約しない。
- **状態ライフサイクル**: `scheduled`（計画・未投入）→ `queued`（X キュー投入済。`x-sync-status` がキュー実在を確認して昇格＝§9 偽成功検証を兼ねる）→ `posted`（送信時刻通過後キューから消えたら昇格）。guard / `x-schedule-view` / `x-sync-status` は `scheduled`＋`queued` を「未来予約」として扱い、**guard の `--queue` 二重チェックだけは `queued` を除外**（既にキューに在って当然なので、週次で次バッチを積むとき誤検出で赤にならない）。次バッチは未投入の `scheduled` のみを `publish-x --tweets N-M` で対象化する。
- **アカウント境界（epoch）**: 凍結アカウントの drafts は `docs/sns/x/_archive-<handle>/` へ退避する。`_` 接頭辞ディレクトリは guard / `x-schedule-view` / `x-sync-status` のスキャン対象外＝**新アカウントは常にクリーンな台帳から始める**。旧アカの予約済み status を新アカで publish しないための物理的隔離。

### 11.7 競合 read（scout-x-competitors）の安全弁

> 節番号は 2026-08-13 に §11.6 から §11.7 へ変更（復帰ゲートと番号が重複していた。参照の多数は復帰ゲート側を指していたためそちらを §11.6 のまま残した）。

> **背景（2026-07-20）**: 多チャネル競合パイプライン（[[note-competitor-intel-pipeline]]・`/competitor-review --platform x`）で X 競合のフォロワー/投稿/エンゲージを機械取得する。凍結復帰中の **@doboku373 に read 自動化の足跡を足さない**ことを構造で担保する。

- **取得アカウント＝運営者個人 `uruhayato373`**（agent-reach の twitter CLI が認証済み）。**投稿アカウント @doboku373 の Playwright プロファイル（`.local/playwright-x-profile`）は競合 read に使わない**。当初方針 backlog「X は未ログイン公開読取に留める」は、X が 2023 以降ログアウト閲覧を 404 で遮断するため実行不能＝**個人アカ CLI 経由の read がその代替（投稿アカを守る目的は同じ）**。

| 段階 | 状態 | 満たすべき条件（全て） |
|---|---|---|
| **S0 縮退** | 完全手動・低頻度 | `x-post-writer` で下書きのみ／投稿・リプライは人手／`publish-x` 停止 |
| **S1 予約補助の再開** | `publish-x` を予約のみに限定復帰 | ① @doboku373 が凍結・機能制限なしで最低 **4 週間**手動運用を継続（ロック/警告ゼロ）② その間の手動投稿が §11.1〜11.2 を実際に満たしていた（near-dup なし・同時刻並べなし）③ `npm run x-schedule-guard --queue` が緑 ④ 1 日 **2 本**上限（`--max-per-day 2`）を維持 |

- **後退条件**: どの段でも、警告・機能制限・凍結の兆候が 1 度でも出たら即 **S0** に戻し、原因（テンプレ反復・頻度・同一 URL）を §11.1〜11.2 で洗い直す。段階を飛ばして戻さない。
- **ban evasion はしない**（§11.3）。再凍結時に新アカウントを量産して回避しない。解除は正規手順のみ。
