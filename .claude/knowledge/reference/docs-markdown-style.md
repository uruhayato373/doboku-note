# docs/ 内 Markdown ドキュメントの執筆スタイル

> [!note] 適用範囲（2026-08-18・4 領域モデル）
> - `docs/**/*.md` — 人向けストック。本規約（Obsidian callout 4 種）の対象
> - `content/**/article.md` などプラットフォーム本文 — **callout 対象外**（note・ココナラ等は独自記法）
> - `.claude/plans/**/*.md` — 一時作業契約。許可 callout は既存 4 種のみ
> 置き場の原則 → [information-architecture.md](./information-architecture.md)

## いつ読むか

`docs/` 配下の **Markdown（.md）ドキュメント** を新規作成・編集するとき。具体的には:

- `docs/handoffs/YYYY-MM-DD-{context}.md` — セッション引き継ぎ
- `docs/{strategy,editorial,marketing,operations,products,design}/**/*.md` — 戦略・設計・進捗
- `.claude/knowledge/reference/*.md` — 運用ポリシー（このファイルもここに属する）

**対象外**: `content/note/**/article.md`（note プラットフォームが Obsidian callout 記法を解釈しないため）

---

## なぜ必要か

- handoff / project ドキュメントは Obsidian で目視するワークフロー → 「重要」「TODO」「警告」を視覚マーキングできる callout が有効
- 一方、公開記事 MDX には別途 `<Callout type="...">` コンポーネント（12 種）が存在し、**同名 "callout" の別物が 2 系統並ぶ** → 混同防止が必須
- 漫然と全段落を装飾すると強調インフレで本文の重みが消える → 使う場所と種類を絞ったポリシーが必要

---

## MDX `<Callout>` との対比

| 対象 | 記法 | 配置場所 | 種類 | 真実源 |
|---|---|---|---|---|
| 公開記事 (MDX) | `<Callout type="...">` | `content/site/**/*.mdx` | 12 種 | [content-principles.md §7](./content-principles.md) |
| 社内ドキュメント (MD) | `> [!type]` | `docs/` 配下 `.md` | **4 種限定** | このファイル |

両者は **記法も種類も実装も別物**。MDX 公開記事に `> [!note]` を書くとレンダリングされず、社内ドキュメントに `<Callout>` を書いても Obsidian で素のテキストになる。

---

## 推奨タイプ — 4 種限定

| タイプ | 用途 | 典型例 |
|---|---|---|
| `[!note]` | 補足情報、参考 | 「補足: バックグラウンドで …」 |
| `[!warning]` | 注意点、落とし穴 | 「R2 残骸は手動掃除が必要」 |
| `[!important]` | 決定事項、重要前提 | 「次セッションはこのファイルから着手」 |
| `[!todo]` | 未完了タスク、残課題 | 「PE 19 件の張り替え」 |

**拡張禁止**: 上記 4 種で 90% カバーできる。新タイプが必要になったら、まずこのファイルを改訂してから追加する（ポリシー安定化のため、その場のアドリブで増やさない）。

> [!warning] Obsidian 標準以外のタイプ
> `[!tip]` / `[!success]` / `[!question]` 等の Obsidian 標準タイプも動作はするが、本プロジェクトでは使わない。役割が `[!note]` / `[!important]` と被り、判断コストが上がるため。

## 記法

### 基本

```markdown
> [!note] タイトル（任意）
> 本文。複数行可。
>
> 段落を分けるときは空行を `>` で挟む。
```

レンダリング:

> [!note] タイトル（任意）
> 本文。複数行可。
>
> 段落を分けるときは空行を `>` で挟む。

### 折りたたみ

```markdown
> [!warning]+ 展開状態で開く
> 内容

> [!todo]- 折りたたみ状態で開く
> 内容
```

- `+` … デフォルト展開（読者にまず見せたい）
- `-` … デフォルト折りたたみ（長い残課題リスト・補足の詳細など）
- なし … 展開（Obsidian 仕様）

### ネスト

callout 内に通常 markdown（リスト・表・コードブロック・リンク）を入れ子にできる。

```markdown
> [!todo]+ Priority 1: PE 19 件の張り替え
> - `lca` → `life-cycle-assessment` を探す
> - 見つからなければエントリ削除
>
> 完了条件: `npm run check-mdx` で HIGH = 0
```

## スコープ別運用ガイド

| 場所 | 使用頻度 | 推奨タイプ | 理由 |
|---|---|---|---|
| `docs/handoffs/` | ◎ 積極利用 | `[!todo]` 残課題 / `[!important]` 着手手順 / `[!warning]` 注意 | 次セッション Claude が読む。視認性が直接生産性に効く |
| `docs/{領域}/` | ○ 限定利用 | `[!important]` 決定事項 / `[!warning]` 制約 | 戦略文書。決定事項を強調したいが、装飾過多は避ける |
| `.claude/knowledge/reference/` | △ 慎重利用 | `[!warning]` 例外・落とし穴のみ | 運用ポリシーは本文で淡々と書く。例外だけ強調 |
| `content/note/` | ✗ 使用不可 | （該当なし） | note プラットフォームが解釈しない |

## 長さの既定（全 docs 成果物 共通）

CLAUDE.md §6「書き出すドキュメントは必要な長さに収める」の具体化。**レポート・レビュー・監査結果を md に書くときは以下を既定とする**（スキル側に個別の分量指定があればそちらが優先）。

- **結論を先頭に置く**。冒頭は「何が起きたか／何が分かったか」を数行で。経緯・過程は後ろ
- **各セクションは箇条書き 3〜5 点**を目安。それを超えるならセクションを分けるか、上位のみ載せて残りは件数で示す
- **表は上位 N 行＋「他 M 件」**。全件が必要なら別ファイル（`.tmp/` やデータ JSON）へ出してリンクする
- **書かない**: 埋めるための章、同じ内容の再要約、定型の前置き、「以上の通りです」型の締め
- **省略と検出は別物**: 分量を絞るのは「表示」であって「検出」ではない。検出は全件行い、載せきれない分は件数と参照先を必ず明示する（黙って落とさない）

> 長さを削るために内容を落とさない。中身は保ったまま、水増しだけをやめる。

## 失敗パターン — やらない

- **文章すべてを callout で囲う** → 強調インフレで本文の重みが消える
- **1 セクション 3 個以上の callout** → 視認性逆効果（1 セクション 1-2 個まで）
- **短文（1 行）を `[!note]` で囲う** → 通常段落で十分。callout の重みを安売りしない
- **ドメイン特化タイプの導入**（`[!exam]` 等） → 4 種で 90% カバー、迷ったら本文へ
- **MDX `<Callout>` を `.md` に書く** → レンダリングされず素のタグが表示される
- **`> [!note]` を `.mdx` に書く** → MDX の引用扱いでレンダリングされ、Callout デザインにならない
- **`content/note/` で使う** → note 投稿時に未対応構文として崩れる

## チェック

### Obsidian / GitHub 両環境

- **Obsidian で開いてレンダリング確認**: callout として正しく表示され、折りたたみが動くこと
- **GitHub の Files Changed タブで引用ブロック扱い**: `> [!note]` 行が消えても本文が引用として読めること（GFM フォールバック）
- 推奨タイプ 4 種は両環境で同じ見た目に近づくよう設計されている（拡張タイプは Obsidian 専用になりがち）

### タイポ・記法ミス

```bash
# 4 種以外の type 名タイポを目視確認
grep -rE "^> \[!\w+\]" docs/ | grep -vE "\[!(note|warning|important|todo)\]"
```

該当 0 件であれば OK。

### 文字化け

```bash
grep -rE "U\+FFFD|﹖|�" docs/
```

該当 0 件であれば OK（CLAUDE.md §11 準拠）。

> [!warning] 検出器そのものが持つ U+FFFD を「破損」と誤認して消さない
> `.claude/` 配下には U+FFFD の実文字を含むファイルが 7 件ある（本ファイル・
> `agents/kindle-book-qa.md`・`skills/{authoring/keyword-page, quality/consolidate-duplicate-keyword,
> quality/exam-backlinks, quality/figure-recrop, social/social-post}`）。
> これらは**文字化けを検出する grep の検索パターンそのもの**で、消すと検出器が
> 「空パターン＝全件マッチ」になって壊れる。リポジトリ全体を U+FFFD 走査すると
> 破損に見えるが、`content/` を走査する既存ゲート（note-lint / lint-mdx-mobile）は
> `.claude/` を対象にしないので偽陽性も発生していない。
>
> **エスケープ化での回避は不可**: Git Bash では bash の Unicode エスケープ
> （`$'` + `\u` + コードポイント + `'`）が文字へ展開されず、バックスラッシュ込みの
> 6 文字の文字列になる（2026-08-28 実測）。実文字で書くか、バイト列
> `$'\xef\xbf\xbd'` で書くかの二択で、実文字の方が読み手に意図が伝わる。
>
> **U+FFFD を 2 つ並べて書かない**（2026-08-28 に 3 件を 1 文字へ是正）。2 つ並べた
> パターンは 1 文字だけ壊れたケースを取りこぼして緑になる（実測: 1 文字破損ファイルに
> 対し 1 文字パターンは 1 件ヒット・2 文字パターンは 0 件）。必ず 1 文字で書く。

## 既存ドキュメントへの漸進導入

新規ドキュメントには本ポリシーを最初から適用する。既存ドキュメントは:

1. **handoff 系**: 新規作成分から適用、既存分は更新時にあわせて改修
2. **project 系**: 改訂時に決定事項を `[!important]` 化する程度
3. **reference 系**: 落とし穴節を `[!warning]` 化する程度

一括書き換えはしない（装飾コストが本文編集の機会を奪うため）。
