# 画像出典ポリシー

doboku-note の記事に図・写真を載せるときのルール集。PDF スキャン画像からの脱却と、著作権クリーンな画像運用を両立するための判定フローと許容ソースを定める。

**いつ読むか**: textbook 記事のリライト時、新規 keyword ページに図を追加するとき、既存 PNG スキャンを置き換えるとき。

**関連文書**:
- 図版作成スキル: `.claude/skills/authoring/create-svg/SKILL.md`
- 画像配信フロー: `.claude/knowledge/reference/content-authoring.md` § 画像配信
- デザイン原則: `.claude/knowledge/design-system/design-system.md`

## 判定フロー

図を載せようとするときは、まず以下のフローで種別を決める。

```
1. 本文の理解に図が必要か？
   ├─ No → 図を載せない（装飾目的は禁止）
   └─ Yes → 2 へ
2. 何を示すのか？
   ├─ 概念・仕組み・工程・関係（フロー/マトリクス/比較）
   │    → SVG 新規作成（create-svg スキルを使う）
   ├─ 実機の外観・現場の雰囲気・器材の使用場面・変状の見た目
   │    → 写真（§ 写真は AI で生成する。実写は使わない）
   └─ 数式・表で表せる内容
        → 図にせず、本文内で表・箇条書き・数式で表現
```

## SVG 優先の原則

以下のいずれかに該当する場合、写真ではなく **SVG** を優先する。

- **構造を示す**（機械の部品構成、建物の断面）
- **工程を示す**（PDCA、施工手順、ネットワーク工程）
- **比較を示す**（Before/After、方式比較、トレードオフ）
- **関係を示す**（組織図、力の釣り合い、熱移動）
- **抽象概念を可視化する**（リスク分布、指標の位置関係）

SVG の方が写真より優れる理由:
1. **著作権リスクゼロ**（自前制作）
2. **モバイルで鮮明**（ベクタ、拡大しても劣化しない）
3. **学習効果が高い**（本質だけ抽出できる、ノイズが入らない）
4. **後からの修正が容易**（テキスト・色・レイアウトをファイル直編集）

SVG 制作は `create-svg` スキルに従う。モバイル 400px viewBox、デザイントークン（brand/positive/warn/danger）、4 つのレイアウトパターンを適用する。

## 写真は AI で生成する（2026-10-07 運営者決定）

記事の写真（機械・器械の外観、変状の見た目、現場の様子）は**すべて AI で生成した画像**にする。CC/PD の実写・自前撮影・メーカー画像と、実写を AI で描き直した画像は使わない。比率は **4:3**（配信 960×720 の WebP）にそろえる。比率・配信幅・全写真に共通する生成の指示は `config/image-limits.json` の `aiPhoto` だけが持つ。

> [!warning] なぜ（2026-10-07）
> 1級土木テキスト 8 記事の機械の写真 23 枚は、Wikimedia Commons の実写を AI で描き直した画像だった。元の出典コメントと caption は消え、出所の記録は無く、描き直したセオドライトは実在しない形の器械になっていた。誰も実物と照らしていなかった。

**手順**（台帳は 2 つ。手で「済」と書く欄は無く、状態は台帳から導く）:

1. **仕様**: `config/figure-sources.json` の `provenance[図キー]` に `{ "kind": "ai-generated", "tool": "…", "prompt": "…" }`。`prompt` は被写体の指示で、本文が説明する部位・台数・形式（車輪の数・フレーム形式・ブームの構造など）を書く
2. **生成と配置**: `npm run gen-article-photo -- --fig <資格/記事/img/名前> [--prompt "…"] [--model <codex のモデル>]`。生成 → 中央で 4:3 に切る → `<図キー>.webp` を書く → 記事の src と width/height を合わせる → 実績の台帳（`.claude/state/quality/ai-image-review-ledger.json`）に sha と promptSha を記録する。生成済みの画像は `--from <画像>` で配置だけ行う
3. **監査**: `node scripts/check-image-origin.mjs --ai-queue --json` の項目を `ai-image-fidelity-auditor` が判定（種別・構造・本文・生成の破綻）→ `node scripts/check-image-origin.mjs record-ai <verdicts.json>`。不合格は `prompt` を直して 2 からやり直す
4. **検査**: `npm run check-image-origin`（`quality:audit:ci`）が、出所なし・実写・4:3 でない・未生成・未監査・不合格を止める

| 状態 | 意味 |
|---|---|
| 未生成 | 仕様の `prompt` から作った記録が今の画像に無い（指示を変えた・手で差し替えた） |
| 未監査 | 生成・配置したが、実物どおりかの判定が無い |
| 不合格 | 実物と違う（`prompt` を直して作り直す） |
| 合格 | 生成・配置・判定が今の画像でそろっている |

写真の MDX に出典コメントと caption は要らない（出所の正本は `provenance`）。書くなら台帳と食い違わないこと（`comment-mismatch`）。

### 禁止ソース

- **Google 画像検索の無差別利用** — 出典不明・ライセンス未確認のまま使わない
- **他社書籍・教材のスキャン** — 既存の PDF スキャン PNG も、ライセンス不明なものは置換対象
- **SNS（Twitter/X、Instagram 等）投稿画像** — 個人の著作物
- **ストックフォトの有料版を無許諾で利用** — 透かし除去・トリミングによる回避は違法

> [!note]
> **政府機関由来の図の扱い（2026-07-02 更新）**: 原典が国土交通省等の政府機関（白書・年報・統計・省庁HP）の図・グラフは、政府標準利用規約により出典明記のうえクロップ等の加工・商用利用が可。使う場合は画像直前に `{/* source: 国土交通省「…」, 政府標準利用規約 */}` ＋ caption に短い出典を付す。
>
> **運営者権利保有書籍の例外（2026-07-03 再々確定）**: 技術士建設部門『論文対策キーワード』は**運営者が著作権に問題がない（権利を保有する）ことを明言**しており、同書のスキャン図（`content/sources/textbook/技術士（建設部門）/論文対策キーワード/img/figNN.png`）は**クロップして `*-ronbun-keyword` 記事へ埋込可**（本書に限る例外。一般の「他社書籍・教材のスキャン」禁止は不変）。埋込時は `{/* source: ... */}` コメント＋出典 caption を付す。
>
> **経緯**: 2026-06-22 に本例外を設け 02(iji-kanri) で実施 → 2026-07-02 いったん撤回（クロップ図撤去・原典直接取得のみ可へ） → **2026-07-03 運営者判断（著作権問題なし）で例外を復活**。逐語本文の活用可否も同判断で許可。真実源＝`content/sources/textbook/技術士（建設部門）/論文対策キーワード/README.md`。

## 禁止事項: 写真の "参考 SVG 化"

既存写真を参考にして SVG（線画トレース・構図模倣）を作ることは **原則禁止**。

**理由**: 日本著作権法・米国著作権法ともに、特徴的な構図・配置の模倣は「翻案権侵害」と判定されるリスクがある。「参考にしただけ」は抗弁として弱い。

**許容される再構成**:
- 機械部品の **一般的な名称と配置** を示す SVG（例: ブーム・フック・ワイヤの関係図）は、技術的事実の可視化であって特定写真の模倣ではないため OK
- 力学的な関係図（例: 土圧の方向ベクトル）も同様に OK

**NG 例**:
- 特定メーカーの特定機種のシルエットを SVG 化
- 特定教科書の図版レイアウトをそのまま SVG で再現

判断がつかない場合は「削除して本文のみ」か、AI で生成した写真（§ 写真は AI で生成する）を選ぶ。

## 出典表記フォーマット

公的資料・運営者の権利保有書籍の図を使うときは、**画像直前の MDX コメント** で出典を明記する。出所の正本は `config/figure-sources.json` の `provenance`（`public-data`・`own-book-scan`）で、コメントは人が読む注記。公的資料は caption に提供者を出す（`check-image-origin` の `attribution-missing`）。

### 公的資料（政府機関）

```mdx
{/* source: 国土交通省, 政府標準利用規約 2.0, https://www.mlit.go.jp/... */}
<ArticleImage src="..." alt="..." caption="出典：国土交通省（政府標準利用規約）" />
```

> [!important]
> `loading="lazy"` は **2 枚目以降**の書き方。**本文 1 枚目（先頭 2,000 文字以内）は `loading="eager" fetchpriority="high"`** にする（フォールド内＝LCP 要素になるため）。機械ゲート `npm run check-lcp-image-hints` が pre-commit / CI で検査する。詳細: [content-authoring.md](./content-authoring.md)「読み込み優先度（LCP ゲート・必読）」

### SVG（自前制作）

SVG は自前制作が前提のため、出典コメントは不要。代わりに SVG ファイル内の先頭に `<!-- Created by doboku-note, <YYYY-MM-DD> -->` を付けておく（任意）。

## 推奨コンポーネント: `<ArticleImage>`

**新規記事は `<ArticleImage>` を使う**（`src/components/ui/ArticleImage/ArticleImage.tsx`）。`<figure>` セマンティクスを自動で付与し、Next.js `<Image>` の最適化も効く。

### caption の使い方

**真実源**: [.claude/knowledge/reference/content-principles.md §8](./content-principles.md) L146

> `<ArticleImage>` の caption は「図の説明」には使わない。ただし、**出典・著作権帰属・機種名などの短い帰属情報**（目安 60 字以内）は caption に書いてよい。

- **NG**: caption で図の内容・構造・関係を説明する（本文と重複する）
- **OK**: caption で **出典（公的資料の提供者と利用規約）** を短く示す（公的資料は必須）

`alt` には簡潔な識別情報（60〜80 字以内）を入れる。機種の詳細説明・図の読み方は **本文** に書く。

### 良い例

```mdx
#### クローラクレーン

全油圧式が主流で、ブームはパイプまたは形鋼のラチス構造で軽量。

<ArticleImage
  src="/posts/civil-construction-1/textbook-crane/img/crawler-crane.webp"
  alt="クローラクレーン"
  width={960}
  height={720}
/>
```

### 悪い例（caption で詳細説明）

```mdx
{/* 本文が薄く、caption に図の内容を詰め込んでいる */}
<ArticleImage
  src="..."
  alt="..."
  caption="ラチス構造のブームとクローラ式走行体が特徴で、不整地走破性に優れる"
/>
```

### 過去問図の caption / alt — 問題文に無い情報を絶対に追加しない

**真実源**: 本セクション（2026-04-26 追加、Issue #128 起因）

過去問（`*-primary` / `*-secondary` カテゴリ）の図版を反映する際は、**問題文に書かれている語句のみを caption / alt に使う**。問題文に無い情報（構造の説明、関係の解釈、答えに直結する記述）を加えると **受験者の判断材料を奪う / 答えを漏らす** ことになる。

#### 厳格ルール

1. **caption は問題文の関連箇所をそのまま引用** するか、**省略する**（出典がなければ caption 不要）。
2. **alt は問題文の図番号・タイトルをそのまま使う**（例: 「下図のシステム」→ alt="問題文に示されたシステム"）。
3. **構造・関係・分類などの判断情報を絶対に書かない**（特に組合せ問題・空欄補充問題で答えに直結する）。
4. 図の出典（指針名・規格名・白書名など）が問題文中に明示されている場合のみ caption に書いてよい。
5. **図そのものの描画にも解答情報を入れない**（過去問図を新規 SVG 等で再作図する場合）。クリティカルパスの色強調・正答・工期/余裕日数の集計・「最長経路＝○○日」等のサマリーは、設問を見た瞬間に答えが分かるため禁止。問題図は原則 PDF（過去問/問題集）からのクロップ（原図のまま）。解答補助図が有用なら**別図として解説 `<details>` 内へ**置く（2026-06-21 追加、1級土木 primary 工程表図の再発防止）。

#### NG / OK の具体例

**Ⅰ-1-30: 信頼性ブロック図問題**（並列か直列かを受験者が判断する）

```mdx
{/* 問題文: 「下図のシステムにおいて、ユニット1からの信頼度はR1=R2=R3=0.9である。」 */}

{/* NG: 「並列＋直列構成」と書いて答えを漏らす */}
<ArticleImage
  alt="ユニット1〜4の信頼性ブロック図（並列＋直列構成）"
  caption="図: ユニット 1+2 の直列とユニット 3+4 の直列を並列接続した信頼性ブロック図"
/>

{/* OK: 問題文の語句のみ */}
<ArticleImage
  alt="問題文に示されたユニット1〜4からなるシステム"
  caption="図: 信頼度 R₁=R₂=R₃=0.9 の 4 ユニットからなるシステム"
/>
```

**Ⅰ-1-29: OSHMS 概要図問題**（空欄補充）

```mdx
{/* 問題文: 「下図は、労働安全衛生マネジメントシステム（OSHMS）の概要について…」 */}

{/* NG: 「事業者による安全衛生方針の表明から PDCA サイクル、見直しまで」は問題文に無い */}
<ArticleImage
  caption="図: OSHMS の概要（事業者による安全衛生方針の表明から PDCA サイクル、見直しまで）"
/>

{/* OK: 問題文の語句のみ */}
<ArticleImage
  caption="図: 労働安全衛生マネジメントシステム（OSHMS）の概要"
/>
```

#### チェックリスト

過去問図に `<ArticleImage>` を追加する前に必ず確認:

- [ ] caption / alt の **すべての語句が問題文に存在する** か（または出典である指針名・規格名のみ）
- [ ] 図の **構造・関係・分類** を解釈して書いていないか（受験者が判断すべき情報）
- [ ] 「並列」「直列」「PDCA」「Plan-Do-Check-Act」など、図中ラベルや問題文に無い専門用語を補足していないか
- [ ] 不安なら caption を省略する（caption は必須ではない）

### 既存 `<img>` との棲み分け

- **新規記事・新規画像**: `<ArticleImage>` で統一
- **既存の生 `<img>` 記事**: リライト時に順次 `<ArticleImage>` へ移行（互換性維持）
- `{/* source: */}` コメントは公的資料・権利保有書籍の図に付ける（写真は不要・出所の正本は `provenance`）

## 実装ガイドライン

### ファイル配置

```
content/site/{slug}/img/
  figure-{n}.svg          # SVG 図版
  {name}.webp             # 写真（AI 生成・960×720・gen-article-photo が書く）
  {name}.png / .webp      # PDF・スキャンからの切り出し図
```

### 推奨ファイル形式

| 用途 | 形式 | 理由 |
|---|---|---|
| 概念・構造・工程図 | **SVG** | ベクタ、モバイル鮮明、修正容易 |
| 写真（AI 生成） | **WebP 960×720** | 4:3 にそろえる（`gen-article-photo` が切って書く） |
| スクリーンショット・UI 図 | **PNG** | 文字エッジがくっきり |

### ファイルサイズ目安

- SVG: 10KB 以内（過度な装飾を避ける）
- JPG: 200KB 以内（モバイル回線で 2 秒以内に読める）
- PNG: 100KB 以内（重い PNG は WebP 変換も検討）

## 図クロップの機械検査（`check-figure-crop`）

スキャン過去問・教材から切り出した図クロップ（`content/site/**/img/`）の**画素ジオメトリ**を検査する機械ゲート。既存の図監査は OCR ベース（`audit-figure-text` = 答え/本文テキスト、`build-figure-provenance` = 鮮明度・出所）で「テキストの内容」しか見ないため、クロップ縁の切断・隣接図の写り込みを取りこぼしていた（例: `r07-a-fig-04` 下端に隣接図のルビ写り込みが `textStatus:clean` で素通り）。本ゲートが画素で補完する。

実行: `npm run check-figure-crop`（全走査＋`.claude/state/quality/figure-crop-report.json` 出力）/ `check-figure-crop:ci`（baseline 比の新規のみ exit 1）/ `--file <img>`（1枚検査・figure-recrop の自己検証と `/figure-quality-loop` の QA 用）。写真（白率<50%）は自動スキップ。

| ルール | 扱い | 意味 |
|---|---|---|
| **STRAY_SLIVER** | **CI ブロッキング（HIGH）** | 上下端の**極薄インク島**（≤6px かつ ≤1%H）が白ギャップで本体から分離＝**隣接図の切れ端＝写り込み**（縦の線で本体へ繋がる島＝帰還矢印・軸の矢じりは除く）。フルハイトの正当ラベル/軸と分離できる唯一の高精度シグナル（実測 precision ≈ 8/10） |
| EDGE_CUT / EDGE_LINE / EDGE_TIGHT | 情報のみ | 縁接触の分類。finished 図では tight-crop（正当な密着・実測 538/643 が該当）と切断を幾何で判別できないため gate にしない |
| STRAY_LABEL / THIN_MARGIN | 情報のみ | 厚めの分離島（小見出し/軸/写り込みのいずれか・要目視）/ 極薄マージン |

**画素数**: 長辺が `config/image-limits.json` の `figureMinLongSide`（500px）未満の図は `figure-review-queue` の LOW_RES（優先2）。画素数を残していない古い ok の判定は、低解像度なら判定し直す（2026-10-07・DN-0577: 260×280 の図が鮮明度だけで「sharp」と素通りしていた）。

EDGE_CUT・STRAY_LABEL は CI では落とさないが、`/figure-quality-loop` の判定待ち（`npm run figure-review-queue` の優先2・3）が毎回読み、目視判定を台帳に残す（写真は除く）→ [figure-provenance.md](figure-provenance.md)。

**運用**: content-quality-ratchet と同方式。既存債務は `--update-baseline` で `figure-crop-baseline.json` に棚卸し登録し、`--ci` は baseline に無い**新規 STRAY_SLIVER のみ** fail。是正したら再度 `--update-baseline` で刈り込む。CI では `quality:audit:ci` の `figure-crop-integrity` チェックが 0 件を enforce。

**既知の限界と予防**: 旧 `figure-recrop.mjs` は切断後に白 border を付加するため、「切断済み＋白枠」の legacy 図（`r07-a-fig-02`「収縮限界」欠け型）は画素が失われており機械では高精度検出できない。対策は**予防側**＝`figure-recrop.mjs` が border 付加**前**の生クロップに `analyzeImage()` の EDGE_CUT/STRAY_SLIVER 検査を掛け、切りすぎた時点で `crop_warnings` を返す（生クロップでは切断=縁接触が確実に成立）。「切れた文字」の意味判定は機械ゲートに入れず、視覚監査（`civil-exam-figure-auditor`）の守備範囲とする。

## 既存 PNG スキャンの扱い

`content/site/**/img/` に現存する PNG スキャン（PDF 由来）は、**順次リライトで置換する方針**だが、以下のルールで段階的に移行する。

1. リライト対象記事の PNG スキャン → SVG または AI 生成の写真に **完全置換**
2. リライト未対象の記事は **現状維持**（段階展開の途中で放置する）
3. PNG スキャンを残す場合も、著作権侵害の疑いが濃いものは **即削除**（本文のみで理解可能なら削除可）

### 置換履歴の追跡

置換作業の所要時間・CC ヒット率・削除比率は、パイロット記事（textbook-network-schedule / textbook-crane / textbook-leveling）で実測し、全体展開計画の判断材料とする。

## 政府系サイト（go.jp）の画像を利用する場合

**国や地方公共団体のウェブサイトから画像を転載する場合**、以下を満たす必要がある。

### ライセンス確認

- **デフォルト**: 「公共データ利用規約（第 1.0 版）」（PDL 1.0、CC BY 4.0 互換）が適用されることが多い
- **個別規約の確認**: `{domain}/copyright.html` または親省庁の利用規約ページを必ず参照
  - 国交省本体: <https://www.mlit.go.jp/link.html>
  - 環境省: <https://www.env.go.jp/guide/copyright.html>
  - 各地方整備局・独立行政法人は別ポリシーの場合あり

### 運用ルール

1. **ホットリンク禁止**: `src` に相手サイトの URL を直接書かず、画像は自リポジトリ（`content/site/{slug}/img/`）にダウンロードして配置する
   - 相手サーバー負荷回避
   - URL 変更による表示破損回避
   - R2 経由で高速配信
2. **出典明示は caption で**: `<ArticleImage caption="出典：{機関名}（公共データ利用規約 1.0）" />` の形式（60 字以内）
3. **編集・加工時は明記**: 一部切り取り・翻訳・再描画した場合は caption に加工の旨を含める
4. **参考資料にも元ページへのリンクを併記**: 転載元の原ページを「参考資料」セクションでもリンクし、読者が最新版・詳細版にアクセスできるようにする

### 事例

`content/site/pe-comprehensive-management/environmental-impact-assessment/img/eia-procedure-flow.gif`:
- 出典: 国土交通省中部地方整備局
- ライセンス: PDL 1.0
- caption: `出典：国土交通省中部地方整備局（公共データ利用規約 1.0）`
- 参考資料に [環境アセスメント](https://www.cbr.mlit.go.jp/local_info/eco/assessment/) を併記

## チェックリスト（レビュー時）

画像を追加・置換する PR をレビューするときは、以下を確認する。

- [ ] 図の種別判定フローが適切か（SVG でよいものを写真にしていないか、逆もしかり）
- [ ] 写真は AI 生成で、`npm run check-image-origin` が通るか（出所・4:3・仕様から生成・実物どおりの判定）
- [ ] 公的資料は利用条件を確かめ、caption に提供者を出したか
- [ ] SVG は create-svg スキルの視認性ルール（viewBox ≤ 400px、フォント ≥ 13px）に準拠しているか
- [ ] alt テキストが具体的か（「画像」「写真」等の一般語は NG）
- [ ] ファイルサイズが目安以内か
- [ ] 政府系画像の場合、ホットリンクでなく自リポジトリに保存されているか、出典を caption に明示したか
