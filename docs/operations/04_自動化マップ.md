# 自動化マップ（2026-10-24 現在）

doboku-note の自動化の入口。個々のワークフロー・launchd ジョブの一覧は持たない（ドリフトするため）。

## 正本

| 見たいもの | 場所 |
|---|---|
| 全自動化の台帳（runner・source・schedule・ログインするサービス・書き込み先・読み手・目的） | `config/automations.json` |
| 台帳と実物（`.github/workflows/*.yml`・`scripts/scheduled/*.plist.tmpl`）の一致検査 | `npm run check-automations`（quality-audit の ci:true） |
| 台帳の画面と、直近の土曜の収集結果 | 管理画面 `/ops/automations`（`npm run admin`） |
| 土曜の収集の合否 | `npm run check-weekly-collect`（記録 `.claude/state/weekly-collect/runs.json`） |
| 自動化の失敗の通知 | GitHub Issue `automation-failure`（channel ごと。収集は `weekly-collect`） |

自動化を足す・消すときは、台帳に 1 件足す・消す。`check-automations` が台帳に無い workflow・plist と、実物の無い台帳行を止める。

## 原則

- **ログインが要る処理は、運営者の Mac で週 1 回（土曜の週次レビュー前後）だけ回す。** CI・Windows・他のセッションはログインしない。2026-10-24（DN-0817）に、Mac の launchd 4 本・Windows のタスク・CI のログイン系 3 本が別々に壊れ続けたため一本化した
- **機械で完結する処理は GitHub Actions が正**。取得・検査・配布・デプロイは公開 API・サイト・R2・GA4/GSC の API だけで動かす
- **意味判断**（週次の解釈・優先順位・文章）は Claude のスキル。土曜は launchd がヘッドレスで起動する（`/weekly-review`・`/monthly-review`）。クラウドルーティンは持たない
- **npm scripts** は Actions とローカル手動の共通実装（`refresh-indexes`・`quality:audit` など。一覧 → [commands.md](../../.claude/knowledge/reference/commands.md)）
- Google Drive を読み書きするワークフローは存在しない（意図的）。人のアセットは手元の `drive-vault-sync` だけが触る → [asset-storage-policy.md](../../.claude/knowledge/reference/asset-storage-policy.md) §1

## 土曜の Mac（`com.doboku-note.weekly-review`・土 09:30）

`scripts/scheduled/weekly-review.sh` が、使い捨ての収集用 worktree（`.claude/worktrees/weekly-collect`）で次を順に回す。段は 1 本ずつで、失敗しても次の段へ進み、結果を記録して develop へ push する。

| 順 | 内容 |
|---|---|
| 前段 `weekly-collect --phase pre` | `auth`（ログイン確認と入り直し）・`a8`・`kdp`・`note-traffic`・`note-sales`・`coconala`・`gsc`（登録リクエスト 10 件と月次の UI CSV） |
| 週次・月次レビュー | ヘッドレスの Claude が記録を読んで書く。`.claude/` へは書けないため `.tmp/claude-out/` に書き、`scripts/apply-claude-out.mjs` が許可リストのファイル（`.claude/todo/weekly.md` など）だけを写す |
| 後段 `weekly-collect --phase post` | `note-live`（添付・会員限定のライブ照合）・`note-sync`（記事の同期）・`note-sync-check`（反映の照合） |

運営者が 1 段だけ取り直すときは、収集用 worktree の端末で `node scripts/weekly-collect.mjs --only <段>`。ログインの詳細 → [playwright-auth-profiles.md](../../.claude/knowledge/reference/playwright-auth-profiles.md)。

## 記録を読むセッションの側

土曜以外のセッションは、A8・KDP・note・ココナラ・GSC の値を取りに行かず、記録とその最終取得日を読む。古ければ数値を埋めず「未取得」と書き、次の土曜の収集か、運営者の `--only <段>` を待つ。

## Claude を CI で動かすときの落とし穴

`gsc-auto-review.yml`（claude-code-action）で実測した。同種の自動化を作るときに再発しやすい。

- workflow_dispatch も cron も**デフォルトブランチ版**で動く。action は workflow がデフォルトブランチと同一内容でないと実行をスキップする
- `gh secret set` の隠し入力に貼り付けが効かず、値が空で登録されることがある（run ログの env が `TOKEN: ***` か `TOKEN: ` かで判る）
- `id-token: write` が必須。action は step 終了時に自身の app token を revoke するため、後続の push は `GITHUB_TOKEN` で remote を貼り直す
- CI は非対話で、turn 終了でセッションも終わる（サブエージェントを待って turn を終えると記録が失われる）
- `.claude/**` への Write は sensitive file として一律拒否される（allowlist 不可）。Claude は別の場所に断片を出し、反映と commit は bash が行う
- 成功終了でも記録が増えていなければ成功ではない。workflow 自身のゲートで実行前後の記録数を突合する。緑を信じる前に「何件記録されたか」を見る

分業の詳細 → [gsc-management.md](../../.claude/knowledge/reference/gsc-management.md)。
