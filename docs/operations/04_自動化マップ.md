# 自動化マップ（2026-10-25 現在）

doboku-note の自動化の入口。個々のワークフロー・launchd ジョブの一覧は持たない（ドリフトするため）。

## 正本

| 見たいもの | 場所 |
|---|---|
| 全自動化の台帳（runner・source・schedule・ログインするサービス・書き込み先・読み手・目的・GitHub Actions のまとまり） | `config/automations.json` |
| 台帳と実物（`.github/workflows/*.yml`・`scripts/scheduled/*.plist.tmpl`）の一致検査 | `npm run check-automations`（quality-audit の ci:true） |
| 土曜の流れ（収集の前・GSC の記録・週次レビュー・収集の後）の段ごとの結果と Mac の Issue | 管理画面 `/ops/mac`（`npm run admin`） |
| GitHub Actions の直近の実行結果・監視の判定（台帳のまとまりごと）と CI の Issue | 管理画面 `/ops/ci` |
| 土曜の収集の合否 | `npm run check-weekly-collect`（段ごとの最新・取り直しを含む。記録 `.claude/state/weekly-collect/runs.json`）。日次の死活は `npm run check-weekly-collect:alive` |
| 自動化の失敗の通知 | GitHub Issue `automation-failure`（channel ごと。収集は `weekly-collect`） |

自動化を足す・消すときは、台帳に 1 件足す・消す。GitHub Actions の行は `group`（`groups` のどれか）も書く（無いと型の検査 `check-datasets` が止める）。`check-automations` が台帳に無い workflow・plist と、実物の無い台帳行を止める。

## 原則

- **ブラウザの対話ログインが要る週次収集は、運営者の Mac で週 1 回（土曜）だけ回す。** CI・Windows・他のセッションで対話ログインしない。2026-10-24 に、Mac の launchd 4 本・Windows のタスク・CI のログイン系 3 本が別々に壊れ続けたため一本化した
- **機械で完結する処理は GitHub Actions が正**。取得・検査・配布・デプロイは API・サイト・R2 で動かす。承認済みの初回 YouTube 通常動画を個別予約する手動 workflow は、Actions の YouTube API 資格情報を使う
- **意味判断**（週次の解釈・優先順位・文章）は Claude のスキル。週次レビューと週次計画は土曜 13:10 のスケジュール済みタスク `doboku-weekly-review`（デスクトップアプリ）が実行する（2026-11-14〜。落ちた週は運営者の指示で後日まとめて回す）。月次レビュー（`/monthly-review`）は運営者の指示で対話セッションが実行する。クラウドルーティンは持たない
- **npm scripts** は Actions とローカル手動の共通実装（`refresh-indexes`・`quality:audit` など。用途は `npm run cmd -- <語>` で探す）
- Google Drive を読み書きするワークフローは存在しない（意図的）。人のアセットは手元の `drive-vault-sync` だけが触る → [asset-storage-policy.md](../../.claude/knowledge/reference/asset-storage-policy.md) §1

## 土曜の Mac（`com.doboku-note.weekly-review`・土 09:30）

`scripts/scheduled/weekly-review.sh` が次を順に回す。収集と GSC の記録層は自動実行用の worktree（`.claude/worktrees/weekly-collect`・毎日の GSC の登録と共用）で動く。週次・月次レビューは回さない（週次は 13:10 のスケジュール済みタスク）。launchd は定刻（土 09:30）に加えてログイン・起動のたびにも起動し（RunAtLoad）、土曜の開始時刻から日曜の間だけ、収集の記録から「今週まだ終わっていない範囲」（全部・後段だけ・なし）を決めて回す（再起動で途中終了した収集の回し直し・同じ週に 3 回まで・2026-11-14〜・DN-1196。plist を変えたときは `npm run weekly-review:install` で入れ直す）。段は 1 本ずつで、失敗しても次の段へ進み、結果を記録して develop へ push する。

| 順 | 内容 |
|---|---|
| 前段 `weekly-collect --phase pre` | `auth`（ログイン確認と入り直し）・`a8`・`kdp`・`note-traffic`・`note-sales`・`coconala`・`gsc`（登録リクエスト 10 件と月次の UI CSV）・`drive`（Drive を読めるかの事前検査）・`moshimo`・`note-status`（note の公開状態・マガジン・題名と価格の照合・毎週・旧 note-live-audit.yml の 4 本）・`note-audit`（note の全記事の照合・構造やタグなど 5 本・前回から 27 日たった週だけ）・`note-public-view`（note の公開画面の照合・公開 API の層だけ。代表ページの撮影は必要時・旧 note-public-view.yml）・`competitors`（競合の公開データ・四半期の最初の土曜だけ・旧 competitor-scan.yml）。各段は取った記録の検算（`verify`）つき（DN-0819） |
| GSC の記録層（`run_gsc_record`） | 週次・coverage が未記録のときだけ、ヘッドレスの Claude が断片を `.tmp/claude-out/gsc/` に書き、`scripts/apply-gsc-records.mjs` が `gsc-management.md` へ追記して push する。失敗は Issue channel gsc-auto-review（旧 CI の gsc-auto-review.yml・DN-0819） |
| 後段 `weekly-collect --phase post` | `note-live`（添付・会員限定のライブ照合）・`note-sync`（記事の同期）・`note-sync-check`（反映の照合） |

運営者が 1 段だけ取り直すときは、収集用 worktree の端末で `node scripts/weekly-collect.mjs --only <段>`。ログインの詳細 → [playwright-auth-profiles.md](../../.claude/knowledge/reference/playwright-auth-profiles.md)。

## 記録を読むセッションの側

土曜以外のセッションは、A8・KDP・note・ココナラ・GSC の値を取りに行かず、記録とその最終取得日を読む。古ければ数値を埋めず「未取得」と書き、次の土曜の収集か、運営者の `--only <段>` を待つ。

## Claude を CI で動かすときの落とし穴

CI で Claude を動かす自動化はいま無い（`gsc-auto-review.yml` を 2026-10-25 に外し、記録層は土曜の Mac へ移した・DN-0819）。作り直すときに再発しやすい要点だけ残す。

- workflow_dispatch も cron も**デフォルトブランチ版**で動く。`id-token: write` が要り、action は終了時に自身の token を revoke するので後続の push は `GITHUB_TOKEN` で行う
- ヘッドレスの Claude（CI でも土曜の Mac でも）は、パスの途中に `.claude` を含むファイルへ書けない（sensitive file）。`.claude` を含まない置き場に書かせ、反映と commit は bash が行う（土曜は `.tmp/claude-out/<.claude を外したパス>`）
- 成功終了でも記録が増えていなければ成功ではない。実行前後の記録数を突き合わせる

分業の詳細 → [gsc-management.md](../../.claude/knowledge/reference/gsc-management.md)。
