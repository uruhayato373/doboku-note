# 動画コンテンツ運用設計 批判的レビュー

**対象**: [動画コンテンツ運用設計](../../marketing/06_動画コンテンツ運用設計.md)

**レビュー日**: 2026-08-21

**結論**: 条件付き採用。動画展開そのものは妥当だが、量産・全資格展開・管理画面からの操作を先行すると、在庫と仕組みだけが増えて送客が改善しない。

## 1. 主な問題と処方

### 1. Shorts在庫がすでに多く、追加量産はボトルネックを解かない

`.claude/state/youtube-schedule.json` には200本あり、公開13本・保留187本。現状の律速はネタ不足ではなく、通常動画への接続、公開、計測、学習である。

**処方**: 新規Shorts量産より先に、4本の通常動画、関連動画設定、1CTA、公開後計測を完成させる。既存在庫は通常動画へ接続できるものから使う。

### 2. Shortsから外部URLへ直接送る導線は弱い

既存文書はShorts概要欄のURLを主導線として扱うが、Shortsの説明欄・コメントの外部URLはクリックできない。再生が増えてもサイトやnoteへ移らない構造になり得る。

**処方**: `Shorts → YouTube関連動画 → 通常動画のクリック可能な概要欄 → 外部` を標準とする。Shorts単体のUTM流入を主要KPIにしない。

### 3. 既存Shorts用エージェントへの通常動画兼務は責務過多

タイトル生成と配信物QAは、長い台本の論理構成、出典、図版、Red Line、商品導線の評価とは異なる。mode追加だけでは専門外の責務が混ざり、品質基準が曖昧になる。

**処方**: 動画マスター専用にGenerator/Evaluatorを1組だけ新設し、既存Shortsエージェントは狭い責務のまま残す。資格別agentは作らない。

### 4. 全資格・全媒体を同時に始めると一人運営の処理能力を超える

サイト記事数や図版数が多いことは機会だが、そのまま制作対象数になるわけではない。動画は台本、図版、音声、字幕、サムネイル、投稿、コメント、計測まで後工程が多い。

**処方**: 施工経験記述2本、総監2本の計4本に限定し、6週間で制作時間と送客を測る。技術士建設部門・コンクリート・Threadsは後続判定にする。

### 5. 管理画面に編集・投稿を持たせると既存ガードを二重化する

既存adminはローカルread-onlyで、外部操作はCLI・skill・workflow側に安全弁がある。管理画面へ公開ボタンを足すと、account assert、dry-run、承認gate、エラー処理を別実装することになる。

**処方**: adminは企画・QA・派生・公開・計測をjoinする読み取り専用ビューに限定する。操作は既存の承認済み経路へ渡す。

### 6. 動画ファイルをSSOTにすると容量と再利用性が悪化する

mp4は編集意図や出典を十分に表現できず、Gitへ置けば容量を圧迫する。媒体ごとに動画ファイルを起点にすると、同じ論点の台本とCTAが分散する。

**処方**: manifest、script、storyboardをSSOTにし、バイナリはR2へ置く。公開状態はruntime stateへ分離する。

## 2. 全findings

| # | 重要度 | Finding | 対応 |
|---|---|---|---|
| 1 | 高 | Shorts在庫200本に対し公開・回遊・計測が遅い | Phase 1を通常動画4本と導線へ限定 |
| 2 | 高 | Shorts外部URLを直接導線とする既存記述 | 関連動画経由へ変更 |
| 3 | 高 | 既存Shortsエージェントへ通常動画を兼務させる設計 | 専用Generator/Evaluator 1組 |
| 4 | 高 | 全資格・全媒体同時展開の危険 | 2領域4本、6週間のpilot |
| 5 | 高 | adminからの投稿は安全弁を二重化 | read-only固定 |
| 6 | 高 | mp4中心のSSOTは容量と差分管理に不利 | manifest/script/storyboard + R2 |
| 7 | 中 | 企画と公開状態が複数台帳へ分散し得る | creative/stateを分離しreconcileでjoin |
| 8 | 中 | 通常動画の16:9 rendererが未実装 | Phase 1の最小実装に含める |
| 9 | 中 | Shorts尺のプラットフォーム仕様と運用推奨尺が混同 | policyで分離 |
| 10 | 中 | ThreadsをX自動複製で始めると媒体特性を使えない | 会話brief・手動pilotを先行 |
| 11 | 中 | 1動画にサイト・note・ココナラを並べるとCTAが散る | 1 pack 1 primary CTA |

## 3. 採用条件

次の条件を守る限り、動画展開を採用してよい。

1. schemaと機械ゲートを動画量産より先に実装する
2. 最初の4本は手動レビューを必須にする
3. 通常動画への関連Shortsと主CTAを公開前に確定する
4. 外部公開は既存のapproval gateを通す
5. 6週間後に送客シグナルが無ければ自動化拡張を停止する
6. 全記事一括変換、全資格一括展開、Threads同時投入を行わない

## 4. 残る不確実性

- 通常動画4本で検索・関連動画流入を判断するにはサンプルが小さい
- YouTube Analyticsの取得項目とCI供給頻度は実装時に確定が必要
- note・ココナラ売上の動画起点attributionはUTMだけで完全には判定できない
- TTS中心の長尺動画で維持率を確保できるかは実測が必要
- 16:9図解の視認性はモバイルとTVの両方で目視QAが必要

これらは設計だけでは解消できないため、Phase 1の目的を「成功の証明」ではなく「継続判断に必要な観測の成立」とする。
