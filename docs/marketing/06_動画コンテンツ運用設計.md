# 動画コンテンツ運用設計

サイト・note・既存図版を、YouTube 通常動画を核とするストックコンテンツへ再編集し、Shorts・Instagram・X・将来の Threads へ展開するための横断設計。資格別の企画は各戦略文書が持ち、本書は資格をまたぐ運用構造・優先順位・投資判断を定める。

**制定**: 2026-08-21

**実装タスク**: `DN-0110`

**作業契約**: [.claude/knowledge/reference/video-content-policy.md](../../.claude/knowledge/reference/video-content-policy.md)

**批判的レビュー**: [動画コンテンツ運用設計_批判的レビュー.md](../reviews/critical/動画コンテンツ運用設計_批判的レビュー.md)

> [!important] 結論
> 動画展開は有効。ただし「記事を片端から動画化」するのではなく、**1つの動画パックを企画のSSOTとして、通常動画を検索・信頼の核にし、短尺・静止画・テキストへ派生する**。2026-09-05のユーザー決定により、QA済みの1級土木66本・2級土木18本と、コンクリート技士12本・主任技士16本は試験日前の通常動画公開を先行する。他資格と派生媒体の拡張可否は、従来どおりパイロットKPIで判断する。

## 1. この施策で解く問題

doboku-note には、サイト記事、note記事、過去問、施工経験記述、図解がすでに蓄積されている。一方、現在のSNS運用は媒体ごとの制作物が中心で、次の断絶がある。

1. サイト・noteの知識資産が「動画として検索される資産」になっていない
2. Shortsから購入までの導線が弱く、動画再生が成果に接続しにくい
3. 同じ論点を媒体ごとに別企画として作り、企画意図・出典・CTAが分散する
4. 完成数を増やしても、公開・回遊・売上まで追跡する共通台帳がない
5. 管理画面で動画パック単位の品質・派生・成果を横断できない

このため、制作本数ではなく、**悩み → 答え → 次の行動**が一貫した動画パックを運用単位にする。

## 2. 基本原則

### 2.1 マスターは動画ファイルではなく企画パック

mp4やwavは再生成可能な成果物であり、Git上の真実源にしない。真実源は、対象者の悩み、約束する答え、出典、台本、図解、CTA、派生先を束ねた `video-pack` とする。

```text
悩み・検索意図
  ↓
動画パック（企画・出典・台本・CTA）
  ├─ YouTube通常動画 ── 関連Shorts
  ├─ Instagram Carousel / Reels
  ├─ Xスレッド
  └─ Threads向け会話案（後段）
             ↓
      サイト / note / ココナラ
```

### 2.2 通常動画をストック、短尺を入口にする

- **YouTube通常動画**: 検索、理解、信頼を担う恒久資産
- **Shorts / Reels**: 発見と興味喚起を担い、通常動画へ送る
- **Instagram Carousel**: 保存と復習を担う
- **X**: 論点、反論、経験断片を会話化する
- **Threads**: 将来、質問・補足・対話に再編集する。Xの単純複製はしない

Shortsの説明欄・コメントに置く外部URLはクリック導線にならないため、ShortsはYouTubeの関連動画機能で通常動画へ送り、通常動画のクリック可能な概要欄から外部へ送客する。

### 2.3 1パック1悩み・1回答・1CTA

1本の通常動画で複数商品を並べない。主CTAは次の対応で選ぶ。

| 視聴者の悩み | 動画で答える範囲 | 主CTA |
|---|---|---|
| 用語・過去問が分からない | 論点、解き方、関連知識 | サイト記事 |
| 記述式の型・答案構成が分からない | 思考順序、失敗例、チェック項目 | note無料記事または有料マガジン |
| 自分の答案で合格できるか不安 | 自己診断の観点、添削前の準備 | ココナラ診断・添削 |
| 学習順序が分からない | ロードマップ、教材の使い分け | 資格別もくじ・サイト `/links` |

CTA URLを本文へ直接埋め込むのではなく、可能な限り商品・記事カタログIDから解決する。UTMは `utm_source=youtube&utm_medium=video&utm_campaign={packId}&utm_content=longform|shorts` を基本とする。

## 3. 優先するコンテンツ

初期パイロットは、素材量だけでなく、視聴者の悩みが明確で購入導線と近い2領域に絞る。

> [!important] 2026年 土木通常動画の公開枠
> 1級土木は既公開1本＋残り65本を2026-09-08〜10-03（1日2〜3本）、2級土木は18本を10-05〜10-22（1日1本）にAPI予約する。1級二次10-04、2級後期10-25の前に全本を公開し、10-04は投稿しない。公開順・時刻の機械可読な真実源は `video-content-status.json` の `publishAt` とする。

> [!important] 2026年 コンクリート系通常動画の公開枠
> コンクリート技士12本・主任技士16本は、2026-10-23〜11-19の毎日20:00 JSTにAPI予約する。両資格を交互に配信し、後半は主任技士の小論文・予想・直前総仕上げへ寄せる。11-29の試験前に全28本を公開し、最後の10日間を復習期間として残す。

### 3.1 1級・2級土木施工管理技士

優先テーマは施工経験記述。悩みが「何を書くか」「字数に収まるか」「この答案で減点されないか」と具体的で、サイトの無料解説、noteの想定工事・模範答案、ココナラの診断・添削が一本につながる。

パイロット例:

- 工事概要7項目で最初に失点する理由
- 安全管理の答案が一般論になる3つの原因

### 3.2 技術士総合技術監理部門

優先テーマは5管理・トレードオフ・記述式の考え方。サイトの大量キーワード・過去問と、noteの論文系商品を接続しやすい。

パイロット例:

- 5管理を列挙で終わらせずトレードオフにする方法
- 総監記述式で設問ごとの役割を取り違えない読み方

### 3.3 後続候補

技術士建設部門、コンクリート主任技士・診断士は、初期4本の制作時間と送客成果を確認した後に追加する。既存記事数が多いことだけを理由に全資格へ広げない。

> 建設部門は2026-09-01のユーザー決定で**パック準備（manifest・台本・QA）のみ先行**した。公開は本節のpilot判定通過後（整合の宣言は [08_YouTube戦略_技術士建設部門.md](./08_YouTube戦略_技術士建設部門.md) 冒頭）。
> コンクリート技士・主任技士は同日のユーザー決定で準備を先行し、その後の全件予約の明示承認により、QA済み28本に限って10-23〜11-19の公開へ進めた。この限定承認は建設部門・診断士・派生媒体を自動的に公開する根拠にはしない。整合の宣言は [09_YouTube戦略_コンクリート技士・主任技士.md](./09_YouTube戦略_コンクリート技士・主任技士.md) 冒頭。

## 4. 専用スキル・エージェントの設計

### 4.1 専用エージェントは2役だけ新設する

資格別・媒体別のエージェントは作らない。動画パック全体を扱うGenerator/Evaluatorの1組を新設する。

| 役割 | 名前（予定） | 責務 | 担当しないこと |
|---|---|---|---|
| Generator | `video-script-writer` | 悩みの定義、出典付き通常動画台本、ストーリーボード、派生ブリーフ、CTA案 | 事実の合否判定、レンダリング、投稿 |
| Evaluator | `video-content-qa` | 出典・正確性・構成・視聴維持・図版・Red Line・CTA整合を採点 | 台本修正、投稿、公開状態の照合 |

既存の `yt-shorts-title-writer` はShortsタイトル、`yt-shorts-publisher-qa` はShorts配信物の検査に限定して残す。通常動画の長い台本や商品導線を兼務させない。

### 4.2 ユーザーが呼ぶ入口は1つ

`/video-content`（予定）を薄いオーケストレーターとして新設する。

1. 既存資産と重複を検査
2. `video-script-writer` がパックを生成
3. `video-content-qa` が独立評価
4. 機械チェックを実行
5. 人の承認後にレンダリング・外部投稿工程へ渡す

スキル内へ生成・採点・投稿ロジックを複製しない。投稿は既存CLIまたはGitHub Actionsが持つ承認ゲートを維持する。

### 4.3 専用の投稿エージェントは作らない

投稿、R2退避、公開状態照合は決定論的なスクリプトとworkflowの責務とする。外部公開はユーザー承認なしに実行しない。エージェント数を増やすより、manifestと機械ゲートを強くする。

## 5. データと状態の分離

### 5.1 制作物SSOT

```text
content/sns/video-packs/{exam}/{slug}/
  video-pack.json      # 安定ID、悩み、対象者、出典、CTA、派生予定
  script.md            # 通常動画のマスター台本
  storyboard.json      # 画面・音声・図版・尺の設計
  thumbnail.json       # サムネイル生成仕様（任意）
```

動画パックは既存のInstagram、X、YouTubeディレクトリを置き換えない。派生先は既存チャネルの規約どおりに生成し、`video-pack.json` から参照する。

### 5.2 実行状態SSOT

```text
.claude/state/video-content-status.json
```

公開待ち、生成済み、公開URL、YouTube videoId、関連動画設定、派生物の状態、計測更新日時はruntime stateへ置く。企画ファイルを公開状態の更新だけで書き換えない。

既存 `.claude/state/youtube-schedule.json` はShorts投稿台帳として維持し、reconcile処理が共通statusへjoinする。移行時に二重台帳を作らない。

### 5.3 バイナリ

mp4、wav、字幕、レンダリングフレーム、生成済みサムネイルはR2へ置き、Gitへ追加しない。会社PCではパック・台本・QAを扱い、外部通信や重い生成はMacまたはGitHub Actionsで行う。

## 6. 管理画面

管理画面は**編集・投稿ツールではなく、判断のための読み取り専用ビュー**とする。

### 6.1 ナビゲーション

既存のコンテンツ中心IAに次を追加する。

```text
コンテンツ
└─ YouTube
   ├─ 動画パック
   ├─ 通常動画
   └─ Shorts

運用
└─ SNS状態

分析
└─ 動画成果
```

実装ルートは `/content/video` を基本とし、資格・フォーマット・状態はページ内フィルタにする。通常動画とShortsで別のファイルブラウザを増やさない。

### 6.2 一覧で見る項目

| 項目 | 出典 |
|---|---|
| タイトル、資格、悩み、検索意図 | `video-pack.json` |
| 元記事・図版、最終更新 | manifest + filesystem |
| 台本・ストーリーボード・QA | 制作物SSOT |
| 通常動画、Shorts、IG、X、Threadsの状態 | `video-content-status.json` |
| 主CTA、送客先、UTM campaign | manifest |
| 公開日、公開URL、関連動画設定 | runtime state |
| 視聴・送客・購入シグナル | CIが供給するsnapshot |

一覧では「未作成」「要QA」「承認待ち」「生成済み」「公開済み」「要再測定」「停止」を色だけでなく文字で示す。

### 6.3 詳細で見る項目

- 悩みと約束する答え
- 根拠記事・一次資料・使用図版
- 台本、ストーリーボード、サムネ仕様
- QAの軸別得点とBLOCK理由
- 派生コンテンツと公開状態
- CTA、関連動画、UTMの整合
- 公開前後の計測推移

### 6.4 管理画面に置かないもの

- 台本のインライン編集
- 任意コマンド実行
- YouTube・X・Instagram・noteへの公開ボタン
- APIトークン、Cookie、Playwright profile
- ライブAPIへの直接依存

管理画面はCIが供給したsnapshotを読む。失敗時は0件表示にせず「未取得」「期限切れ」を明示する。

## 7. 品質ゲート

### 7.1 機械チェック

`check-video-content`（予定）で最低限、次を検査する。

- manifest schema、packId一意性、必須ファイル
- sourceRefの実在と公開可否
- CTA ID・URL・UTMの整合
- storyboardの尺、画面比率、字幕長、最小フォント
- 音声と画面の対応、無音・黒画面・末尾切れ
- 通常動画とShortsの重複率、逐語読み上げの過多
- 関連動画IDと公開状態
- Git内のmp4/wav混入
- statusの孤児・二重videoId・鮮度

### 7.2 意味評価

`video-content-qa` は次の6軸を0〜3で採点し、平均2.0以上かつBLOCKなしを公開候補とする。

1. 悩みへの適合
2. 事実・出典・試験制度の正確性
3. 動画としての理解・視聴維持
4. 図版・音声・字幕の整合
5. 既存記事との差別化とRed Line
6. CTA・ファネル・計測可能性

資格固有の事実監査が必要な場合は既存の専門Evaluatorへ委譲し、`video-content-qa` が専門知識を再実装しない。

## 8. 段階実装

### Phase 0 — 契約を固める

- `video-pack.json` schema、status state machine、UTM、CTA解決規則を確定
- Shortsの外部リンク前提、尺の旧記述、cron自走記述など既存docのドリフトを修正
- `check-video-content` のfixtureと偽PASS防止テストを作る

### Phase 1 — 4本の手動パイロット

- 16:9レンダラーと字幕・音声の最小経路を実装
- 施工経験記述2本、総監2本を制作
- 各通常動画からShorts 2本、IG 1組、X 1スレッドを派生
- Shortsに関連動画を設定し、通常動画の主CTAを1つに固定

### Phase 1.5 — 1級・2級土木の試験前公開（2026-09-05 決定）

- `video-content-qa` で合格済みの1級66本・2級18本を対象とし、新規に未監査の台本は混ぜない
- 既公開の1級1本を除く83本を、上記の試験前公開枠へ割り当てる
- `youtube.json` はカタログから主CTAを1件だけ解決し、YouTube用UTM・動画/サムネイルSHA-256・`publishAt`を固定する
- API投入は同一タイトル再利用と状態照合を行う再開可能なバッチとし、YouTubeの日次上限を検出したら停止して翌日に続きから再開する
- 土木84本の先行公開は、他資格・Threads・TikTokまで無条件に量産する根拠にはしない

### Phase 1.6 — コンクリート技士・主任技士の試験前公開（2026-09-05 決定）

- `video-content-qa` 合格済みの技士12本・主任技士16本だけを対象とする
- 10-23〜11-19の毎日20:00 JSTへ割り当て、11-29試験の10日前に全本を公開し終える
- 技士・主任技士を前半で交互に配信し、後半は主任技士の小論文・予想・直前対策を優先する
- この28本の限定承認は、建設部門・診断士・Shorts等の公開ゲートを解除しない

### Phase 2 — スキルと2エージェント

- `/video-content`、`video-script-writer`、`video-content-qa` を新設
- skills/agents registryとcoupling gateを同時更新
- 既存Shorts用エージェントとの責務境界をテストで固定

### Phase 3 — 管理画面とCI計測

- `/content/video`、SNS状態、動画成果ビューを追加
- CIで公開状態・YouTube Analytics・GA4 UTMをsnapshot化
- 未取得・期限切れ・status driftを表示

### Phase 4 — 派生の拡張

- 既存図版からCarousel/Reels/Xを生成
- Threadsは単純クロスポストではなく、質問・反論・補足の会話案として小規模実験
- 実績のあるテーマだけ他資格へ展開

### Phase 5 — 継続・停止判断

パイロット公開後6週間で評価する。次のいずれも観測できない場合、自動化拡張を止め、通常動画のテーマ・CTA・尺を見直す。

- Shortsから関連通常動画への流入
- `utm_source=youtube` のサイト・note流入
- noteまたはココナラへの遷移
- 動画起点の販売・相談シグナル

## 9. KPI

| 層 | 主指標 | 補助指標 |
|---|---|---|
| 発見 | Shorts→関連動画流入、インプレッションCTR | 再生数、登録者 |
| 理解 | 平均視聴率、冒頭30秒維持率 | 高評価、コメント |
| 送客 | YouTube UTM sessions、CTAクリック | `/links`経由遷移 |
| 収益 | note・ココナラの動画起点売上/相談 | 商品ページ閲覧 |
| 生産 | 1パック制作時間、派生再利用率 | 生成本数 |

登録者数と広告収益は参考値とし、主KPIにしない。

## 10. 禁止事項

- QA・出典・CTA・公開台帳を持たない全記事の一括動画化
- 出典未確認のTTS読み上げ量産
- サイトや有料note本文の逐語転用
- Shorts説明欄の外部URLを主導線とみなすこと
- 1動画に複数の主CTAを置くこと
- 生成物mp4/wavをGitへ蓄積すること
- 管理画面からの投稿・任意shell実行
- 資格別、媒体別に同じ役割のエージェントを増殖させること
- KPI確認前のThreads・TikTok同時展開
- ユーザー承認なしの外部公開
