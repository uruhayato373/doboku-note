# 検索キーワード戦略 — 狙う読者 × 検索語 × 受け皿のページ

最終更新: 2026-10-13

## 結論

- 検索は **4 つのクラスター** で持つ。資格名・土木公務員・施工管理の転職・技術図書（共通仕様書など）。クラスターごとに狙う読者と受け皿のページを決め、機械の正本は [`search-strategy.json`](../../config/search-strategy.json)。
- 順位は 2 つの帯で見る。**上位の帯**（`striking.minPosition` より上・既定 10 位以内）と **改善候補の帯**（`minPosition`〜`maxPosition`・既定 11〜30 位）。境目は [`search-strategy.json`](../../config/search-strategy.json) の `striking` だけが持ち、画面・CLI の表示名もそこから作る。
- 改善の中心は **改善候補の帯で表示がある検索語を上位の帯へ上げる** こと。新しいページを増やすより、既に表示されているページの手直しの方が早く効く。
- KPI ツリー（[15_KPIツリー.md](./15_KPIツリー.md)）の「サイト」の段に、クラスター別の **上位の帯の検索語数** と **表示回数** を置く。順位の件数そのものを売上の代わりにしない。
- Google 検索は流入全体の一部（自然検索の大半は Bing。[measurement-incidents.md](../../.claude/knowledge/reference/measurement-incidents.md)）。改善候補（ページ単位）は Google の検索語×ページ集計（GSC）で出す。Bing は毎週の CI（`fetch-bing-webmaster`）で検索語とページを別々に取れるが、検索語×ページの組が無いので、クラスター別に「上位の帯の検索語数」と「改善候補の帯の検索語」だけを別枠で出す（`npm run report-search-opportunities` の [Bing]）。2026-09-27 時点で資格名クラスターの Bing の検索語 102 件はすべて 1 桁で、11〜30 位の候補は 0 件＝Bing では既に上位にいて、伸ばす余地は Google 側にある。

## クラスター

| クラスター | 狙う読者 | 検索語の型 | 受け皿 | 2026-08-25〜09-21（旧境界の集計：1 桁＝10 位以下） |
|---|---|---|---|---|
| 資格名 | 受験を決めた人・受験中の人 | 資格名＋解答例・年度・論文・キーワード | `/exam/` の過去問・ガイド・キーワード | 表示 392・1 桁 22・11〜30 位 39 |
| 土木公務員 | 自治体・国の土木職（発注者） | 公務員・土木職・発注者＋資格・実務 | 資格ハブ・公務員向けガイド・`/practice/` | 表示 12・1 桁 1・11〜30 位 6 |
| 施工管理の転職 | 施工管理を続けるか迷う人 | 転職・辞めたい・年収・キャリア | 1 級土木のキャリア記事・`/topics/` | 表示 32・1 桁 0・11〜30 位 4 |
| 技術図書 | 共通仕様書・基準書を実務で引く人 | 発行元（地整・都道府県）＋共通仕様書 | `/standards/` | 表示 236・1 桁 22・11〜30 位 18 |

- **資格名** は商品（note・ココナラ）に最も近い。年度の解答例（「1級土木 2次 解答例 令和7年」11 位など）とキーワード記事（技術士 CPD）が 11〜20 位に多い。
- **土木公務員** は運営者の経歴（元・自治体の土木職）が最も効く。検索量は小さいが競合が少なく、1 ページ目に届く位置（10〜15 位）にいる。方針は [13_土木公務員SEO戦略2026-08.md](./13_土木公務員SEO戦略2026-08.md)。
- **施工管理の転職** は表示が小さく、平均 60 位台。アフィリエイト（転職一本）の入口なので、既存のキャリア記事で年収・辞めたい理由の検索意図に答えているかを先に直す。
- **技術図書** は `/standards/` 公開後 1 か月で表示 236 まで伸び、発行元名＋共通仕様書の語が 10〜12 位に並ぶ。ページ名・見出しに発行元名と「土木工事共通仕様書」を正確に入れ、章の目次から探しやすくするだけで 1 ページ目に入る見込みがある。国・都道府県の技術図書を「見やすく整理した入口」として広げるのは、このクラスターで 1 桁が取れてから。

## 改善サイクル

直す→記録→本番反映→計測→判定を、週次レビューがその週のうちに回す。改善はカードに積んで待たせない（「起票済」の状態は作らない。2026-10-13 にカードで待っていた 13 件のうち 9 件は 9/27 に直っていたのに計測へ進んでいなかった）。記録は実験台帳（`data/business/experiments.json` の kind `search-strategy`・EXP-###）。順位の帯・週の改善件数・計測の型は `config/search-strategy.json`（`striking`・`cycle`）だけが持つ。

1. **候補を出す（機械）**: `npm run report-search-opportunities` がクラスターごとに、改善候補の帯（既定 11〜30 位）で表示のある検索語をページ単位に束ねる。候補にするのは、直したあと効果を判定できる表示（計測の型 `cycle.measure.minVolume`。設定に別の下限を持たない）があるページだけ。表示の少ないページは、表示が増えたら自動で候補に入る。旧 URL（`/docs/`）・受け皿外（判断前）・計測の終わっていない実験があるページは直さない。判定済みのページは前回の結果つきで候補に戻る。
2. **直す（週次・その週のうちに）**: 週次レビューが、直してよい候補を表示の多い順に `cycle.improvePerWeek` 件、develop で直して commit・push する。検索語に対して、タイトルと冒頭で答えているか、発行元名・年度などの語が正確か、関連ページからリンクされているかを直す。新しいページは作らない。
3. **記録する**: `npm run search-improvement -- record --page <path> --change "何を直したか" --commit` で EXP を作る（commit は develop に入ったもの・基準は直す前の GSC 集計・段階は「本番反映待ち」）。squash 前の feature の commit は本番に入らないので記録を断る。
4. **計測する（CI）**: 毎週の計測（fetch-metrics）が `search-improvement sync` で記録した commit を含む最初の本番デプロイを探し、その日を境目に計測を始める。`measure-experiments` が「対象ページ × 直す前の検索語」の平均順位を前後 `cycle.measure` の日数（既定 28 日）で比べる。
5. **判定する（週次）**: 事後窓が確定すると判定待ちになり、週次レビューが `search-improvement -- close` で結果と学びを残す。月次は `search-improvement -- monthly` でクラスター別に数え、改善 0 が続くクラスターは検索意図と受け皿を見直す。

- 検索順位の改善はこのサイクルが唯一の経路。「観察だけして直さない」並行経路は置かない（2026-10-13 に SEO Rank Watch を廃止して統合。稼働した 2026-09-14 以降、改善実験は 0 件で、観察中のページがここの候補から外れていた）。計測が終わったページは候補へ戻り、サイクルは止まらない。過去の観察記録 `data/gsc/rank-watch/` は不変アーカイブ。
- 検査: `npm run check-search-improvements`（CI ゲート）が、改善の記録の無い EXP と、起点が検索キーワード戦略のカード（ページの順位改善をカードに積むこと）を止める。改善以外の作業のカードは「**実験**: なし（理由）」を書く（`search-improvement -- link --none`）。週次の要処置は週次の点検（`check-search-triage`・`quality:audit:weekly`）が週次レビューで読まれる。

- **週次の処置（全件・カードに回さない）**: 計測のたびに `npm run search-improvement -- triage` が、判断の要る候補と実験を「要処置」と「観察中」に分ける（実験は、判定待ち＝close、カード完了から期限を過ぎても本番デプロイに入らない＝commit を確かめて sync）。週次レビューは要処置を 0 件にして終える（完了条件 `triage --check --weekly`＝今週の改善件数も数える）。判断は記録し、期限まで観察し、残れば次の手を打つ。
  - **受け皿外**（クラスターの受け皿の外のページが出ている）: 受け皿に加える（`decide --accept`）か、狙いのページへ内部リンクで誘導する（`decide --route-to`・リンクはその週に足す）。判断は設定のクラスターの `pageDecisions` に理由と日付で残る。誘導から `cycle.legacyGraceDays` を過ぎても出ていれば判断をやり直す。
  - **旧 URL（`/docs/`）**: 本文は直さない。転送・転送先の公開・旧 URL を指すサイト内リンクを機械で確かめ、崩れていれば直す。転送（か登録リクエスト）から `cycle.legacyGraceDays` を過ぎても出ていれば、運営者の承認を得て正規 URL を登録リクエストする（`gsc-indexing:request`。送信は indexing-history に残り、次の週から観察に戻る）。

## 月次で見ること

- クラスター別の表示・クリック・上位の帯の検索語数・改善候補の帯の検索語数と、重ならない直前の期間との差（日数は集計の窓どうしで 1 日前後ずれることがある）。
- 判定済みの実験（`npm run search-improvement -- status --json`）の成否をクラスター別に数える。効果なしが続くなら、検索意図とページの中身がずれていないかを見直す。
- クラスターの追加・削除（検索語の型 `queryPattern`）は、週次の処置で同じ種類の受け皿外が続いたときに、`search-strategy.json` とこの文書を同時に直す。受け皿のページの判断は週次（上の `pageDecisions`）。
