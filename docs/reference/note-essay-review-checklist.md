# note 模範論文（総監記述式）レビュー手順書

`docs/note/magazines/総監模範論文-*/` および `docs/note/magazines/総監記述式-R8予想問題集/` 配下のフル模範論文を公開レベルに引き上げるための実施手順。`docs/reference/content-principles.md`「note 模範論文の品質原則」と対をなす。

> **重要（2026-06-16 方針転換・旧「決定2026」を撤回）**: ペルソナ模範論文は**全14ペルソナで R03-R07 ＋ R8予想2記事（`R08-yosou-1`/`-2`）を作成する**（真実源 → [総監マガジン構成_決定2026.md](../note/技術士総監/総監マガジン構成_決定2026.md) 2026-06-16追補）。旧「決定2026」の **「per-persona R8予想は作らない・evergreen純化・R8は横断フラッグシップに一本化」は撤回**（実装が原則と逆にドリフトし 14中12ペルソナが既にR8同梱だったため、整合の最小コストは「2つに足す」と判断）。**トレードオフ＝全記事パックで R8 が per-persona と横断「R8予想問題集」で二重化するのを受容**（横断R8予想問題集はテーマ駆動フラッグシップとして併存）。よって R08予想2記事化（Step 6d 等）は legacy でなく**全ペルソナの標準工程**。なお 2026-06-12 に削除されたゼネコン/河川コンサルの per-persona R8予想は本転換により**再作成済（PR #249）**、自治体道路担当はデモ1本のため `R08-yosou-1`/`-2` 2記事への拡充が残作業。

## 目的

模範論文を**本番再現可能な字数（各施策600字以内）**かつ**読者がそのまま参考にできる品質**で公開する。試行錯誤の繰り返しを避けるため、評価軸を **字数 → 散文性 → 監理可能性 → 専門度 → 白書根拠** の順で固定する。

> [!note]
> **記事の導入・無料部分・販売導線**（論文本文の外枠）は [note-selling-structures.md](note-selling-structures.md)（売れる9型）を観点に組む。模範論文（＝商品本体）の字数・散文性・専門度は上の評価軸が優先で、9型は「読者の悩みをつかみ購入理由を作る」フック〜導線にだけ適用する。

> [!important]
> **本書は `cem-essay-writer`（Generator）／`cem-essay-qa`（Evaluator）のランブック**（2026-06-18 新設）。総監 note 記述式（persona模範論文/R8予想/設問3バンク/クロストレードオフ）の生成・採点はこのペアが担い、本書の Step 0〜6f が評価軸・公開ゲートの真実源。親はこのペアを起動し、配線（note-magazines.ts/note掲載文.txt/PDF spec）・公開後 URL 反映・commit を担当する。サイトの `r0X-essay-{attr}` は別物（`/pe-essay-draft`・無料サイトページ）。

## Step 0: ペルソナ採否（著者の真正経験座）

**新規ペルソナの横展開・公開に着手する前に、「著者が一人称で語れる座か」を確認する。** 模範論文の差別化の源泉は「合格者が実務経験を活かして執筆」という真正性であり、経験座を外れると売り文句が虚偽になり（景表法/ステマと同根）、現場固有の制度・用語でドメイン誤りも生じる。

著者ペルソナ＝**元・地方自治体土木職（発注者）**（SSoT: `src/config/author.ts`）。

| 区分 | 例 | 判断 |
|---|---|---|
| 真正（発注者・自治体） | 河川/都市計画/道路/下水道/上水道/砂防/港湾/公園緑地/技術基準/契約調達 | **GO**。全ペルソナ新標準で完成済（建築営繕は建築職領域のため不採用・削除。アセットマネジメント担当は道路担当A案と論点重複＋B案が建築営繕領域に抵触のため2026-06-11 廃止削除。農業農村整備担当は農業土木職＝農業部門（農業農村工学）の領域で著者の土木職の経験座外のため2026-06-11 廃止削除＝建築営繕と同基準） |
| 異業種・民間 | 電力会社土木（民間ダム/発電）・NEXCO（高速道路会社）・鉄道・民間プラント 等 | **不採用**（2026-06-09 電力/NEXCO 除去 commit fc433b7ad） |
| 受注者系 | ゼネコン・各種コンサル（受注者の座） | **GO（2026-06-10 ユーザー決定＝売る）**。ただし著者の真実経験座（発注者）ではないため、受注者視点を厳守（発注者権限の施策＝仕様書義務化/条例改正/補助金/税制は書かない。受注者は施工・調査設計の高度化/技術開発/社内体制/提言まで）。一人称の実体験は捏造せず一般専門知識・白書ベースで credible に描く |

着手前にこの判定を通し、異業種は作らない。受注者系は売るが受注者視点の制約を厳守（詳細は引き継ぎ `docs/handoffs/2026-06-10-pe-essay-contractor-personas-cloud.md` §1）。

### Step 0b: 専門分野ラベルの正確性（技術士選択科目との対応）

ペルソナの「専門分野」枠付け（こんな人のため／前提／立場 等の "○○分野の発注・監督経験" 表現）は、**そのペルソナの分野に正しく対応する技術士選択科目**を使う。**他部門・他科目の選択科目名を流用しない**（テンプレ流用時に紛れ込む事故に注意）。

| ペルソナ | 正しい選択科目（部門） |
|---|---|
| 河川 | 河川砂防及び海岸・海洋（建設部門） |
| 都市計画 | 都市及び地方計画（建設部門） |
| 港湾 | 港湾及び空港（建設部門） |
| 道路 | 道路（建設部門） |
| 上水道 | 上水道及び工業用水道（**上下水道部門**） |
| 下水道 | 下水道（**上下水道部門**） |

**建設部門外（上下水道・農業・森林等）のペルソナに、建設部門の科目（施工計画・施工設備及び積算／建設環境 等）を当てない**。迷う／分野が建設部門外なら、選択科目名を出さず**役割ベースに一般化**する（例「下水道事業の発注・監督経験」「工事の積算審査・施工監督など発注者としての実務経験」）。業務記述としての施工計画・積算・環境配慮の語は可（選択科目ラベルとしての枠付けのみ避ける）。2026-06-10 に下水道で誤枠付け（建設部門科目）を一般化是正（commit 3884d7bc0）。詳細メモリ [[feedback_essay_persona_field_label]]。

## Step 1: ベンチマーク確定（R7 過去問の Read）

該当ペルソナの R7 過去問模範論文を Read し、以下を把握する。

- 設問(1)・(2)・(3) の各施策の**文字数**
- 立場ラベル（道路維持課 課長補佐 等）
- 設問(2) 各施策のトレードオフ軸の組み合わせ（情×安、経×人 等）
- 設問(3) で扱う国家施策の語彙レベル

これが**自施記事の到達目標**となる。R7 が 600 字を多少超えていれば、同水準が許容ライン。

## Step 2: 字数実測（最優先・決定論ツール）

**真実源ツール**: `scripts/essay-shisaku-charcount.mjs`（施策ブロックの CJK 字数を計測し 600 字超過を検出する決定論ゲート）。

```bash
node scripts/essay-shisaku-charcount.mjs "総監模範論文-{persona}" --detail   # ブロック別明細
node scripts/essay-shisaku-charcount.mjs "総監模範論文-{persona}" --strict    # 超過1件で exit 1（ゲート）
```

- 施策見出しは **`### 施策N:` / `### 方法N` / `### 戦略N`** で統一する（R08 予想等で `**施策N:**` 太字インラインにすると 2 施策が 1 ブロックに合算され誤計上する。必ず `###` 見出しにする）。
- ブロックは `##`/`###` のどちらでも区切られる（修正済み）。設問1（2 枚＝1200 字枠）は別枠。

**判定基準**：

| 字数 | 判定 |
|---|---|
| 585〜600 字 | ✅ 本番再現可能・マージンも確保 |
| 575 字未満 | △ 余白が大きい（内容追加の余地あり） |
| 601 字以上 | ❌ **必ず圧縮**（許容範囲なし） |

**「答案用紙 1 枚以内」は厳密な上限**。R7 A案も 618〜657 字で超過しているが、R7 を「同水準＝許容」の基準にしてはならない。**601 字以上は無条件で圧縮対象**。超過があれば最初に「内容議論より先に圧縮」と順序宣言。

## Step 3: 散文性チェック（答案は必ず散文）

```
grep -nE "^- \*\*(内容|根拠|効果|障害|課題|方法|利活用|リスク|克服)" article.md
```

**答案本文（設問1〜3 のフル解答）は流れる散文段落で書く**。`- **効果**: …` `- **障害**（A × B）: …` のような箇条書き化は**禁止**（本番答案は散文で書くため）。検出したら **河川／下水道／都市計画担当（散文の真の基準＝`答案箇条書き0`・`箇条書き混入0`）** と同じ散文段落へ統合する。トレードオフの分野名（経済性管理 × 社会環境管理 等）は**散文の中に**明示する（箇条書きラベルにしない）。

> **基準の注意（2026-06-10 是正）**: 道路担当は散文の基準ではない（`答案箇条書き38`・`R08旧式`）。散文の手本は **河川／下水道／都市計画** の3ペルソナ（いずれも `答案箇条書き0`・`箇条書き混入0`）。`✗散`（箇条書き混入）を「道路と同形式だから許容」と判断してはならない。**`答案箇条書き(全体)=0` かつ `箇条書き混入=0` を必須合格条件とする**。
>
> **常習箇所＝R05（SWOT 戦略）の設問(3)「障害と克服策」**。`**障害と克服策**（トレードオフ）:` の直後を `- **障害**（X × Y）:` `- **克服策**:` と箇条書きにしがち。河川R05と同じく**1段落散文**（「X管理 × Y管理 の観点では、〜一方、〜。これに対し、〜。」）へ統合する。`**方針**`/`**具体的方策**` 段落・SWOT項目（`- **S1**` 等）・設問(1)の `- **経営資源/アウトプット**` 箇条書きはゲート非対象（河川も箇条書き）で変更不要。

**修正前**:
```markdown
- **内容**: ...
- **根拠**: ...
- **効果**: ...
```

**修正後**:
```markdown
内容として〜。〜することで〜（根拠）。効果として〜（経済性管理）、〜（情報管理）。
```

**修正前**:
```markdown
- **内容**: ...
- **根拠**: ...
- **効果**: ...
```

**修正後**:
```markdown
内容として〜。〜することで〜（根拠）。効果として〜（経済性管理）、〜（情報管理）。
```

## Step 3b: 導入部の文体統一（ですます調）

**導入部（記事冒頭 〜 `## 試験問題`/`## 予想問題`/`## A 案` の直前）は ですます調で統一する**。読者向けの「こんな人」「この記事でわかること」「magazine 案内」「intro 段落」「本記事の構成」は すべて「〜です／〜ます／〜ください」。**答案本文（A 案・B 案の設問解答）は である調**（論述式）で、ここは別系統＝混在ではない。

導入部の散文に である調（`〜である。` `〜であり、` `〜だった` `〜だ。` `〜ではない。`）が混じると文体混在。検出：

```
node scripts/essay-shisaku-charcount.mjs "{persona}"   # 「導入部文体混在(警告) N」を確認
```

混在は**警告**（`--strict` の exit には含めない＝既存記事の許容は人間判断）だが、**新規生成時は導入部をですますで書き、警告 0 を目指す**。注: 「であること（です）」のような連体形・「のではなく」のような連結語は である調ではない（ツールも除外済み）。

## Step 3c: 導入部の段落を文単位で細かく区切る（note 可読性）

**導入部の散文段落は 1 文（。）= 1 段落を基本に細かく分割する**。note はモバイル中心で、1 段落に複数文を詰めると読みづらい（intro ナラティブ・`**本記事の使い方/構成**`・`**R8 予想の根拠**`・magazine 案内が対象）。答案本文（`## 試験問題` 以降）・見出し・箇条書き・括弧内の `。` は分割しない。

既存記事への一括適用は専用スクリプト（冪等・導入部のみ対象）を使う：

```
node scripts/split-essay-intro-paragraphs.mjs 自治体下水道担当 --dry   # プレビュー
node scripts/split-essay-intro-paragraphs.mjs 自治体下水道担当         # 適用
```

frontmatter 後〜「## 試験問題/予想問題/A 案」直前の非構造行の内部「。」のみを「。\n\n」へ置換し、末尾の。や 。」、見出し・箇条書き・URL・引用は分割しない。再実行しても変化しない（冪等）。

> **ツール使い分け**: 上記 `split-essay-intro-paragraphs.mjs` は essay マガジンの**導入部に特化**（1 文 1 段落・誤分割回避ロジックあり）。一般の note 記事（入口/ガイド/キーワードページ等）の本文段落を短くするときは汎用ツール `npm run note-reflow -- [--target N] <file|dir>`（`scripts/reflow-note-paragraphs.mjs`、>120 字を文境界で再パッキング・1〜2 文/段落・語句不変）を使う。note-reflow も「## 試験問題」以降の答案本文は自動保護するため essay 記事に誤適用しても答案は割れない。真実源: `content-principles.md §14-e`。

PDF は `試験問題 → 採点者視点` のみ収録のため、導入部の段落分割は **PDF に影響しない**（再生成不要）。

## Step 4: 監理可能性チェック

設問(2) 各施策で、ペルソナの立場（例: 道路維持課 課長補佐）が**自前で実施できる範囲**に収まっているか確認。

**越権施策の典型例**：
- ゼロトラスト移行（CIO 部局所掌）
- 庁内ネットワーク全面整備（情報政策課所掌）
- AI モデル・ベンダーの選定（情報政策課・契約検査課所掌）
- 共同調達のリード（契約検査課所掌）

該当する場合は、「**情報政策課と連携のうえ協議に参画する位置づけ**」のように所掌調整の枠組みに書き換える。**立場ラベルに「(情報化・DX 担当)」などの兼務付与をして越権を正当化することは禁止**。

## Step 5: 専門度チェック

設問(3) の用語をスキャンする：

```
grep -nE "EU AI Act|SBOM|AI-SBOM|第三者認証|リスクベース規制|認証要件法制化|基盤モデル|サプライチェーンリスク評価" article.md
```

**NG リスト**（撤去対象）：
- EU AI Act、AI-SBOM、ソフトウェア SBOM 国際標準
- 第三者認証制度、認証要件法制化、認証機関
- リスクベース規制、用途別認証制度
- 基盤モデル、サプライチェーンリスク評価、SBOM

**OK リスト**（推奨語彙）：
- リスクに応じた規制、定期見直し条項、監督権限の集約
- 人材育成、社会受容性、代替チャネル、救済制度、透明化
- 既存政府指針、AI 関連法、所管集約、分野横断統括機関

NG 用語が混在していれば、OK 語彙へ書き換える。**規制側 1 施策＋人材／社会受容性側 1 施策**で構成を整える。

## Step 6: 白書根拠チェック

「なぜ R8 でこのテーマが出題されると予想するか」セクションの白書言及を、WebSearch で章構成・原表現と照合する。

**検証対象**：
- 白書名・特集タイトル・章番号・章タイトル
- 引用している用語が原文・公的サマリーに登場するか

**確認できない用語は撤回または広い概念語へ置換**：
- ハルシネーション → 偽・誤情報の流通
- 生成 AI 悪用 → 巧妙化・高度化するサイバー攻撃
- ランサムウェア（情報通信白書由来として書く場合は原文確認必須）

「予想問題本文」中の白書引用は出題者風の再構成が許されるが、根拠説明セクションは厳密に。

## Step 6b: 引用記号（blockquote）の濫用チェック

```
grep -nc "^> " article.md
```

**導入の枠組み文（「本記事の構成」「本論文はテンプレートとして…」「A案/B案の対象者注記」等）を blockquote `>` で書かない**。これらは著者自身の説明文であり「引用」ではないため、引用記号は意味的に不適切。**通常の段落**で書く（強調したい行は `**太字**` の通常段落、注意喚起は `<Callout>` でなく素の段落で可）。blockquote は「外部の規程・白書原文・設問前文の引用」など真に引用である箇所のみに限定する。

## Step 6c: 記事ごとアセット（カバー・ハッシュタグ）必須

各記事（`{persona}/{RXX}/`）に以下が**揃っているか**確認する。マガジン単位の `_cover.png`/`hashtags.txt` とは別に、**記事ごと**に必要：

- `img/cover.png`（＋ `cover.svg`）: `node scripts/generate-note-covers.mjs "{persona}"` で生成（部分一致で当該マガジン配下を一括生成）
  - **frontmatter `cover.banner` は短い単一テーマ＋「｜3,000字級フル論文」に留める**。長い銘（例「資源循環 × サプライチェーン強靭化｜…」）は `bannerFontSize` 下限48pxに張り付いて改行が崩れる（河川R08で発生）。完全テーマは `cover.hiSuffix` とタイトルに既出なので重複させない。生成後は cover.png を必ず目視確認
- `hashtags.txt`: `/note-hashtags` スキルで生成（記事の論点に沿った 80〜90 個・単一行 space 区切り。本文には入れない＝[[feedback_note_prepublish_verify_not_proxy]] の SoT 規約）

```
ls docs/note/技術士総監/magazines/総監模範論文-{persona}/{RXX}/img/cover.png
ls docs/note/技術士総監/magazines/総監模範論文-{persona}/{RXX}/hashtags.txt
```

## Step 6d: 見出し構成チェック（正準=自治体道路担当）


ペルソナの見出し構成を正準（自治体道路担当）の構造不変条件で検査する。

**R03〜R07（過去問）**: `## 試験問題` / `## A 案`・`## B 案`（各「（前提条件）」付き） / 各案 `## A 案 設問（１）(２)(３)` / `## 採点者視点でのチェックポイント` を備える。設問(2)(3)の各施策は `### 施策 X-N:` 見出しで区切り、本文は散文化する（設問(2)＝`**内容**:`／`**効果**:`／`**障害と克服策**（トレードオフ）:`、設問(3)＝`**①施策の内容**`／`**②有効性と実現性**`／`**③重大な障害と克服策**`）。**各 `### 施策` ブロックは ①②③ 合算で 600 字以内**（Step 2 で実測）。手本＝自治体道路担当 R06。

**R08予想（legacy＝既存 R8章ありペルソナの保守時のみ。新規ペルソナでは作らない＝決定2026）／予想問題ごとに2記事化**: チェッカーは旧来の単一 `R08-yosou` を「要2記事化」で弾く。予想問題が2つ（例: 気候変動適応 / 資源循環）なら **`R08-yosou-1` / `R08-yosou-2` の2記事**へ分割し、**各記事に A 案・B 案の両方**を収録する（＝各予想テーマを2つの管理対象パターンで解く）。元データが「A案=予想1／B案=予想2」の非対称構成なら、各テーマに**欠けている案を新規生成**して対称化する。各記事の本文は R03〜R07 と同じ過去問形式（`## 試験問題` ＋ `### 出題予想根拠` / `## A 案`・`## B 案` / 設問（１）〜（３）/ `## 採点者…`）。手本＝自治体下水道担当 `R08-yosou-1`/`-2`。

> **予想テーマの選定理由の表現（2026-06-10 是正）**: 予想テーマは白書重点テーマ＋的中率から「**出題が予想される**」ため選定する。「**ペルソナで論じやすい**（から取り上げる）」と書いてはならない（論じやすさで選んだのではない、というユーザー指摘）。出題予想根拠の直後は「本記事では、その中でも出題が予想される「{テーマ}」を{ペルソナ}の視点で取り上げます。」の型で接続する。複数テーマから絞る場合も「出題可能性が高い上位N テーマ」とし「論じやすい上位…」としない。`grep -rn "論じやすい" docs/note/技術士総監/magazines/` = 0 を確認する。

## Step 6e: 印刷用PDF（記事別）の生成・配置・冒頭訴求

1. spec を作成（道路担当 `scripts/pdf-specs/総監模範論文-自治体道路担当.json` を複製し srcDir/out を差し替え）
2. 記事別PDFを各記事dirへ直接生成：
   ```
   node scripts/magazine-to-pdf.mjs --spec scripts/pdf-specs/{persona}.json --in-place
   ```
   （`--in-place` で各 `{RXX}/` 配下に `{out}.pdf` を配置。試験問題＋模範論文のみ＝note CTA・採点者視点・出題予想根拠は除外）
3. 各記事冒頭「**この記事でわかること**」末尾に PDF 訴求 1 行を追加（例:「**本記事の模範論文を印刷できる PDF 付き** — 答案用紙への手書き書き写し練習に使えます（購入者は本記事からダウンロード可）」）
4. **各記事末尾に PDF ダウンロード導入文ブロックを追記**（note で末尾に PDF を添付する際、唐突にならないよう導入文を置く）。フッターと同じ `**太字ブロック**` 形式（`##` 見出しにしない＝見出しチェッカー非干渉、pdf-spec の include 範囲〔試験問題〜採点者視点〕外なので PDF 自体には含まれない）。**太字内に全角括弧を入れない**（`｜` 区切り）。文面:
   ```
   ---

   **印刷用 PDF｜本記事の模範論文**

   本記事の模範論文（試験問題と A 案・B 案のフル解答）を、そのまま印刷できる PDF にまとめました。

   答案用紙への手書き書き写し練習や、試験直前の読み返しにご活用ください。
   ```
   （note 可読性のため**1文 ≒ 1段落**で区切る。フッターの magazine CTA 閉じ段落も同様に文単位で区切る）
   この導入文の直後（note エディタ上）に PDF ファイルを添付する。一括追記は `.tmp/append-pdf-leadin.mjs` 相当（冪等・CRLF保持）で全記事へ。

## Step 6f: マガジン掲載文（note掲載文.txt）と価格登録

> **`_meta.yaml` は作らない（2026-06-09 廃止）**。ペルソナ別マガジンの `_meta.yaml` はどのビルド/ジェネレータからも参照されない死蔵メモだった（[[feedback_essay_magazine_meta_yaml_retired]]）。掲載文は `.txt`、価格は note-magazines.ts と記事 frontmatter に集約する。

**1. `note掲載文.txt`（マガジン dir 直下・note へコピペする掲載文）**

`docs/note/技術士総監/magazines/総監模範論文-{persona}/note掲載文.txt` を作る。note の入力欄制限に合わせ、以下を厳守：

- **マガジンタイトル ≤ 30 字**（例: `総監 模範論文｜自治体下水道担当 R3-R7+R8予想`）
- **説明 ≤ 400 字** / **アピールポイント ≤ 250 字**
- 説明・アピールは **1 文 ≒ 1 段落**に区切る（note 可読性。本文は変えず改行のみ）
- **価格欄**を併記（例: `単品 ¥500／セット ¥2,480（7本・単品比29%OFF）`）

手本＝`総監模範論文-自治体下水道担当/note掲載文.txt`。文字数は実測する：

```
node -e "const fs=require('fs');const t=fs.readFileSync(process.argv[1],'utf8').split(/\r?\n/);/* タイトル/説明/アピール各行を [...s].length で確認 */" "<path>"
```

**2. 価格の真実源（SoT）**

| 価格 | 記載先 | 形式 |
|---|---|---|
| 単品（¥500） | 各記事 `article.md` frontmatter | `price: 500` |
| セット（¥2,480） | `src/lib/note-magazines.ts` の該当エントリ `price` フィールド | `price: '¥2,480（7本セット、単品比29%OFF）'` |

7本×¥500＝¥3,500 → ¥2,480 で **29%OFF**（5本構成の旧ペルソナは「5本セット」「17%OFF」表記）。**note-magazines.ts の `price` 追記漏れに注意**（旧 `_meta.yaml` 廃止で宙に浮きやすい）。

## Step 10: note 公開後のURL反映

note でマガジンを作成する際は、**マガジン名・説明・価格は `note掲載文.txt`（Step 6f）からコピペ**する。運営者から URL を受領したら：

1. 各記事本文のプレースホルダを実URLに置換：**`npm run note-inject-magazine-url -- {persona} {magazineURL}`**（冒頭・末尾の2箇所×記事数を一括置換。実体は `.claude/scripts/note/inject-magazine-url.cjs`、CRLF保持・旧バリアント吸収・冪等）。各記事の frontmatter `noteUrl:`/`noteId:` にも反映（公開済URLの真実源＝記事 frontmatter）
   - **手作業で置換しない**: `sed -i` は CRLF を LF に壊す、`{{MAGAZINE_URL}}` 以外の旧バリアントを取りこぼす、冪等性が無い——を全部自前で再実装することになり事故る（2026-06-11 Opus が既存スクリプトを探さず手置換し CRLF を一度破壊）。必ず上記スクリプトを使う（[[feedback_note_magazine_url_injection]]）。
   - **執筆時の規約**: マガジン誘導は **`{{MAGAZINE_URL}}` を単独行**で書く（推奨・新規はこの形式のみ）。`（{{MAGAZINE_URL}}）` のように**全角括弧で囲まない**／同一行に文を置かない（note でリンクカード化できず、注入後に `（https://note.com/.../m/xxxx）` の壊れたリンクになる＝港湾R03事故、2026-06-10）。
   - **自動検知**: `scripts/note-lint.mjs`（pre-commit）が「マガジンURL／`{{MAGAZINE_URL}}` の非単独行」「**markdown リンク形式のマガジンURL `[text](…/m/ID)`**」「**マガジンURL同一行の価格（¥）**」（後 2 者は検査項目 4b＝リンクカード化・CTA に価格を書かない、`content-principles.md §14-c`）「**公開状態の記事の3点セット欠落（`img/cover.png`・`hashtags.txt`）**」（検査項目 4c、`content-principles.md §14-d`）に加え、**部分注入**（同一マガジンdir内に実URL注入済み記事がありながら `{{MAGAZINE_URL}}` が残る記事＝注入漏れ）を BLOCK し、修正コマンド `npm run note-inject-magazine-url -- <persona> <url>`（persona・実URL自動抽出）を提示する。公開前＝全記事 placeholder のときは発火しない。注入漏れ変種は `inject-magazine-url.cjs` の `PLACEHOLDERS` 配列で吸収（空白・括弧バリアントも登録済）。
2. `src/lib/note-magazines.ts` の該当エントリを `published: true` ＋ `noteUrl`（マガジンURL）に更新。`price` フィールドは Step 6f で既に入っているはず（未記載なら追記）
3. 個別記事も note 投稿済みなら各 PDF を有料エリアに添付（Step 6e の冒頭訴求と対応）
